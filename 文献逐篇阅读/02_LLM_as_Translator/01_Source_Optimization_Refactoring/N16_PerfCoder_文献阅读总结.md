## 1. 研究背景

代码模型即使能生成正确程序，也常给出含糊或无效的“优化建议”。作者认为问题不仅是高质量代码对不足，更缺少“为什么这样优化”的策略监督和实测性能对齐。

## 2. 论文要解决的问题

如何让小模型一次性输出可读、针对输入的优化策略与代码，并进一步作为规划器指导更大、甚至闭源模型获得更高加速。

## 3. 核心方法概述

PerfCoder 重构 PIE 慢—快代码对，以用户最终/全局最佳提交替代模糊中间目标；由策略提取器生成自然语言优化轨迹并按策略类别均衡采样，先 SFT 学习“策略+代码”，再让小规划器通过 GRPO 和冻结的大优化器协作。

## 4. 实验框架与训练流程

```text
PIE 代码对 → 重构最优端点 → 提取/均衡优化策略 → SFT
 → 小 PerfCoder 输出策略 → 冻结外部模型写代码
 → gem5 运行反馈 → GRPO 只更新规划器
```

## 5. 奖励函数、损失函数或关键公式

SFT 使用因果语言建模损失。GRPO 中定义 `Δ=Tslow/Tgen`；编译失败给予强负奖（系数 ω=100），变慢奖励 -1，加速时奖励 `Δ²`，再进行组内相对优势计算。

## 6. 实验设置

### 6.1 数据集来源

原 PIE C++ 有 77,967 对；重构后 `Dref` 30,649 对，其中 12,350 对使用跨用户全局更优提交。测试为 978 个未优化程序，每个 20 个测试输入。

### 6.2 模型与工具

CodeLlama-7B、Qwen2.5-Coder-1.5B/7B 作为 PerfCoder 基座；外部优化器含 Qwen2.5 32B 与 GPT-5。运行时间按 PIE 协议使用 gem5 确定性模拟。

### 6.3 对比方法

GPT-4/5、CodeLlama、PIE 微调模型、Qwen/DeepSeek 32B、Effi-Learner，以及有无策略监督、类别均衡和 GRPO 的消融。

### 6.4 评价指标

Speedup；正确且至少 1.1× 的 Effective Optimization；通过全部测试的 Code Accuracy。

## 7. 实验结果与结论

PerfCoder-QC-7B 单步达到 2.50× 加速、33.13% 有效优化率，优于 PIE-Qwen2.5-Coder-HQ 的 1.98×/32.62% 和 GPT-5 的 1.96×/53.25%。1.5B 规划器经 GRPO 指导 32B 模型达到 3.03×；指导 GPT-5 达 4.82×、有效优化 79.86%、正确率 97.95%。去掉策略监督后加速从 2.50× 降到 2.11×。

## 8. 主要创新点

### 8.1 显式策略监督

训练目标不仅含最终代码，还含可检查、可迁移的优化意图。

### 8.2 重构和均衡 PIE 轨迹

用更明确的性能端点并提高长尾策略曝光。

### 8.3 小规划器—大优化器解耦

只用性能奖励训练规划器，可插拔地指导冻结的外部模型。

## 9. 局限性

仅 PIE 竞赛 C++ 和 gem5，实机、工程项目及跨硬件泛化未验证；20 个测试输入不能证明语义等价。自然语言策略由模型提取，可能存在伪解释；GPT-5 等闭源结果可复现性有限。

## 10. 阅读后的研究方向反思

PerfCoder 提醒我们：规划器小并不妨碍创新，关键是它是否学到可迁移、可执行的性能策略。后续应把策略与编译器 remark、IR 变化和硬件计数器对齐，避免只生成听起来合理的解释。

## 11. 可进一步尝试的研究方向

### 11.1 硬件证据对齐的优化策略规划器

#### 研究问题

自然语言策略能否与 cache miss、向量化 remark、分支事件形成可验证对应。

#### 与原论文的区别

策略监督加入编译器和硬件证据，并做 x86/K3 跨硬件条件规划。

#### 可能的创新点

“策略—IR 变化—计数器收益”三方一致性奖励。

#### 实验框架

```text
源码+remark+perf → 策略规划器 → 优化器 → 双硬件执行 → 一致性/性能奖励
```

#### 可行性与风险

工具易得；硬件计数器语义和可用事件跨平台不一致。

## 12. 与其他已读文献的关系

与 N05 的效率判别器互补：一个规划、一个筛选；与 N07 SBLLM 相比把多轮搜索知识蒸馏到单次策略；与 N03 StepCoder 同用 RL，但 PerfCoder 奖励运行速度而非编译/测试错误等级。

## 13. 一页式总结

| 项目 | 内容 |
|---|---|
| 论文研究任务 | 可解释的代码性能优化 |
| 核心问题 | 缺少策略监督与性能对齐 |
| 输入/输出 | 慢代码 / 策略与优化代码 |
| 核心方法 | PIE 重构 + 策略 SFT + 规划器 GRPO |
| 使用的模型 | CodeLlama、Qwen2.5、GPT-5 等 |
| 使用的编译器工具 | gem5 性能评测，编译版本未集中说明 |
| 是否使用强化学习 | 是，GRPO |
| 是否使用形式化验证 | 否 |
| 数据集规模 | 重构 30,649 对；测试 978 |
| 主要指标 | 加速、有效优化、正确率 |
| 最重要实验结果 | 1.5B 规划器+GPT-5 达 4.82× |
| 核心创新 | 显式策略监督与小规划器解耦 |
| 主要局限 | 竞赛代码、模拟器、策略可能非因果 |
| 与 RISC-V 研究的相关性 | 高；可加入 K3 证据监督 |
| 最适合作为 | 性能策略规划模块 |

> 最值得借鉴的是把性能知识单独训练进小规划器；下一步必须证明策略与真实编译/硬件事件一致。
