# UniTrans 文献阅读总结

论文题目：**Exploring and Unleashing the Power of Large Language Models in Automated Code Translation**

作者：Zhen Yang, Fang Liu, Zhongxing Yu, Jacky Wai Keung, Jia Li, Shuo Liu, Yifan Hong, Xiaoxue Ma, Zhi Jin, Ge Li

发表时间：2024 年 7 月

发表平台：Proc. ACM Softw. Eng., Vol. 1, FSE, Article 71；FSE 2024

论文链接或编号：[DOI 10.1145/3660778](https://doi.org/10.1145/3660778)，[arXiv:2404.14646v2](https://arxiv.org/abs/2404.14646)

关键词：自动代码翻译、大语言模型、测试用例增强、执行反馈、程序修复

> 以下事实均依据论文正文；UniTrans 的最终系统角色是直接输出目标源程序，因此建议归入 TRANSLATOR/T3。

## 1. 研究背景

源到源翻译用于跨语言迁移软件。规则式转译器需要为每种语言对手工编写大量规则；学习式转译器降低了规则成本，但依赖规模很大的单语预训练，准确率仍不足。论文考察 GPT-3.5、LLaMA、CodeGen 与 TransCoder 系列，并指出 LLM 翻译失败主要来自源程序理解不足、缺少输入输出类型信息，以及忽略源语言和目标语言差异。

## 2. 论文要解决的问题

### 2.1 LLM 翻译错误

作者分析 GPT-3.5 的 174 个失败样例：逻辑错误占 67 例，语法错误 38 例，I/O 错误 26 例，API 错误 14 例，精度错误 20 例，其他错误 9 例。论文将主要原因归结为源程序理解、I/O 类型提示和跨语言差异。

### 2.2 缺少轻量级纠错闭环

论文研究如何利用源程序生成的有效测试输入、目标语言格式化的 I/O 类型和执行结果，增强翻译提示并修复失败程序。

> 本文主要研究：如何在不重新训练转译器的情况下，用 LLM 生成测试用例、增强翻译提示，并依据编译/运行反馈迭代修复目标程序。

## 3. 核心方法概述

UniTrans 包含三个阶段：测试用例生成（TCG）、翻译增强（TAP）和翻译修复（TRP）。LLM 直接生成目标语言程序；源程序执行器、目标语言编译器/运行环境和错误分析器负责筛选测试、检查结果并提供反馈。

```text
源程序
  ↓
LLM 生成候选输入
  ↓
源程序执行器过滤有效输入并得到输出
  ↓
启发式转换为目标语言测试用例并补充 I/O 类型
  ↓
LLM 根据源程序和测试用例生成目标程序
  ↓
编译/运行目标程序并比较测试输出
  ↓
错误分析器提取错误行、错误信息或输出差异
  ↓
LLM 修复目标程序，可重复若干轮
```

它的关键区别是用测试用例作为程序需求和类型信息，并用真实执行结果辅助修复；它没有把程序变换交给一个新的编译器 pass。

## 4. 实验框架与训练流程

本文不涉及模型训练，主要采用一次提示、多次采样和执行反馈。

### 4.1 测试用例生成

LLM 每次根据源程序生成 10 组差异化候选输入。源程序执行这些输入，过滤无效输入并记录正确输出；再将输入输出按目标语言格式重写。对 Java、C++ 等静态类型语言，测试用例补充输入变量和输出类型。

### 4.2 翻译增强

作者将源程序、目标语言、测试用例放入 Translation Augmentation Prompt，要求生成能通过全部测试的目标程序。默认随机选取 3 个生成测试用例。

### 4.3 翻译修复

未通过测试的程序进入 TRP。错误分析器从编译错误、运行时错误和逻辑输出差异中抽取信息，再填入修复提示。默认修复 1 轮；实验还比较最多 0、1、2、3 轮。

## 5. 奖励函数、损失函数或关键公式

本文没有使用强化学习，因此不存在强化学习奖励函数，也没有训练损失函数。论文使用三个评估目标：

```text
EM Acc = 完全等于参考程序的翻译数 / 翻译样本总数
CA = 在给定测试套件上与参考程序产生相同结果的翻译数 / 样本总数
PR = 修复后通过的单元测试数 / 单元测试总数
```

EM Acc 是严格的字符串一致性指标；CA 只反映所给测试输入上的执行一致性；PR 用于分析部分测试通过情况。有限测试通过不等于形式化语义等价。

## 6. 实验设置

### 6.1 数据集来源

主要数据来自 GeeksforGeeks 代码翻译数据集，原始数据含 Python、Java、C++ 的 948 个平行函数；其中 568 个函数至少有一种语言的评估测试。作者人工清理发现 252 个噪声，包括 Python 132、Java 58、C++ 62 个，并由两名参与者交叉检查。六种翻译方向为 Java↔Python、C++↔Python、Java↔C++。论文还用大学私有 OJ 上人工编写的 82 个 C++ 程序检查潜在数据泄漏。

### 6.2 模型与工具

模型包括 gpt-3.5-turbo-0613、LLaMA-7B/13B/33B、CodeGen-6B-multi，以及 TransCoder、TransCoder-IR、TransCoder-ST。LLM 默认使用 top_p=0.95、temperature=0.8、每个翻译 10 个样本；开源模型通过 HuggingFace/复现包加载。执行环境用于运行源程序、编译和运行目标程序；具体编译器版本论文中未明确说明。

### 6.3 对比方法

主要对比是 GPT-3.5、LLaMA、CodeGen 与三个学习式转译器。UniTrans 的消融比较基础 LLM、加入 TAP、加入 TRP 的逐步结果。

### 6.4 评价指标

| 指标 | 含义 | 趋势 |
|---|---|---|
| CA | 给定测试套件上的执行结果一致率 | 越大越好 |
| EM Acc | 与参考程序字符串完全一致率 | 越大越好 |
| PR | 单元测试层面的通过率 | 越大越好 |

## 7. 实验结果与结论

### 7.1 主要结果

基础模型中 GPT-3.5 在四个主要翻译方向平均达到 87.92% CA、18.04% EM Acc。加入 UniTrans 后，LLaMA-7B 平均 CA/EM Acc 提升 28.58%/71.22%，LLaMA-13B 提升 19.20%/36.42%，GPT-3.5 提升 4.02%/13.28%。这些是相对对应基础模型的平均改进。

### 7.2 组件消融

TAP 对理解逻辑、I/O 类型和语法差异帮助明显；TRP 在 TAP 后继续修复编译、API 和部分逻辑错误。GPT-3.5 上 TAP 后平均 CA 为 87.65%，加入 TRP 后为 89.31%。

### 7.3 测试用例数量

测试用例从 0 增加到 1、3、5 时，覆盖率通常上升，但过多测试会占用提示空间并引入冗余。LLaMA-7B 在不超过 3 个测试用例时表现较好；GPT-3.5 在部分设置中可利用 5 个。

### 7.4 迭代修复与案例

GPT-3.5 通常在 2 轮修复附近达到较好结果，LLaMA-7B 有时在第 3 轮继续提升；继续修复也可能使程序退化。失败案例显示，测试用例能纠正逻辑误解，错误信息能帮助修复 Java API 误用。

## 8. 主要创新点

### 8.1 将源程序辅助测试用例贯穿翻译生命周期

测试输入由源程序校验并生成正确输出，再用于翻译提示和执行检查，连接了需求理解、类型补充与错误修复。

### 8.2 将翻译增强和翻译修复解耦

TAP 负责在生成目标程序前增加约束，TRP 只处理未通过测试的程序，降低了对所有样本进行昂贵多轮修复的成本。

### 8.3 系统评估了 LLM 翻译失败类型

174 个失败样例的分类帮助作者将方法设计对应到逻辑、I/O、语法、API 和精度问题，而不是只报告总体准确率。

## 9. 局限性

### 论文明确承认的局限

论文指出测试用例数量过多会造成提示冗余；多轮修复会增加时间并可能退化。评估数据清理后仍可能残留噪声，GPT-3.5 的训练数据不可见，闭源模型的数据泄漏难以完全排除。模型和语言对数量也有限。

### 阅读后的潜在局限

CA 只覆盖给定测试输入，不能证明完整语义等价；测试用例由 LLM 生成并受源程序执行过滤，可能覆盖不足。方法依赖目标语言编译和运行环境，论文没有报告跨架构或 RISC-V 实验。修复只使用第一个失败测试提示，可能忽略多个相互作用的错误。

## 10. 阅读后的研究方向反思

值得借鉴的是“源程序信息—可执行测试—反馈修复”的闭环，以及用 CA 和 PR 补充 EM Acc 的评估方式。UniTrans 的核心贡献是跨语言翻译中的测试增强与修复，不能仅把目标语言替换成 RISC-V 汇编就视为新研究。它更适合作为 TRANSLATOR baseline 或测试反馈工具模块，而不是 pass 选择器。

对 RISC-V 的相关性为中等偏低：可以迁移其测试反馈思想到 C/C++ 到 RISC-V 汇编或 LLVM IR 翻译，但必须新增 ISA 语义、ABI、寄存器约束和真实执行验证，单纯换目标语言不足以形成贡献。

## 11. 可进一步尝试的研究方向

### 11.1 面向 RISC-V ABI 的翻译测试闭环

#### 研究问题

如何从 C/C++ 源程序生成能覆盖 RISC-V ABI、寄存器和向量指令边界的测试。

#### 与原论文的区别

增加 ISA/ABI 约束和跨模拟器、真实板卡的差分执行，不只是更换目标语言名称。

#### 可能的创新点

设计 ABI 感知的输入生成与错误定位策略。

#### 实验框架

```text
C/C++ → LLM 生成 RISC-V LLVM IR/汇编 → QEMU/硬件执行 → 差分反馈 → 修复
```

#### 可行性

需要 LLVM、RISC-V 工具链、QEMU 或 RVV 硬件和可执行测试集。

#### 主要风险

模拟器与真实硬件行为、未定义行为和浮点精度差异会影响反馈可靠性。

### 11.2 测试覆盖驱动的跨语言翻译预算控制

研究如何根据覆盖增益动态决定测试数量和修复轮数，区别于 UniTrans 固定采样 3 个测试用例和固定修复轮数。需要记录覆盖率、token 成本和 CA/PR 的联合曲线。

## 12. 与其他已读文献的关系

UniTrans 与直接源代码优化工作同属 TRANSLATOR，但目标是跨语言迁移而非性能变换；与编译器反馈修复类工作相似之处是使用外部执行结果，区别是反馈来自目标程序测试而非 LLVM 优化报告。它可作为跨语言翻译 baseline，也可为需要执行反馈的后续编译器翻译系统提供测试生成模块。当前批次没有其他已完成正文的论文可进行更细粒度横向比较。
