## 1. 研究背景

本文研究项目级自动程序翻译，具体实现是把真实 Go 项目翻译成 Rust。引言指出，代码翻译可用于软件现代化、多语言 SDK 维护和迁移到具有安全或性能优势的语言；Rust 的内存安全和无运行时开销使 Go 到 Rust 的迁移具有实际动机（第 1 节）。

传统方法主要有两类：基于规则或符号的翻译，以及基于机器学习/LLM 的翻译。规则方法可以通过构造保证 I/O 等价，但容易产生不够地道、难维护的代码；LLM 方法更可能生成符合目标语言习惯的代码，却没有天然的正确性保证。已有工作通常结合单元测试、差分模糊测试或形式化验证，在验证失败后重新生成代码，但主要处理竞赛题、小片段或小规模真实代码。项目级翻译还受到上下文窗口、错误概率随代码规模增加、跨语言特性不直接对应和错误修复循环的限制（第 1 节，第 2 页）。

本文没有把 LLM 当作一个已经具有编译器正确性保证的编译器，而是把 LLM 的代码生成能力放入分片、依赖分析、编译检查、类型兼容性检查和 I/O 测试组成的翻译流程中。研究价值在于探索如何把“能编译”推进到“在测试覆盖到的输入输出上通过等价检查”，同时把翻译扩展到数千行代码的完整项目。

## 2. 论文要解决的问题

### 2.1 项目规模问题

如何将超过单一上下文或单一提示适合范围的真实项目拆成可独立翻译的片段，并在依赖关系下逐步形成完整目标项目？论文将函数/方法、类型定义和全局变量声明作为片段；互递归函数放在同一片段中（第 2.2 节，第 3 节）。

### 2.2 跨语言特性映射问题

Go 与 Rust 在错误处理、接口/trait、全局变量初始化、可空类型、可见性和模块组织方面存在语义或组织差异。仅让 LLM 模仿源代码表面语法，可能生成看似地道但不能编译或语义不等价的 Rust。论文要解决的是如何用预定义 feature mapping 规则指导 LLM，同时保留 LLM 生成较自然代码的能力（第 2.3 节、第 4 节）。

### 2.3 早期错误发现与局部修复问题

如果类型错误等到后续函数或集成测试才暴露，错误会沿依赖图传播并增加回溯成本。论文提出 type-compatibility 检查，在类型或函数签名生成后立即检查源值能否跨语言映射到目标类型，以缩小修复范围（第 2.3 节、第 5.2 节）。

### 2.4 语义验证问题

项目的完整翻译不应只以编译成功作为目标。论文使用源项目单元测试产生的执行快照，检查目标函数在相同输入上的输出和副作用是否与源函数一致；但这种 I/O 等价是基于收集到的测试输入的有限验证，不是对所有输入的形式化证明（第 6 节、第 7.1.1 节）。

> 本文主要研究：如何将真实 Go 项目分片后，用 LLM 生成 Rust 翻译，并通过 feature mapping、type-compatibility、编译检查和基于执行快照的 I/O 等价测试，提高项目级翻译的可编译性与可验证比例。

## 3. 核心方法概述

论文实现了 Oxidizer。其最终 LM 输出是目标语言 Rust 代码片段，因此按 Taxonomy v2 的最终角色规则属于 TRANSLATOR；编译器、静态检查、依赖分析和测试工具负责约束、验证和修复，不改变 LM 的最终角色。

整体数据流如下：

```text
输入：Go 项目及其单元测试
        ↓
执行快照收集：记录函数输入、输出以及输入/全局状态副作用
        ↓
项目分片：函数/方法、类型、全局变量；建立依赖图并后序遍历
        ↓
LLM 读取源片段、已翻译依赖摘要和 feature mapping 规则
        ↓
生成 Rust 片段
        ↓
编译检查与局部修复 + type-compatibility 检查
        ↓
得到可编译且类型兼容的项目翻译；困难函数可生成可调用原 Go 函数的 mock
        ↓
语义阶段：冻结签名，使用 mock 被调函数做 I/O 等价单元测试
        ↓
输出：Rust 项目、通过/未通过的函数、必要时的函数 mock
```

方法包含四个主要阶段（第 2 节图 1、第 7.1.1 节）：

1. **Execution Snapshot Collection**：对 Go 项目函数插桩，执行原项目单元测试，记录 JSON 格式的输入、输出、输入状态变化和全局状态变化。
2. **Project Partitioning**：按声明构造代码片段，计算依赖关系，并按依赖图后序顺序翻译。
3. **Type-Driven Translation**：LLM 生成片段；feature mapping 规则通过自然语言指导和静态检查约束跨语言特性；Rust 编译器错误用于局部重新查询；随后检查类型兼容性。
4. **Semantics-Driven Translation**：对已类型兼容的翻译构造函数级 I/O 测试，mock 被测函数的 callees；等价失败时保持签名不变，重新生成和修复函数体。

feature mapping 规则由三部分组成：适用的语法模式、给 LLM 的自然语言规则说明、检查规则是否被正确应用的静态检查（第 4 节）。示例包括 Go 全局变量函数初始化映射到 Rust `Lazy::new`、Go 错误处理映射到 Rust `Result`/`anyhow::Error`、Go 接口映射为由多个子 trait 组合的 Rust trait。

## 4. 实验框架与训练流程

### 4.1 模型与推理流程

本文不涉及预训练、SFT、PPO、GRPO 或其他模型训练，主要采用推理阶段的 LLM 查询与工具反馈。实验使用 Anthropic Claude 3 Sonnet，经 Amazon Bedrock 提供；Oxidizer 也支持配置专有或开源 LLM，并记录 LLM 输入输出以便离线 replay（第 7.1.1、7.1.2 节）。

### 4.2 类型驱动阶段

对依赖图后序遍历的每个片段，系统先取得适用 feature mapping 规则和已翻译依赖摘要，然后查询 LLM。若 feature mapping 静态检查失败，重复查询；若 Rust 编译失败，使用编译器错误消息对当前片段进行局部修复；若 type-compatibility 失败，再次查询。算法 2 中，只有同时满足编译成功和类型兼容，片段才被加入翻译映射。

当达到最大尝试次数而签名仍可类型兼容时，系统可以用一个保持兼容签名、内部调用原 Go 函数的 mock 继续翻译项目；如果无法获得类型兼容签名，则中止该项目翻译（第 5 节）。

### 4.3 语义驱动阶段

算法 3 对每个已保存片段执行 I/O 等价检查。测试使用源项目的执行快照，并 mock 当前函数的 callees 以隔离被测函数。若不等价，系统冻结签名，只重新生成函数体并再次编译、测试，直到成功或达到尝试预算。论文报告该阶段不是全局形式化验证，也不保证未被测试覆盖的输入上的等价性。

### 4.4 实验参数

论文设置 feature mapping 的 `requery_budget` 为 10，算法 2 的 `max_tries` 为 15，算法 3 的 `max_tries` 为 5；Claude 3 Sonnet 的 temperature 为 0.2（第 7.1.4 节）。

## 5. 奖励函数、损失函数或关键公式

本文没有使用强化学习，因此不存在强化学习奖励函数或训练损失函数。

论文的关键目标是约束和验证，而不是优化一个显式数值奖励。重要定义包括：

### 5.1 Type-compatibility

对于源类型 `T`、可行值集合 `V` 和目标类型 `Tr`，如果每个 `v ∈ V` 都能通过源类型序列化和目标类型反序列化得到目标值 `vr`，并且可以反向还原，则称 `Tr` 关于 `V` 与 `T` 类型兼容（定义 1，第 14 页）。`V` 在本文中来自单元测试产生的执行快照，因此兼容性结论依赖这些可观察值。

### 5.2 I/O 等价

对于源函数 `f` 和目标 Rust 函数 `g`，论文要求：源函数成功时，目标函数在序列化/反序列化后的对应输入上返回相同输出状态；源函数失败时，目标函数也返回错误（定义 5，第 17 页）。输入输出还扩展了副作用状态，包括输入和全局变量的变化。

### 5.3 评价目标

实验主要报告两类比例：

| 指标 | 含义 | 口径 |
| --- | --- | --- |
| `% Compiled` | 可编译函数比例、可编译代码行比例 | `Func.` / `LoC.` |
| `% Equiv.` | 通过 I/O 等价测试的函数比例、代码行比例 | `Func.` / `LoC.`；未收集到样例的函数标记为未等价 |

论文没有把这些比例表述为所有输入上的语义证明；它们是基于源项目单元测试执行快照的经验性验证结果。

## 6. 实验设置

### 6.1 数据集来源

论文没有使用传统机器学习训练集、验证集和测试集，而是从 GitHub 选择 8 个真实 Go 开源项目作为翻译 benchmark。选择条件主要是项目拥有超过 100 个 GitHub stars 或近期仍在维护，并且评测项目只使用 Go 标准库；项目覆盖银行业务、统计、字符串算法、TextRank、近似直方图、姓名解析和校验码等场景（第 7.1.3 节）。

执行快照来自各项目已有的单元测试。系统记录函数输入、返回值、错误和副作用的前后状态；如果函数没有收集到任何输入输出样例，系统创建一个自动失败的空单元测试。因此，论文的等价率既受翻译质量影响，也受原始测试覆盖率影响。

| 项目 | LoC | 函数/方法 | 结构体/接口 | 语句覆盖 | 函数覆盖 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `geo` | 9766 | 780 | 75 | 87.0% | 87.6% |
| `ach` | 6642 | 369 | 75 | 92.9% | 95.2% |
| `go-edlib` | 639 | 25 | 1 | 100% | 100% |
| `stats` | 1241 | 79 | 8 | 93.2% | 99.2% |
| `textrank` | 1132 | 69 | 20 | 94.6% | 98.3% |
| `histogram` | 314 | 23 | 5 | 43.2% | 61.9% |
| `gonameparts` | 413 | 15 | 2 | 96.1% | 100% |
| `checkdigit` | 428 | 29 | 9 | 100% | 100% |

### 6.2 模型与工具

- 基础模型：Anthropic Claude 3 Sonnet，经 Amazon Bedrock 提供；论文没有给出参数量。
- 翻译工具：Oxidizer，核心模块为执行快照收集器、项目分片器、类型驱动翻译器和语义驱动翻译器。
- 解析与插桩：Python、`py-tree-sitter`。
- 编译与测试：Rust 编译器、Rust 单元测试、Go 项目原有单元测试、JSON 序列化/反序列化机制。
- 规则与检查：feature mapping 静态检查、依赖分析、类型兼容性检查、I/O 等价测试。
- 硬件：论文未报告专门的真实硬件性能实验；主要测量翻译、编译和测试结果。

### 6.3 对比方法

论文以 Oxidizer 的完整配置为主，并进行三种消融：

1. **No Semantics-Driven**：关闭语义驱动阶段，用于衡量 I/O 等价修复阶段的作用。
2. **No Type Check**：关闭 type-compatibility 检查，但保留 feature mapping。
3. **No Feature Map**：同时关闭 feature mapping，用于观察缺少跨语言特性规则的影响。

此外，论文与两个并行的整项目 LLM 翻译工作做结果层面的比较：一个主要报告可运行/可编译结果，另一个报告平均约 25.8% 函数的 I/O 等价验证率；由于它们不支持 Go 源语言或不能直接在相同 benchmark 上运行，论文没有把它们作为同条件复现实验 baseline（第 7.2 节、第 8 节）。

### 6.4 评价指标

- **可编译函数比例**：成功编译的函数数量占总函数数量的比例。
- **可编译代码行比例**：成功编译代码行占总代码行的比例。
- **I/O 等价函数比例**：在执行快照上通过输出和副作用比较的函数比例；没有样例的函数自动不通过。
- **I/O 等价代码行比例**：通过等价验证的函数涉及代码行占总代码行的比例。
- **运行时错误**：语义验证时由于跨语言值映射或执行失败导致测试崩溃的情况；论文特别比较了这种错误与断言失败的区别。

## 7. 实验结果与结论

### 7.1 主要结果

完整 Oxidizer 配置在 8 个项目上的平均结果为：98% 的函数、97% 的代码行可编译；73% 的函数、67% 的代码行通过 I/O 等价验证（表 2）。最大项目 `geo` 为 9766 行代码、780 个函数；论文摘要将实验范围概括为最多 9700 行、780 个函数，平均 73% 函数成功验证 I/O 等价。

逐项目完整配置的 `% Compiled Func./LoC.` 与 `% Equiv. Func./LoC.` 为：

| 项目 | 可编译 Func./LoC. | 等价 Func./LoC. |
| --- | --- | --- |
| `geo` | 94 / 85 | 68 / 59 |
| `ach` | 96 / 92 | 65 / 62 |
| `textrank` | 97 / 95 | 75 / 78 |
| `go-edlib` | 100 / 100 | 81 / 89 |
| `stats` | 100 / 100 | 73 / 61 |
| `histogram` | 100 / 100 | 63 / 43 |
| `gonameparts` | 100 / 100 | 71 / 57 |
| `checkdigit` | 100 / 100 | 86 / 85 |

这些数字是函数比例和代码行比例，不是运行时间加速比，也不是所有可能输入上的证明结果。

### 7.2 与传统规则式方法和可运行性比较

论文不把 Oxidizer 与完整的纯符号翻译器做同条件数值比较，而是讨论方法取舍：纯规则方法更容易保持语义，但可能不够地道；Oxidizer 通过规则约束 LLM，并允许 LLM 生成名称、类型和表达式等细节。与并行整项目工作相比，Oxidizer 的平均可编译比例约为 98%，同时对 I/O 等价的验证比例更高。

### 7.3 消融实验

- **No Type Check**：平均可编译率为 98%/95%，等价率为 62%/60%，低于完整配置的 73%/67%；type-compatibility 在 7 个 benchmark 中的 5 个提高了函数等价率，通常提高 5%–35%，有一例提高 144%。
- **No Feature Map**：平均可编译率只有 27%/20%，等价率为 0；算法 2 在所有 benchmark 上中止，因此 feature mapping 是获得稳定项目级翻译的关键组成。
- **No Semantics-Driven**：平均可编译率为 98%/96%，等价率为 72%/66%，与完整配置接近。8 个 benchmark 中有 5 个没有由语义阶段修复任何非等价函数；其余 3 个中，`geo` 修复 15 个、`ach` 修复 4 个、`textrank` 修复 1 个，成功修复一个非等价函数平均需要 2.65 次查询。

### 7.4 案例和失败模式

- Go 的全局变量可以由任意函数初始化，而 Rust 静态全局变量需要适合编译期求值的初始化；feature mapping 将其映射到 `Lazy::new`。
- Go 的可空切片若直接映射为 Rust `Vec` 会丢失 `nil` 情况；type-compatibility 检查促使系统改用包裹 `Option` 的类型。
- Go 结构化接口与 Rust 名义 trait 的关系不同；论文用子 trait 和自动实现保留部分接口组合关系。
- 53% 的 `ach` 非可编译函数涉及需要改变表面语法的 use-after-move 模式；LLM 倾向于直接模仿源语法。
- `stats` 中随机置换代码可以被正确翻译，但由于随机性，论文无法用当前方法验证它与原实现的等价性。

## 8. 主要创新点

### 8.1 创新点一：面向整项目的分片式 LLM 翻译流程

论文不是把整个项目一次性放入提示，而是按声明分片、构造依赖图、后序翻译，并在片段级保存结果。这是解决上下文规模和错误传播问题的系统设计。论文在 8 个真实 Go 项目上报告了最高 9766 行规模的实验，但该结果不等于对所有项目语言或规模都成立。

### 8.2 创新点二：Feature mapping 与 LLM 生成的混合约束

feature mapping 将跨语言特性差异写成“适用模式 + 自然语言指导 + 静态结论检查”。与完全符号化翻译相比，它保留了 LLM 生成较地道代码的自由度；与无规则提示相比，它显著减少了错误特性映射。消融实验中关闭该模块后算法无法可靠完成项目级翻译，支持其有效性。

### 8.3 创新点三：基于执行快照的局部 type-compatibility

论文把“目标类型能否承载源项目测试中出现的可行值”作为早期检查条件，用 JSON 序列化/反序列化实现跨语言值检查。它不是简单要求源/目标类型名称或结构完全相同，而是关注跨语言边界上的可转换性，并能在函数签名或类型定义刚生成时暴露问题。

### 8.4 创新点四：类型驱动与语义驱动两阶段验证

类型驱动阶段先保证编译和类型兼容，语义驱动阶段再冻结签名、隔离 callees 并验证 I/O 等价。这种分层让错误更局部；不过论文结果也表明，语义驱动修复阶段的增益有限，主要效果来自前置的特性映射与类型检查。

## 9. 局限性

### 9.1 论文明确承认或实验直接体现的局限

- 实现只具体支持 Go 到 Rust，虽然作者认为思想可扩展到 C/C++，但没有在本文中验证其他语言对。
- 等价检查依赖源项目单元测试的执行快照；没有样例的函数自动失败，测试覆盖率会直接影响等价率。
- 随机行为等非确定性函数可能无法被当前快照方法验证，即使翻译逻辑本身正确。
- 某些 Rust 借用检查器约束要求改变源代码表面结构，LLM 仍可能产生不可编译翻译；难以翻译的函数可以被 mock，但这意味着该函数本体没有被翻译为 Rust。
- 只报告基于测试的 I/O 等价，不构成对所有输入的形式化语义等价证明。
- 评测项目主要使用 Go 标准库，第三方库映射虽被工具支持，但不是这组主要 benchmark 的核心覆盖范围。

### 9.2 阅读后发现的潜在局限

- `type-compatibility` 的可行值集合取自测试执行，不是完整静态可行域；未见于测试的边界值可能仍导致类型或语义错误。
- LLM 日志 replay 有助于复现，但结果仍依赖 Claude 3 Sonnet、提示和预算设置；论文没有报告跨模型系统性对照。
- mock 允许项目继续翻译，但最终 Rust 项目可能保留对原 Go 函数的外部调用，因而“项目完成”与“全部代码本地 Rust 化”需要区分。
- 论文的主要指标是编译和等价比例，没有把翻译时间、LLM 查询成本、人工修复成本作为主结果展开比较。

## 10. 阅读后的研究方向反思

本文最值得借鉴的是“先让跨语言边界可检查，再做更细的语义验证”的分层思想，而不是简单把 LLM 接在编译器报错后面。对于 LLM 与编译器研究，Oxidizer 可作为项目级翻译、编译反馈和有限语义验证的 baseline 或工具框架。

本文的核心贡献已经是 Go/Rust 特性映射、执行快照驱动的类型兼容和 Oxidizer 流程；仅把目标语言替换成 RISC-V 汇编或把 Go/Rust 替换成另一对语言，通常只能算方法迁移。若面向 RISC-V，必须增加新的研究问题，例如寄存器/调用约定/向量类型的跨层语义映射、ISA 扩展约束下的可验证翻译，或跨架构目标的可迁移规则学习。论文自身没有实验 RISC-V，也没有证明其规则可直接覆盖 RISC-V 后端。

从 taxonomy 角度看，LLM 的最终输出是目标 Rust 源代码，属于 TRANSLATOR/T3；依赖分析、编译器诊断和测试反馈是横向机制，不能据此改成 SELECTOR 或 GENERATOR。type-compatibility 是验证与边界约束模块，不是形式化证明。

## 11. 可进一步尝试的研究方向

### 11.1 基于覆盖缺口的跨语言语义验证

#### 研究问题

如何在有限单元测试之外，针对未覆盖分支、边界值和错误路径自动补充能区分源/目标行为的输入？

#### 与原论文的区别

原论文主要复用源项目单元测试生成执行快照；新方向把覆盖缺口分析、差分测试或符号约束用于主动扩展快照集合，而不是只重复查询 LLM。

#### 可能的创新点

将覆盖信息、序列化边界和跨语言差异模式结合，形成面向翻译验证的输入生成策略，并区分随机行为与真正语义差异。

#### 实验框架

```text
源项目测试与覆盖信息
        ↓
识别未覆盖路径和跨语言高风险特性
        ↓
生成额外输入/差分测试
        ↓
运行 Go 与 Rust 实现
        ↓
更新类型兼容与 I/O 等价证据
```

#### 可行性

需要源/目标编译器、覆盖工具、差分执行框架和可序列化的输入输出表示；Oxidizer 的执行快照接口可作为起点。

#### 主要风险

复杂状态、非确定性、外部 I/O 和不可序列化对象可能使差分测试难以稳定；额外测试也不自动等于形式化保证。

### 11.2 面向多目标 ISA 的类型与特性映射

#### 研究问题

如何将同一高层源程序映射到具有不同调用约定、向量类型和内存模型约束的目标后端，同时保持可编译性与可验证的行为边界？

#### 与原论文的区别

原论文只实现 Go 到 Rust 的源语言翻译；新方向增加跨 ISA/后端语义，目标不是简单换一个目标文件格式。

#### 可能的创新点

把目标 ISA 特性、编译器 IR 类型约束和可验证的 ABI/寄存器约束纳入 feature mapping，并让规则检查与后端编译诊断联动。

#### 实验框架

```text
源程序与高层类型信息
        ↓
LLM 生成目标源/IR 候选
        ↓
目标 ISA/ABI 规则检查
        ↓
编译器后端与差分测试
        ↓
候选修复和跨目标结果比较
```

#### 可行性

需要 LLVM/目标后端、RISC-V 或其他 ISA 工具链、ABI 测试和可重复的 benchmark；论文提供的分片与局部修复思路可以复用。

#### 主要风险

低层代码的未定义行为、寄存器分配和性能差异可能无法由有限 I/O 测试充分捕获；不能把编译成功当作性能或语义等价。

### 11.3 可审计的跨语言规则学习与人工偏好控制

#### 研究问题

如何从历史翻译、编译错误和人工修复中学习新的 feature mapping 候选，同时保证每条规则可解释、可回滚和可验证？

#### 与原论文的区别

原论文中的 mapping 规则由开发者预定义；新方向研究规则的增量发现与审计，而不是仅扩大手写规则表。

#### 可能的创新点

使用错误聚类和反例驱动归纳提出规则草案，再用静态检查、测试和人工确认将其纳入规则库；为每条规则记录适用条件、反例和验证证据。

#### 实验框架

```text
翻译日志、编译错误、人工修复
        ↓
按跨语言特性聚类并生成规则草案
        ↓
静态检查与反例测试
        ↓
人工确认/拒绝
        ↓
版本化规则库驱动后续翻译
```

#### 可行性

需要 Oxidizer 日志、规则 DSL、编译器诊断解析器和回归测试集；论文已明确记录 LLM 输入输出，可作为数据来源。

#### 主要风险

规则过拟合特定项目，或把偶然编译修复误归纳为语义规则；规则库变更可能引入难以定位的回归。

## 12. 与其他已读文献的关系

本次子任务只正式处理 C70 一篇论文，因此没有在本批次内完成多论文横向实验比较。论文正文自身将 Repository-Level Compositional Code Translation、Context-aware Code Segmentation for C-to-Rust Translation、VERT 和其他代码翻译工作列为相关工作；这些文献在本文中承担比较背景，不能替代本次对其正文的独立阅读。

与本仓库已有的 LLM 编译器语料相比，C70 的明确边界是“LLM 直接输出跨语言目标源代码并由工具验证”，因此适合作为 TRANSLATOR/T3 的项目级翻译与验证 baseline；不能仅因为使用了编译器错误或测试反馈，就把它当作 pass 选择或编译器搜索论文。
