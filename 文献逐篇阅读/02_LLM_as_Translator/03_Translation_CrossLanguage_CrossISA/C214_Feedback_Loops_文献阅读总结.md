# Feedback Loops and Code Perturbations in LLM-based Software Engineering：C-to-Rust 翻译系统

> 阶段2交付包；仅写入 A2 staging。事实均以本包 PDF 为正文依据，并在文中标注页码/表格；网页用于元数据核验。

## 1 研究背景

论文研究自动化软件工程中的 LLM 代码翻译可靠性。具体场景是把 C 函数翻译为 Rust：Rust 具有内存安全等安全性优势，但生成结果必须同时满足编译、静态检查与行为一致性要求。论文将自动化翻译系统建模为“生成—检查”流程：LLM 生成 Rust，编译器/Clippy 检查可编译性与 lint，差分模糊测试检查与原 C 行为是否一致（摘要、pp.1–3）。

元数据：Martin Weiss、Jesko Hecking-Harbusch、Jochen Quante、Matthias Woehrle；2026；SANER 2026 Industrial Track，pp.367–376；DOI `10.1109/SANER67736.2026.00047`；arXiv `2512.02567`。权威入口：[SANER 2026 论文条目](https://conf.researchr.org/details/saner-2026/saner-2026-industrial-track/6/Feedback-Loops-and-Code-Perturbations-in-LLM-based-Software-Engineering-A-Case-Study)、[DOI](https://doi.org/10.1109/SANER67736.2026.00047)、[arXiv](https://arxiv.org/abs/2512.02567)。

版本族：arXiv v1 于 2025-12-02 提交，PDF 当前为 v2（页眉标注 2026-08-05）；当前 staging PDF 为 10 页的 IEEE/SANER 版本。arXiv 与会议版本标题、作者和核心实验一致，会议版本增加正式出版元数据。

## 2 论文要解决的问题

论文考察三个变量如何影响 C-to-Rust 翻译成功率（摘要、p.2）：

1. 自动反馈循环增加到多轮后，编译/行为检查失败是否能被修复？
2. 不同 LLM 的选择是否决定翻译成功率，以及反馈循环是否会缩小模型差异？
3. 对原始 C 代码施加保持行为的扰动后，翻译系统是否仍然稳健，扰动多样性是否反而提供有益的候选？

论文没有把“通过编译”当作充分正确性证明；差分模糊测试只是行为一致性的实证检查，不能证明形式等价（pp.2, 8–9）。

## 3 核心方法概述

核心系统是带外部检查器的迭代 Translator/T3：原始或扰动后的 C 代码输入 LLM，LLM 输出 Rust；Rust 编译器和 Clippy 检查编译与 lint；C 侧使用 clang/libFuzzer 生成测试，Rust 侧通过 FFI 执行相应逻辑，比较输出；若检查失败，把错误反馈重新提示 LLM，最多继续指定轮数（pp.3–4）。

方法包含三种实验操纵：模型选择、最多 5 次内部反馈循环、以及 51 类代码扰动的随机组合。系统还用重复运行估计 pass@k，而不是只报告一次采样结果（pp.4–6）。

最终 LM 输出角色是 Translator：输出目标语言 Rust 程序，而非选择 compiler pass/flag 的 Selector，也不是只生成测试/数据等支持性产物。反馈循环负责修复 Translator 输出，编译器、Clippy 和差分模糊测试是外部验证器。

## 4 实验框架与训练流程

论文不进行模型训练或微调；使用现成 LLM 的默认调用设置。评估对象为一个自动化 C-to-Rust 翻译系统，流程为：C 输入（可选扰动）→ LLM 生成 Rust → 编译器/Clippy → C/Rust 差分模糊测试 → 失败反馈再提示（Fig.1，p.3）。

模型为 GPT-3.5 Turbo、GPT-4o mini 和 Phi-4，默认参数、temperature 0.7（p.4）。每个系统配置最多 5 个内部反馈迭代；另以 20 次重复运行估计 pass@k（p.5）。反馈循环的输入是编译、lint 或差分检查的失败信息；正文没有给出完整 prompt 模板，也没有报告训练数据或参数更新。

## 5 奖励函数、损失函数或关键公式

论文没有使用奖励函数、损失函数或训练目标；这是评估现成 LLM 的软件工程系统。关键判定是检查器驱动的二值成功条件：生成 Rust 可编译、通过 Clippy，并在差分模糊测试中未观察到与原 C 不同的行为（pp.3–5）。

pass@k 用多次独立运行估计至少有一个成功候选的概率；正文报告该指标及其随反馈循环数量的变化，但当前 PDF 未给出统一的显式数学定义。差分模糊测试在限定时间内未发现 counterexample 被视作成功信号，而非形式等价证明（p.8）。

## 6 实验设置

数据集包含 50 个 C 文件、76 个函数：30 个内部汽车嵌入式样例、10 个开源音频/声卡样例、10 个竞赛编程样例（p.4）。内部数据不可公开。文件最多 296 行，平均约 40 行；平均 token 数约 454，平均圈复杂度 2.4（p.4）。

扰动共 51 类，分为六级：I 注释/缩进，II 标识符，III 声明，IV 函数，V 语义等价变换，VI 决策逻辑/表达式（p.5）。论文用随机组合构造更广泛的输入，另对 20 个扰动组成的随机集合进行 10,000 次采样分析（p.8）。

一次成功要求编译与 lint 检查通过，并且 C 与 Rust 的差分模糊测试未发现行为差异。每个配置最多 5 次反馈循环；重复运行用于 pass@5 等统计。论文明确指出 fuzzing 受测试覆盖、API、内容策略和超时影响，不能替代形式验证（pp.5, 8–9）。

## 7 实验结果与结论

在 GPT-4o mini 上，随最大反馈循环从 1 增至 5，编译成功率从 0.88、0.98、0.98 提升到 1.00；最终综合结果从 0.69、0.78、0.78 提升到约 0.79（Table III，p.6）。第一轮反馈带来的增益最大，论文摘要概括为最高约 24 个百分点（p.2）。

没有反馈循环时，LLM 选择对翻译成功率影响明显；启用反馈循环后，模型之间的差距缩小。总体上，循环和重复采样共同提高成功率，论文摘要报告两者合用最高可带来约 50% 的相对改进（p.2）。

扰动实验显示 GPT-4o mini 对多数扰动保持稳健，但 Level IV 的函数级提取较困难。不同扰动可提供候选多样性，随机组合实验观察到 pass@5 最多约 9% 的改进（p.8）。论文结论是反馈循环的边际收益主要集中在第一轮，代码扰动通常影响较小但可能通过增加多样性提升结果。

## 8 主要创新点

1. 把反馈循环、模型选择和行为保持代码扰动放在同一个真实 C-to-Rust Translator 系统中进行联合实证，而不是只比较一次性生成。
2. 用编译器、Clippy 与差分模糊测试组成 generate-and-check 验证回路，把 LLM 输出失败原因转化为下一轮修复输入。
3. 量化反馈循环如何缩小模型差异，并研究扰动多样性可能提升 pass@k 的条件。
4. 给出面向工业代码迁移的限制分析，包括数据规模、私有数据、长代码失败和 fuzzing 非证明性。

## 9 局限性

论文使用的样本较小，仅 50 个文件、76 个函数，且一部分内部汽车嵌入式数据不能公开，因此外推性有限（p.8）。超过约 1,000 tokens 的较长代码更容易失败；短函数结果不能代表大型真实模块（p.8）。

差分模糊测试未发现反例不能证明 C/Rust 形式等价；测试质量、API、内容策略和超时都会影响结果（pp.8–9）。系统平均反馈迭代约 2.1 次，且某些失败来自 fuzz harness 或接口问题而非翻译本身（p.9）。

论文没有训练或微调 LLM，也没有释放全部内部基准；因此不能直接推断换用模型、提示、编译器或更大代码规模后的表现。关于代码仓库，检索至 2026-09-23 未找到论文作者确认的公开实现：`Code_Status=NOT_FOUND`，`Code_URL=NOT_FOUND`，`Code_Checked_At=2026-09-23`。

## 10 阅读后的研究方向反思

从编译器角色看，论文把 Translator 输出与编译器验证器分离：LM 负责目标程序生成，编译器/Clippy/fuzzing 负责可执行性和行为反馈。这种边界适合研究“验证信号如何改变翻译候选分布”，但当前系统仍主要依赖错误反馈和随机重复，缺少对 Rust 类型、所有权和 ABI 约束的显式中间表示。

从证据强度看，编译成功、lint 通过和有限 fuzzing 是渐进式证据，不等同于语义保持。若要纳入更严格的编译器文献比较，应分别记录编译成功率、行为检查覆盖和超时/未检测状态，避免把 pass@k 当作正确性概率的无条件估计。

## 11 可进一步尝试的研究方向

1. 将 C AST、类型信息、控制流和 Rust ownership 约束编码为结构化中间表示，再让 LM 生成受约束的 Rust 候选。
2. 用编译器诊断类别、差分反例和覆盖率构造分层反馈，比较“只反馈错误文本”与“反馈可定位 IR 约束”的差异。
3. 将多候选翻译与验证预算联合优化，研究何时使用更多 feedback loop，何时改用扰动生成或模型切换。
4. 以可公开的大规模基准、真实跨模块依赖和形式/符号验证子集评估行为保持，而不只使用 fuzzing 未发现反例。
5. 报告成本维度：token、延迟、编译/fuzzing 时间、失败重试次数与成功率的 Pareto 前沿。

## 13 一页式总结

论文对象：一个把 C 翻译到 Rust 的自动化 Translator 系统。核心机制：LLM 生成 Rust，编译器/Clippy/差分 fuzzing 检查，失败后把反馈送回 LLM，最多 5 轮；另比较 GPT-3.5 Turbo、GPT-4o mini、Phi-4 与 51 类行为保持代码扰动。

主要事实：50 个 C 文件、76 个函数；GPT-4o mini 的编译成功率随反馈循环快速提升，第一轮收益最大；反馈循环缩小模型差距；扰动通常不显著损害结果，候选多样性在随机组合中最多带来约 9% pass@5 改进。主要证据限于小规模、部分私有数据和有限 fuzzing，不能证明形式等价。
