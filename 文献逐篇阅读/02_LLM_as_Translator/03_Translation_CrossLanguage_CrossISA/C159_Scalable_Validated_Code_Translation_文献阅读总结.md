## 1. 研究背景

代码翻译可用于软件现代化、多语言 SDK 维护以及迁移到更安全或更高性能的语言。论文关注 Go 到 Rust：Rust 的编译期内存安全和无运行时开销具有吸引力，但手工迁移耗时且易错。规则式/符号式翻译通常可由构造保证语义，但可能不够符合目标语言习惯；LLM 翻译更可能生成可维护、惯用的代码，却没有天然正确性保证。

引言指出，已有 LLM 翻译大多处理竞赛题、短代码片段或小型真实函数；代码超过约 100 行后成功率会明显下降。整项目放入上下文会遇到窗口限制和错误概率增长，即使把项目切成片段，类型不兼容、运行时崩溃和修复循环仍会阻碍语义验证。因此论文将 LLM 的生成能力与特定语言对的映射规则、编译检查及测试驱动的 I/O 等价检查结合起来。

## 2. 论文要解决的问题

### 2.1 项目规模问题

如何把不能整体放入上下文的真实 Go 项目拆成可独立翻译的片段，同时利用依赖关系和已翻译上下文继续完成项目级翻译。

### 2.2 语言特征映射问题

Go 与 Rust 的全局变量初始化、错误处理、接口/trait、可空类型和可见性等没有简单的一一语法映射。论文要降低“能编译但语义错误”与“不符合 Rust 约束”的情况。

### 2.3 可验证性与修复范围问题

仅以编译成功作为标准不足以确认 I/O 等价；全项目语义检查又容易因参数/返回类型不兼容而崩溃。论文要先进行局部类型兼容检查，再对函数执行样例做 I/O 等价检查，并把修复限制在当前片段。

> 本文主要研究：如何用模块化分区、特征映射、类型兼容检查和执行快照，让 LLM 能够生成可编译且在测试输入上 I/O 等价的 Go→Rust 整项目翻译。

## 3. 核心方法概述

论文实现 Oxidizer。它将项目切为函数/方法、类型定义和全局变量片段，按依赖图后序遍历翻译。LLM 负责直接生成 Rust 片段；静态规则检查、Rust 编译器和测试执行负责约束与反馈。

```text
Go 项目及其单元测试
        ↓
执行快照收集：记录函数输入、输出和副作用
        ↓
项目分区 + 依赖图 + 后序遍历
        ↓
类型驱动阶段：特征映射 → 编译/修复 → 类型兼容检查
        ↓
得到可编译、类型兼容的 Rust 项目（困难函数可 mock）
        ↓
语义驱动阶段：逐函数 I/O 等价测试，callee 使用 mock 隔离
        ↓
固定签名、重新生成函数体并修复；输出 Rust 翻译
```

特征映射规则不是让规则引擎完全生成代码，而是把目标语言特征和静态可检查结论放入提示词。例如 Go 的函数调用初始化全局变量映射到 `Lazy::new`，Go 错误返回映射到 `Result<..., anyhow::Error>`，Go interface 拆为共享方法子 trait 和主 trait。类型兼容检查使用两种语言的 JSON 序列化/反序列化，判断测试快照中的可行值能否跨语言往返。对无法编译但签名兼容的函数，Oxidizer 可生成调用原始 Go 函数的 mock，使后续片段仍可翻译；这不是等价实现，而是项目级继续处理机制。

## 4. 实验框架与训练流程

### 4.1 执行快照收集

论文不训练模型，主要采用推理时系统流程。Oxidizer 对 Go 函数插桩，运行源项目单元测试，记录输入、输出、输入状态变化和全局状态变化。没有收集到输入输出样例的函数会生成自动失败的空测试，因此不能被宣称为已验证等价。

### 4.2 类型驱动翻译

项目片段按依赖图后序处理。每个片段先应用特征映射并查询 LLM，再将已有翻译拼成 Rust 项目交给 Rust 编译器；失败时利用编译器错误重新查询当前片段。随后用执行快照检查类型定义、函数/方法签名的类型兼容性。达到重试上限但签名兼容时可以 mock；不兼容则终止该次项目翻译。

### 4.3 语义驱动翻译

对类型驱动阶段留下的每个片段，使用对应执行快照构造 Rust 单元测试。测试时 mock 被测函数的 callees，以将失败归因到当前函数；若 I/O 不等价，冻结签名，仅重新生成和编译函数体，直到成功或达到预算。该阶段的结果可能仍非 I/O 等价，论文没有将有限测试提升为形式化保证。

### 4.4 模型与工具调用

实验使用 Amazon Bedrock 提供的 Anthropic Claude 3 Sonnet。Oxidizer 的模块用 Python 实现，使用 `py-tree-sitter` 解析和插桩；论文还使用 Go/Rust 的 JSON marshaling、Rust 编译器和 Cargo 测试流程。LLM 输入输出被记录，支持离线 replay。论文没有 SFT、PPO、GRPO 或其他模型训练流程。

## 5. 奖励函数、损失函数或关键公式

本文没有使用强化学习，因此不存在强化学习奖励函数或训练损失。关键约束是类型兼容和 I/O 等价定义。

类型定义的兼容性可概括为：对源类型 `T` 的每个可行值 `v`，源序列化后能够被目标反序列化为 `Tr`，并且目标再序列化/源反序列化能够回到等价的 `v`。可行值来自单元测试执行快照，而不是所有理论上可能的值。

函数 I/O 等价可概括为：对快照中的输入 `i`，若 Go 函数成功，则 Rust 函数返回 `Ok` 且序列化输出（含副作用）一致；若 Go 函数失败，则 Rust 函数也返回 `Err`。这是一组测试输入上的判定，依赖测试覆盖率和确定性。

函数 mock 的论文定义为：`Mock(g) = D_Ur ∘ S_U ∘ f ∘ D_T ∘ S_Tr`，其中 `S`/`D` 是序列化/反序列化，`f` 是原始 Go 函数，`g` 是 Rust 签名。它用于继续翻译，不代表当前函数已被 Rust 重写。

## 6. 实验设置

### 6.1 数据集来源

作者从 GitHub 选择 8 个真实 Go 项目，标准是超过 100 个 stars 或最近 6 个月仍有提交，并且只使用 Go 标准库。项目包括 `geo`、`ach`、`go-edlib`、`stats`、`textrank`、`histogram`、`gonameparts`、`checkdigit`，覆盖球面几何、银行交易验证、字符串/编辑距离、统计、TextRank、直方图、姓名解析和校验码等用途。最大项目 `geo` 为 9,766 LoC、780 个函数/方法；表 1 报告的测试覆盖率从 43.2% 语句/61.9% 函数到 100% 不等。

### 6.2 模型与工具

使用 Claude 3 Sonnet（Amazon Bedrock），温度为 0.2。Oxidizer 参数为：特征映射重新查询预算 10，类型驱动阶段最大尝试 15，语义驱动阶段最大尝试 5。使用 `py-tree-sitter`、Go/Rust JSON 序列化、Rust 编译器和单元测试；论文未给出 Rust 编译器的具体版本。公开 artifact 位于 [Zenodo 15242640](https://zenodo.org/records/15242640)。

### 6.3 对比方法

主要对比是 Oxidizer 的完整流程与三个消融版本：关闭语义驱动阶段、关闭类型兼容检查、关闭特征映射。另与两个同期整项目 LLM 翻译工作报告的可运行率和 I/O 等价率进行间接比较；由于语言对不同，作者没有直接在相同基准上运行它们。

### 6.4 评价指标

| 指标 | 含义 | 方向 |
| --- | --- | --- |
| `% Compiled / Func.` | 可编译函数/方法占比 | 越大越好 |
| `% Compiled / LoC.` | 可编译代码行占比 | 越大越好 |
| `% Equiv. / Func.` | 在测试输入上 I/O 等价的函数/方法占比 | 越大越好 |
| `% Equiv. / LoC.` | 在测试输入上 I/O 等价代码行占比 | 越大越好 |

未覆盖的函数自动记为非等价；被 mock 的函数同时按编译失败和非等价处理，因此结果不是“翻译项目完整可运行”的比例。

## 7. 实验结果与结论

### 7.1 主要结果

完整 Oxidizer 在 8 个项目上的平均结果为 98% 函数可编译、97% LoC 可编译；平均 73% 函数和 67% LoC 在测试输入上通过 I/O 等价验证。单项目中，`go-edlib`、`stats`、`histogram`、`gonameparts`、`checkdigit` 的函数编译率为 100%；`geo` 为 94%，`ach` 为 96%，`textrank` 为 97%。

### 7.2 与传统方法的比较

论文没有与一个可直接运行的 Go→Rust 传统编译器在相同基准上比较。作者指出纯符号规则往往能保证语义但产生不惯用代码；Oxidizer 通过 LLM 生成目标代码、规则只约束语言特征，试图兼顾惯用性与验证性。

### 7.3 与其他 LLM 方法的比较

与同期整项目翻译工作相比，相关工作报告的可运行率约为 99%/100%，Oxidizer 的 98% 相近；但相关工作平均只验证 26% 的函数（在有测试覆盖函数中为 46%），且语义验证约 25% 会崩溃，Oxidizer 平均验证 73% 函数。该比较是跨语言、跨基准的报告值，不是严格控制实验。

### 7.4 消融实验

关闭类型检查后，7 个可比较基准中 5 个的函数等价率下降，通常下降 5–35%，有一个基准下降 144%。关闭特征映射后，Algorithm 2 在所有基准上中止；表中只报告中止前成功编译的部分，等价率为 0。关闭语义驱动阶段时，5/8 个项目没有修复任何非等价函数；其余项目修复 `geo` 15 个、`ach` 4 个、`textrank` 1 个成功案例，成功修复平均需要 2.65 次查询。

### 7.5 案例分析

论文展示了 Go 可空切片到 Rust `Option<Vec<i32>>`、全局惰性初始化、Go error 到 Rust `Result`、Go structural interface 到 Rust trait 组合等映射。还展示了 Go 的借用模式可能无法直接满足 Rust borrow checker；这类函数在 `ach` 的不可编译函数中占 53%。

## 8. 主要创新点

### 8.1 创新点一：LLM 与特征映射规则的混合翻译

规则不完全取代 LLM，而是告诉 LLM 对语言差异采用何种目标特征，并用静态符号检查确认结果遵守规则。实验中去掉映射会使类型驱动翻译在所有基准中止，支持其对可靠性的贡献。

### 8.2 创新点二：以执行快照为基础的类型兼容

类型兼容不是要求 Go/Rust 类型名称或表示完全相同，而是要求测试中可行值能够跨语言序列化往返，并将检查局部化到类型定义和函数签名。它既能及早发现参数顺序/可空性错误，也为函数 mock 提供前提。

### 8.3 创新点三：类型驱动与语义驱动两阶段项目翻译

先获得可编译、类型兼容的项目，再逐函数验证 I/O 等价，并冻结签名修复函数体。该结构使错误定位和修复范围更小；但其语义结论仍局限于测试快照，不是形式化证明。

## 9. 局限性

### 9.1 论文明确承认的局限

- 实验只覆盖 Go→Rust，且选择只使用标准库的项目；外部库映射虽有讨论，但没有在主评测中系统验证。
- I/O 等价依赖源项目测试覆盖率；未覆盖函数自动标记非等价。
- 随机行为（如随机排列）即便翻译正确，也可能无法通过确定性等价验证。
- 某些违反 Rust 借用规则的 Go 习惯需要改变语法结构，LLM 仍容易失败。
- mock 能让项目继续翻译，但表示该函数没有得到 Rust 实现，且会计入失败/非等价。

### 9.2 阅读后发现的潜在局限

- 类型兼容只在测试产生的可行值集合上成立，不能推出所有输入的跨语言语义保持。
- 编译成功和测试通过仍可能遗漏未覆盖路径、并发行为和资源语义；论文没有给出形式化证明。
- LLM 查询预算、Claude 3 Sonnet、温度和语言特征规则会影响复现，论文未报告不同模型/预算的系统敏感性。
- 迁移到 C/C++ 或含 unsafe 指针、宏和复杂并发的项目时，需要额外程序分析，不能只替换源语言名称。

## 10. 阅读后的研究方向反思

最值得借鉴的是把“目标语言结构约束”和“模型自由生成”分开：规则负责可检查的不变量，LLM 负责惯用实现；同时把类型兼容作为语义验证前置门。对 RISC-V 研究而言，本文不是 ISA 翻译论文，不能简单把 Rust 替换成 RISC-V 汇编就声称获得同等贡献。若目标是跨 ISA，必须重新定义寄存器/内存/调用约定和可观测副作用，并提供目标 ISA 的编译、模拟或真实硬件证据。

本文更适合作为 T3 的项目级源码翻译基线、类型边界检查模块和测试驱动验证框架参考，而不是直接复用的训练方法；它没有模型训练或 RISC-V 实验。

## 11. 可进一步尝试的研究方向

### 11.1 面向 RISC-V ABI 的跨语言源码到低层代码翻译

#### 研究问题

如何把源语言函数翻译到带 RISC-V ABI 约束的 C/LLVM IR/汇编，并同时检查参数、返回值、内存副作用和调用约定兼容性。

#### 与原论文的区别

目标不再是 Go→Rust 高层源码，而是跨语言到 RISC-V 低层表示；类型兼容需要加入 ABI 和内存布局约束。

#### 可能的创新点

构造“源类型—IR 类型—RISC-V ABI 值”的分层兼容检查，并把真实硬件/模拟器反馈加入验证闭环。

#### 实验框架

```text
源项目 → 依赖分区 → LLM 生成 C/LLVM IR → LLVM/RISC-V 编译 → ABI/语义测试 → 局部修复
```

#### 可行性

需要 LLVM、RISC-V 交叉编译器、QEMU 或真实 RISC-V 板卡、可序列化测试输入和小型项目。

#### 主要风险

未定义行为、指针别名、并发和硬件差异可能让有限测试无法支撑等价结论。

### 11.2 规则可学习但可审计的跨语言特征映射

#### 研究问题

能否从已验证翻译中归纳新的 Go/C++→Rust 或 C→RISC-V 映射规则，同时保留静态检查条件。

#### 与原论文的区别

原论文使用预定义规则；该方向研究规则发现与规则正确性审计，而不是只增加提示词。

#### 可能的创新点

把每条映射绑定到可执行的结构检查、反例和适用前提，形成可复用的跨语言映射库。

#### 实验框架

```text
已验证翻译对 → 候选规则归纳 → 结构/类型检查 → 反例搜索 → 新项目翻译评测
```

#### 可行性

可从本文 8 个项目和公开 artifact 起步，结合 tree-sitter、编译器诊断和差分测试。

#### 主要风险

归纳规则可能过拟合项目风格，且规则之间可能冲突或扩大 LLM 修复成本。

### 11.3 面向未覆盖路径的跨语言验证扩展

#### 研究问题

如何减少“未被单元测试覆盖就判非等价”的偏差，并在不宣称形式化证明的前提下扩大可验证输入集合。

#### 与原论文的区别

原论文主要使用测试执行快照；该方向加入符号执行、模糊测试或约束生成来产生新的跨语言输入。

#### 可能的创新点

以类型兼容检查过滤不可跨语言表示的输入，再针对剩余边界生成差分测试，减少无效崩溃。

#### 实验框架

```text
源测试快照 → 类型兼容过滤 → 边界/路径输入生成 → Go/Rust 或 IR 差分执行 → 失败归因与修复
```

#### 可行性

需要可控的源语言测试、目标编译器、序列化协议和差分执行环境。

#### 主要风险

生成输入可能触发未定义行为或非确定性；更强验证也会显著增加执行成本。

## 12. 与其他已读文献的关系
