## 1. 研究背景

稀疏矩阵和张量代码的性能依赖数据格式与操作结构。通用 C/C++ 程序往往难以被编译器识别为可替换的库调用；已有 API 匹配系统通常只覆盖少量模式（如 SpMV，稀疏矩阵向量乘法），而不同库对格式、类型和参数有不同要求。论文研究如何把遗留稀疏代数代码提升为库或张量 DSL 调用，同时保留行为并利用目标平台。

SLEB 结合 LLM 的模式识别、程序分析和类型约束搜索。LLM 只提供结构线索，后续工具构造和检查候选，不直接信任模型输出。

## 2. 论文要解决的问题

### 2.1 运算与格式识别

从 C/C++ 函数识别稀疏操作、输入输出张量以及 CSR、CSC、COO、JDS 等格式。局部语法模板容易受代码结构影响。

### 2.2 映射到多种目标 API

同一操作可对应 MKL、cuSPARSE 或 TACO 中不同接口、类型和参数。系统需生成调用草图并绑定对象和维度。

### 2.3 控制搜索并检查行为

候选接口及参数绑定很多。静态分析与类型规则缩小搜索空间，I/O 样例比较则排除明显错误候选。

> 本文主要研究：如何提取遗留稀疏代数代码中的操作与格式线索，并以类型约束综合完成库/API 或 TACO 提升。

## 3. 核心方法概述

SLEB 分析 AST、函数调用、变量和类型；LLM 识别操作、格式和维数等信息。分析器构造带空位的 API 草图，类型约束和枚举搜索选择具体参数绑定。TACO 路径从其语法枚举表达式。最后以多组输入输出样例比较原程序和候选程序。

流程：遗留 C/C++ → AST 与变量/调用分析 → LLM 预测操作和稀疏格式 → 构造库 API/TACO 草图 → 类型约束枚举参数 → 编译并作 I/O 比较 → 输出候选。

LLM 不负责最终参数搜索，也不提供完整语义证明；程序构造由分析器与综合器完成。

## 4. 实验框架与训练流程

### 4.1 草图预测

论文使用 GPT-4o 识别稀疏操作、格式和张量维数，输出用于确定后续搜索空间；正文没有报告微调。

### 4.2 程序分析与综合

静态分析收集函数参数、体内变量和调用信息。系统构造数据 API 或操作 API 草图，以类型及对象一致性限制参数绑定；TACO 目标通过受限语法枚举。综合器尝试绑定，直至满足约束或搜索耗尽。

### 4.3 测试与性能评估

论文用 10 组 I/O 测试输入比较原程序和提升程序输出。性能实验对原程序和提升版分别运行 10 次取平均，再计算可提升基准的几何平均。本文不涉及模型训练、SFT 或强化学习。

## 5. 奖励函数、损失函数或关键公式

本文没有强化学习奖励函数或神经网络损失函数。综合过程要求满足语法、类型和对象绑定约束，并使有限 I/O 样例输出与原程序相符。

I/O 测试不是形式化等价证明，不能保证所有输入上的等价。论文把引入外部验证器列为未来可能方向。

## 6. 实验设置

### 6.1 数据集来源

实验包括 31 个程序基准和 14 个真实稀疏数据集。矩阵数据包括 bcsstk17、pdb1HYS、rma10、cant、consph、cop20k、shipsec1、scircuit、mac-econ、pwtk、webbase-1M；张量数据包括 Facebook、NELL-2、NELL-1。第 4 节、表 1 列出维度与非零元数。它们不是训练集，论文未报告训练/验证/测试划分。

### 6.2 模型与工具

| 项目 | 论文设置 |
|---|---|
| 语言模型 | GPT-4o |
| 编译与运行 | Python 3.10、Clang/LLVM 18.0、Ubuntu 22.04.5 |
| CPU | Intel MKL 2025.1.16；AMD Ryzen Threadripper 7970X，64 核，125 GB DDR5 |
| GPU | NVIDIA cuSPARSE 12；GeForce GTX 1080 Ti，CUDA 12.4 |
| DSL | TACO 0.1 |
| 对比方法 | LiLAC、SpEQ、GPT-4o 直接生成；原始实现作速度基线 |

### 6.3 对比方法

LiLAC、SpEQ 是稀疏代码到库调用的既有方案，主要覆盖 SpMV；GPT-4o 直接生成用于比较纯模型生成效果。速度基线是原始实现。

### 6.4 评价指标

论文报告可提升程序比例、成功率、I/O 测试结果和加速比。每项程序运行 10 次取平均，再按可提升项目汇总。加速比不等于正确率，测试通过也不等于形式化正确。

## 7. 实验结果与结论

### 7.1 主要结果

摘要报告 SLEB 可提升 94% 的程序，高于 LiLAC 11%、SpEQ 17%、GPT-4o 48%。CPU 几何平均加速约 2.6 倍。GPU 摘要约 7.2 倍；正文图 7 对稀疏矩阵基准报告约 7.8 倍，二者汇总口径有差异，引用时需注明。

### 7.2 比较与失败案例

SLEB 涵盖矩阵、张量、多种格式和多个目标库；LiLAC、SpEQ 主要面向 SpMV。SLEB 把 GPT-4o 限定为结构预测器，由分析与搜索工具构造程序。系统未提升 Ginkgo 的 SpMV（相关值为常量结构）及 Splatt 的 MTTKRP（TACO 表达式搜索过于复杂）。

### 7.3 消融和速度分析

论文以系统级 baseline 比较评估流程，没有逐一移除类型约束、静态分析或提示组件的完整消融表。正文图中 GPU 的 SDDMM 峰值约 27.6 倍，是特定基准结果而非几何平均。有限样例测试只检查给定输入。

## 8. 主要创新点

### 8.1 稀疏结构识别接入多目标综合

相对于只匹配单一 API 模式的系统，SLEB 将 LLM 的运算/格式预测接入静态分析和类型约束综合，并支持多个库与 DSL。基准覆盖率支持其实用性。

### 8.2 以草图和类型缩小参数搜索

模型不直接产生最终翻译；系统利用草图、对象关系、类型和格式约束，把搜索限制在可行参数绑定中。

## 9. 局限性

### 论文呈现的边界

- 系统面向稀疏代数与论文支持的操作/API，不是通用 C 翻译器。
- 固定 10 组 I/O 样例不能证明全输入等价；存在 Ginkgo 与 Splatt 失败案例。
- 作者指出 LLM 推理成本较高，并将专用小模型列为未来方向。
- TACO 对部分稀疏输出的 CUDA 生成不稳定，限制 GPU 评测范围。

### 阅读后发现的潜在局限

格式推断错误会引导错误搜索空间；有限测试可能漏掉边界行为；跨库版本、编译器和硬件的扩展成本未被完整量化。特定 CPU/GPU 上的速度结果不能直接外推到 RISC-V。

## 10. 阅读后的研究方向反思

可借鉴让 LLM 提供结构候选、让综合器处理约束搜索的职责分离，以及用类型信息剪枝。直接替换库或架构并不足以形成新贡献。与 RISC-V 联系间接，可研究稀疏库 API 在 RVV 后端的选择与合法性，但应引入具体后端约束、向量长度/布局和真实硬件评测。

## 11. 可进一步尝试的研究方向

### 11.1 面向 RISC-V 向量库的可验证稀疏提升

#### 研究问题

如何在源程序、稀疏格式和 RVV 可用库调用之间生成适配具体硬件的程序。

#### 与原论文的区别

增加 RVV 向量长度、布局和后端限制，并使用更强等价性或差分测试；不只是替换库名称。

#### 可能的创新点

硬件条件化候选排序、格式推断置信度传播、可解释类型约束剪枝。

#### 实验框架

C 稀疏代码 → 格式假设 → RVV API/循环候选 → 编译和等价测试 → 模拟器/真实板卡测量。

#### 可行性

需要 LLVM/Clang RVV 工具链、稀疏基准和 RISC-V 硬件或模拟器。

#### 主要风险

库覆盖、硬件数量和测试覆盖不足会限制结论。

### 11.2 以验证失败驱动草图精化

#### 研究问题

类型或测试失败后，能否把诊断反馈给模型并只重新搜索相关草图部分。

#### 与原论文的区别

将一次预测改为可追踪的局部修正过程，并测量调用和搜索成本。

#### 可能的创新点

置信度校准、失败到草图槽位映射、增量测试。

#### 实验框架

草图预测 → 参数综合 → 测试/编译 → 诊断归因 → 局部修正 → 回归测试。

#### 可行性

可基于已有候选综合和测试循环实现，需建立错误标签与基线。

#### 主要风险

测试失败未必能定位唯一草图错误；迭代修正可能过拟合样例。

## 12. 与其他已读文献的关系

本批次 C2HLSC 也让 LLM 参与转换并使用工具反馈，但将一般 C 改为 HLS 可综合代码；SLEB 让模型识别稀疏结构，再由综合器生成 API/DSL 表达式。已有 Guided Tensor Lifting（C28）也结合 LLM 候选与综合搜索，但研究稠密张量到 TACO，并用概率文法和有界验证；SLEB 的差异在稀疏格式、库 API 和多硬件目标。C28 可作程序提升与搜索的对照基线。
