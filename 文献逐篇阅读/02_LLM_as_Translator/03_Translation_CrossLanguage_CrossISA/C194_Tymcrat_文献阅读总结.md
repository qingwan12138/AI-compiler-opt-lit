# Tymcrat 文献阅读总结

论文题目：**Type-migrating C-to-Rust translation using a large language model**  
作者：Jaemin Hong；Sukyoung Ryu  
发表时间：2024 年在线发表；期刊卷标为 2025  
发表平台：Empirical Software Engineering 30(3), Article 3  
论文链接或编号：[DOI 10.1007/s10664-024-10573-2](https://doi.org/10.1007/s10664-024-10573-2)  
关键词：C-to-Rust 翻译、类型迁移、LLM、编译器反馈、函数调用图

## 1. 研究背景

论文关注将遗留 C 系统程序迁移到 Rust。C 的指针和隐式类型转换有利于表达底层程序，但也难以提供 Rust 类型系统所期待的安全约束。C-to-Rust 不是简单改写语法：同一个 C 类型可能依据函数语义映射到多个 Rust 类型，函数签名改变后，调用者和函数体也要同步重构。

传统 C2Rust、Laertes、Crown、Concrat 等方法主要通过规则和静态分析处理少数特定类型。论文指出 Rust 有六百多种类型，而真实项目签名中至少会使用上百种类型，为每种类型编写专门分析规则成本很高。LLM 具有代码语义和语言习惯知识，因此被用于提出候选 Rust 签名并生成函数体；Rust 编译器负责类型检查和反馈。

## 2. 论文要解决的问题

### 2.1 类型迁移问题

如何从同一个 C 函数的语义出发，生成一个或多个符合 Rust 习惯的函数签名，而不是机械地保留 C 指针和 C ABI 类型。

### 2.2 跨函数重构问题

一个函数调用的被调用者签名发生变化后，调用者必须改变参数构造、返回值处理和控制流。单独翻译每个函数时，LLM 缺少这些上下文。

### 2.3 类型错误修复问题

LLM 生成的 Rust 代码常有类型错误。论文研究如何结合 Rust 编译器的自动修复建议与 LLM 对无建议错误的修复，降低错误数量。

> 本文主要研究：如何借助 LLM、调用图上下文和 Rust 编译器反馈，实现带函数签名类型迁移的 C-to-Rust 翻译。

## 3. 核心方法概述

Tymcrat 先构造 C 程序的语法调用图，从叶函数向调用者翻译。每个函数依次经历候选签名生成、带被调用者签名的翻译、编译器反馈修复和最佳实现选择。最终输出 Rust 函数及其签名，并把签名提供给上层调用者。

```text
C 程序
  ↓
构造调用图，按叶到根排序
  ↓
LLM 生成多个候选 Rust 签名
  ↓
把已翻译的被调用者签名加入上下文，生成多个 Rust 函数
  ↓
Rust 编译器类型检查
  ├─ 有 compiler suggestion：直接应用建议
  └─ 无 suggestion：把错误和代码交给 LLM 修复
  ↓
按类型错误数量选择；并列时让 LLM 选择更符合 Rust 习惯的实现
  ↓
记录签名，供调用者翻译
```

LLM 直接输出 Rust 源码，因此最终角色是 TRANSLATOR，而不是只选择编译动作的 Selector。实现依赖 Rust 编译器内部诊断数据结构，不涉及强化学习或形式化验证。

## 4. 实验框架与训练流程

本文不涉及模型训练，主要采用 API 推理和编译器反馈。

### 4.1 调用图与候选签名

通过函数名识别调用关系，先翻译叶节点。LLM 为每个函数生成 0、1、2、3 或 4 个候选签名；候选签名本身先进行类型检查，有错误的签名会被丢弃。

### 4.2 带被调用者签名的翻译

生成函数体时，把已经翻译的被调用者 Rust 签名和相关类型定义、全局变量翻译结果一并加入提示。互递归时先任意选择一个函数翻译，再回访该函数以补充其余签名。

### 4.3 编译反馈修复与选择

对于 Rust 编译器带修复建议的错误，Tymcrat 自动应用建议并重新检查；没有建议的错误则交给 LLM。若修复后错误数量没有下降，停止并丢弃该修复。多个候选中先按类型错误最少选择；错误数相同时，使用 LLM 比较 Rust 习惯性。

实验中函数超过 3,000 tokens 不翻译，以保持两个模型配置公平。不同叶函数和不同候选可并行执行。

## 5. 奖励函数、损失函数或关键公式

本文没有使用强化学习，因此不存在强化学习奖励函数，也没有训练损失函数。

主要搜索/选择目标是：

```text
优先选择 type_error_count 最少的 Rust 翻译
若并列，则选择更符合 Rust idiom 的实现
```

这个目标是工程启发式，不等价于语义等价证明。论文还以 Rust 类型错误数量、迁移类型数量和完整迁移签名比例作为实验指标。

## 6. 实验设置

### 6.1 数据集来源

作者从 GNU Package Blurbs 收集 41 个 C GNU 包。初始收集 88 个包，过滤掉超过 100,000 LOC 或不能编译的包，再选择在 Wikipedia 有独立条目的 41 个知名包。表 1 给出每个包的 LOC、类型、全局变量、函数、调用边和因超过 3,000 tokens 而省略的函数。最大包为 glpk，59,030 LOC；最小包 time-1.9，796 LOC。

这不是训练数据集，而是翻译评测集合。论文没有报告训练/验证集划分，也没有消除模型预训练语料潜在泄漏的办法。

### 6.2 模型与工具

- GPT-3.5 Turbo：`gpt-3.5-turbo-0125`。
- GPT-4o mini：`gpt-4o-mini-2024-07-18`。
- 温度设为 0；通过 OpenAI API 调用。
- Rust 编译器：论文使用其内部诊断数据结构，但未在正文明确给出具体 rustc 版本。
- 通过 Rust `todo!()` 临时替换已翻译被调用者函数体，以隔离调用者的类型检查。

### 6.3 对比方法

C2Rust、Laertes、Crown、Concrat。它们代表基于语法规则、静态分析或特定类型转换的传统/混合 C-to-Rust 方法。Tymcrat 的主要内部 baseline 是不生成候选签名的 `Tymcrat_0`。

### 6.4 评价指标

| 指标 | 含义 | 趋势 |
|---|---|---|
| Rust types | 输出签名中引入的 Rust 类型出现次数 | 越多不一定越好 |
| Fully migrated signatures | 签名不再含 C 类型，只含 common/Rust 类型 | 越高越好 |
| Type errors | 翻译程序的类型错误数 | 越低越好 |
| Functions without type errors | 无自身类型错误的函数比例/数量 | 越高越好 |
| Idiomatic type case study | 人工判断类型是否符合 Rust 习惯 | 越高越好 |
| Translation time/token/cost | 翻译开销 | 越低越好 |

## 7. 实验结果与结论

### 7.1 主要结果

在 GNU 包集合上，GPT-3.5 Turbo 中 `Tymcrat_4` 相比 `Tymcrat_0` 引入的 Rust 类型数量增加 63.5%，完整迁移签名从 70.7% 提升到 79.9%，未迁移签名减少 84.7%。GPT-4o mini 的基线更强：`Tymcrat_0` 完整迁移签名为 87.1%，`Tymcrat_4` 为 85.6%，但未迁移签名进一步从 3.0% 降至 1.4%。

### 7.2 类型质量

GPT-3.5 Turbo 下，生成四个候选签名使不同 Rust 类型数从 41 增加到 73，增幅 78.0%；GPT-4o mini 下从 57 增至 69，增幅 21.1%。对 300 个函数的人工案例分析中，作者按较保守标准判断，GPT-3.5 Turbo 有 56.1% 函数正确，GPT-4o mini 有 78.0% 函数正确；这只是抽样人工分析，不是全程序语义正确率。

### 7.3 类型错误与传统方法

组合使用被调用者签名增强和错误修复时，GPT-4o mini 的 `Tymcrat_4` 类型错误相比禁用两者的设置减少 71.5%，但每个程序平均仍有 1,155.3 个类型错误，只有 55.9% 函数无类型错误。与 C2Rust、Laertes、Crown、Concrat 相比，Tymcrat 迁移更多 Rust 类型；相反，Laertes 和 Crown 几乎不引入类型错误并保持语义，说明“类型迁移更多”不等于“翻译更正确”。

### 7.4 消融与开销

候选签名数量增加通常减少错误，但带来成本。GPT-3.5 Turbo 中从 0 到 4 个候选使翻译时间增加 98.8%；迭代修复在相应设置下增加 115.6%。GPT-4o mini 中候选签名使时间增加 68.5%，错误修复使时间增加 194.9%。最贵的 GPT-3.5 Turbo `Tymcrat_4` 平均成本为 10.76 美元。并行化缓解了时间，但不能消除 token 和 API 成本。

## 8. 主要创新点

### 8.1 LLM 生成多候选类型签名

论文不是让 LLM 一次猜一个签名，而是显式生成多个 Rust 签名，再分别翻译。实验表明这能增加 Rust 类型和完整迁移签名，尤其对 GPT-3.5 Turbo 有效。

### 8.2 调用图顺序与被调用者签名增强

从叶到根翻译，把已翻译被调用者签名提供给调用者，使 LLM 能重构参数和返回值。这是面向跨函数依赖的上下文组织机制，而不是普通的代码补全。

### 8.3 编译器建议与 LLM 修复的分工

确定性的 compiler suggestion 先自动应用，剩余错误再由 LLM 处理。论文用实验显示这种组合减少类型错误，但没有证明输出语义等价。

## 9. 局限性

### 论文明确承认的局限

- 超过 3,000 tokens 的函数被排除，可能低估大型函数的困难。
- GNU 包和 Wikipedia 筛选限制了外部有效性。
- 类型多样性不是充分的质量指标；人工案例覆盖有限。
- 少量类型错误不代表语义正确，论文明确观察到无类型错误但语义错误的函数。
- 没有完整程序级测试，因为程序常不能编译且缺少函数级测试。
- LLM 即使温度为 0 仍可能非确定；并行计时也受调度影响。

### 阅读后的潜在局限

Tymcrat 的“错误数量下降”目标可能偏向局部可编译性，无法处理跨模块 ABI、宏、未建模环境和运行时不变量。它没有 LLVM IR、RISC-V 或真实硬件性能实验，不能直接推断对其他 ISA 的性能收益。

## 10. 阅读后的研究方向反思

值得借鉴的是“调用图依赖排序—候选生成—编译反馈—选择”的流水线，以及把确定性编译器修复和生成式修复分层。不能简单把 Rust 换成 RISC-V 就称为新贡献；若迁移到 RISC-V，更有价值的问题应是 LLVM IR/ISA 语义、ABI 约束和跨架构等价验证。

对本仓库而言，Tymcrat 最适合作为 TRANSLATOR/T3 的跨语言翻译 baseline，也可作为 compiler-feedback repair 模块参考，而不是 Selector 或 Generator。

## 11. 可进一步尝试的研究方向

### 11.1 面向 LLVM IR 的跨 ISA 类型与 ABI 翻译

#### 研究问题

如何把 C/C++ 或 LLVM IR 迁移到 RISC-V 时，同时处理数据布局、调用约定和向量类型。

#### 与原论文的区别

从 Rust 类型迁移扩展到 IR/ISA 语义和 ABI，不只是替换目标语言。

#### 可能的创新点

让候选生成受 LLVM 类型约束和 RISC-V ABI 约束共同限制。

#### 实验框架

```text
源程序/LLVM IR → LLM 生成候选 → clang/LLVM 验证 → RISC-V 编译运行 → 反例修复
```

#### 可行性

需要 LLVM、riscv-gnu-toolchain、QEMU 或真实 RISC-V 板卡及小规模可编译基准。

#### 主要风险

模拟器通过不等于真实硬件性能，且语义差异可能需要人工 oracle。

### 11.2 类型错误与语义反例联合修复

#### 研究问题

如何避免模型只减少编译错误，却改变原程序行为。

#### 与原论文的区别

把 Tymcrat 的编译反馈扩展为测试反例、差分执行或符号约束。

#### 可能的创新点

按错误类型动态选择修复上下文，并将语义反例作为第二类反馈。

#### 实验框架

```text
候选翻译 → 编译器诊断修复 → 差分测试/符号检查 → 反例回灌 → 终止或选择
```

#### 可行性

可在 GNU 小包和 CodeNet 子集上实现；需要控制 API 成本。

#### 主要风险

测试覆盖不足会把错误翻译误判为正确。

## 12. 与其他已读文献的关系

本批次中 Tymcrat 与 SafeTrans 都是 C-to-Rust Translator，但 Tymcrat 聚焦函数签名类型迁移、调用图和 Rust 类型错误；SafeTrans 聚焦端到端程序翻译、运行时验证和安全漏洞缓解。WaDec 是 Wasm 二进制到 C 的低层恢复，Auto-repair 是工业 CI 编译错误修复，输入输出层级不同。Tymcrat 适合作为跨语言类型迁移 baseline；SafeTrans 适合作为带测试和安全分析的系统级对照。
