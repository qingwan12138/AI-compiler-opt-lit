## 1. 研究背景

大型 HPC 应用一次完整构建和运行可能耗时数分钟至数小时，不适合每个 LLM 候选都在整套工程里验证。热点 kernel 又常依赖复杂上下文，不能简单独立复制后运行。

## 2. 论文要解决的问题

如何自动补齐热点 kernel 的依赖、输入和调用，形成低成本但能预测集成性能的最小可执行程序（MEP），并在其中迭代优化后再回填原应用。

## 3. 核心方法概述

系统先构造 MEP 和满足时长/数据规模约束的输入生成器；每轮由 LLM 结合 profiler 生成多个候选，编译/运行/功能等价失败时自动修复，并把成功的 tiling、访存、同步模式继承给后续轮次。

## 4. 实验框架与训练流程

```text
热点 kernel → LLM 补全 MEP → 功能等价基线
 → 多候选生成 → 编译/运行/性能测量 → AER 修复
 → 继承有效模式 → 迭代 → 回填完整应用验证
```

推理使用 OpenAI o3，无模型训练或 RL。

## 5. 奖励函数、损失函数或关键公式

```text
Speedup = t_baseline / t_optimized
```

只统计通过功能等价验证的候选。每个候选运行 30 次，去掉最高/最低各 3 次后求均值；停止条件为达到轮数上限或提升低于阈值。

## 6. 实验设置

### 6.1 数据集来源

20 个 PolyBench GPU kernel、12 个 AMD APP SDK 程序，以及 LAMMPS、MISA-MD、xblue 三个大型 HPC 应用热点。

### 6.2 模型与工具

OpenAI o3；NVIDIA RTX 2080 Ti/CUDA 11.5/Ubuntu 22.04，以及海光 DCU/HIP 24.04/CentOS 7。

### 6.3 对比方法

直接使用 o3 一次优化作为基线；比较 MEP 单独测量与回填后的集成性能。PolyBench 用 6 轮×3 候选，其余用 10 轮×5 候选。

### 6.4 评价指标

MEP 独立加速、完整应用集成加速、直接 LLM 加速，以及功能等价通过。

## 7. 实验结果与结论

PolyBench 在 NVIDIA/海光 DCU 的平均集成加速分别为 5.05×/7.77×，直接 LLM 为 2.10×/2.28×。AMD APP SDK 平均集成 1.77×，直接 LLM 1.13×；三个真实 HPC 热点平均 1.25×，直接 LLM 接近 1.0×。独立 MEP 与回填结果总体接近，未出现 MEP 预计提升但集成明显退化的案例。

## 8. 主要创新点

### 8.1 MEP 代理完整应用反馈

把高成本整工程验证降成 kernel 级快速循环。

### 8.2 诊断修复贯穿构建与优化

补全阶段和优化阶段共用编译/运行/输出异常反馈。

### 8.3 性能模式继承

把有效 tiling、访存和同步策略压缩为后续轮次约束，减少重复探索。

## 9. 局限性

MEP 与原应用仍存在编译器、运行时和数据流差异，作者也承认个别性能有较大偏差。功能等价依赖生成输入，不能覆盖所有边界；仅测试 o3 和两类 GPU 平台，真实应用只有三个热点。

## 10. 阅读后的研究方向反思

这项工作的可复用核心是“构造低成本、可校准的性能代理环境”。面向毕业论文，可把 MEP 扩展为多架构微基准，并研究代理排序何时失真，这比简单增加 Agent 更扎实。

## 11. 可进一步尝试的研究方向

### 11.1 可校准的跨架构 MEP

#### 研究问题

MEP 在 x86、GPU、RISC-V 上的候选排序与完整应用排序能否预测并校准。

#### 与原论文的区别

增加代理误差建模和不确定时回退完整构建的机制。

#### 可能的创新点

以排序置信度动态决定 MEP 或全应用测量。

#### 实验框架

```text
热点 → MEP 多架构测量 → 排序置信度 → 少量全应用校准 → 搜索更新
```

#### 可行性与风险

K3 可用于 CPU kernel；复杂 GPU kernel 无法直接迁移到 RISC-V。

## 12. 与其他已读文献的关系

与 N07 SBLLM 同为执行反馈搜索，但本论文重点解决“大工程无法廉价运行”。与 N13 NPUEval 一样强调真实硬件；与 N05 的效率判别器可组合成 MEP 前的廉价候选筛选。
