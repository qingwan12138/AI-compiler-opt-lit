## 1. 研究背景

编译器优化 pass 的排列组合空间巨大、交互关系不规则。固定使用 `-O2/-O3` 可能错过特定程序和硬件上的优化机会；搜索算法需要为每个新程序重复探索，监督学习又需要昂贵且稀疏的高质量训练数据。强化学习可以把完整序列选择拆成逐 pass 决策，并从环境反馈中持续学习，但仍面临超参数选择、冷启动、观测信息不足和真实性能噪声问题。

DeCOS 研究一种数据高效的 RL 编译优化框架，重点解决 LLVM 优化序列选择中的启动成本、动态硬件信息和跨程序/跨硬件迁移问题。

## 2. 论文要解决的问题

### 2.1 高维优化序列的逐步搜索

给定 C 程序和其 LLVM IR，系统需要在每一步选择一个优化选项，逐步构造最多 16 个 pass 的序列。

### 2.2 RL 的数据效率与冷启动

实际编译、运行和性能计数器采集代价高，随机探索启动慢。论文使用合成数据调超参数和奖励函数，并用 GPT-4o-mini 为初期探索提供优化建议。

### 2.3 动态硬件与噪声

静态代码特征不足以描述不同硬件上的运行状态。DeCOS 将 CPU cycles、指令数、缓存/分支 miss、已用 pass 和最耗时指令等动态信息加入观测，并用 Cachegrind 模拟结果辅助减小真实 profiling 噪声。

> 本文主要研究：如何将 LLVM IR 静态表示、运行时性能反馈、LLM 初始建议和 RL 在线学习组合为数据高效的编译优化序列选择器。

## 3. 核心方法概述

DeCOS 以函数为粒度抽取热点 LLVM IR，用 IR2vec 生成静态 embedding，再把动态硬件性能信息和已执行 pass 拼成观测。RL agent 每次预测一个优化选项，Clang `opt` 生成新 IR，随后编译并 profiling 或模拟；reward 用于更新策略。LLM 只在初始探索和部分策略反馈中提供建议，不对 LLM 权重做微调。

```text
C/C++ 程序
    ↓ Clang 编译、llvm-extract
热点函数 LLVM IR + IR2vec embedding
    ↓ 加入性能计数器、已执行 pass、耗时指令
RL agent 选择一个优化 pass
    ↓ Clang opt 变换 LLVM IR
编译为 binary → perf/Cachegrind
    ↓ reward 与下一状态观测
继续构造最多 16 个 pass 的序列并在线更新策略
```

## 4. 实验框架与训练流程

### 4.1 合成数据和超参数阶段

论文从 MiBench 小程序随机收集编译器—benchmark 交互，再提取统计特征生成合成数据，用于选择神经网络规模、学习率和奖励函数。合成数据不直接训练最终 RL 模型，而是降低真实数据采集成本。

### 4.2 LLM 冷启动阶段

DeCOS 使用 GPT-4o-mini 分析目标函数并建议可能的优化集合，RL agent 以这些结果替代部分随机初始探索。论文还描述了 LLM 可分析 RL 选择的选项并建议改进，但没有 SFT、PPO/GRPO 式 LLM 微调或 LLM 参数更新。

### 4.3 在线 RL 阶段

内层循环每次追加一个优化选项，长度达到 16 后从原始 IR 重新开始；完成三个 16-option 序列后更新一次 RL 策略，三个内层序列组成一个训练 epoch。Cachegrind 提供中间模拟反馈，完整序列仍用真实 profiling 结果评估最终性能。

## 5. 奖励函数、损失函数或关键公式

对单个 pass `P_k`，论文选择的局部奖励是该 pass 前后 CPU cycles 的差值；完整序列结束后再加入基于总优化结果的额外奖励。论文正文没有给出一个统一的完整数学公式或所有权重，因此不能进一步补写奖励加权形式。

观测中的计数器使用相对 cycles 的对数比值：

```text
observation_counter = log(COUNTER / CYCLE)
```

其中 COUNTER 包括指令数、cache miss、branch miss、L1 data cache load/write miss 和 L1 instruction-cache load miss；CPU cycles 同时是目标和归一化参考。论文未明确说明 RL agent 的具体损失函数或算法名称。

## 6. 实验设置

### 6.1 数据集来源

超参数合成数据源于 MiBench 的若干小程序及其随机优化交互。训练任务使用 Splash-3 和 Parsec-3 的优化任务；测试使用 SPEC CPU 2017 Speed 中以 C/C++ 编写的 benchmark，排除 `600.perlbench_s`，原因是 Clang 编译困难。测试聚焦总执行时间超过 2% 的热点函数，共报告 65 个 hot functions；使用 `llvm-extract` 隔离函数，避免函数间干扰。

### 6.2 模型与工具

编译基础设施是 Clang-12；使用 LLVM IR、Clang `opt`、IR2vec、`llvm-extract`、Linux perf 和 Valgrind Cachegrind。RL agent 超参数搜索得到 NN512-L4（4 层，512、256、256、128）；IR2vec 维度从 50 降为 8。LLM 是 GPT-4o-mini。训练/评测硬件包括 AMD EPYC 7763 和未参与训练的 AMD Ryzen 9950X。

### 6.3 对比方法

主要 baseline 是 OpenTuner。优化序列长度限制为 16，选项来自 60 个常用选项且允许重复。另比较 `-O0` 和 `-O3`，并构造逐函数选择 DeCOS 或 `-O3` 的混合方案。

### 6.4 评价指标

主要指标是 CPU cycles，结果归一化到 `-O0`；越低越好。每项结果平均四次运行，profiling 偏差超过 5% 时追加四次。还报告相对 OpenTuner 更好/相似的热点函数比例、几何平均性能、LLM 查询时间和额外模块的 wall-clock overhead。

## 7. 实验结果与结论

### 7.1 主要结果

在训练于 AMD EPYC 7763 的环境中，DeCOS 相比 OpenTuner 在 SPEC 热点函数的 40/65（61.5%）上更好、5/65（7.7%）相似，几何平均性能优于 OpenTuner 21.4%。在未见过的 AMD Ryzen 9950X 上，43/65（66.2%）更好、11/65（16.9%）相似，平均优于 OpenTuner 26.8%。

### 7.2 与编译器基线比较

以 `-O0` 为探索基线时，程序级结果中 DeCOS 相对 `-O3` 提升 5.1%；逐函数选择 DeCOS 或 `-O3` 的混合方案相对单独 `-O3` 提升 5.7%。论文也指出 641.leela_s 在函数级 DeCOS 更好，但程序级 OpenTuner 更好，说明热点函数局部优化不必然等价于整程序最优。

### 7.3 数据效率和开销

在 Splash-3 Transpose 函数案例中，随 epoch 增加性能逐步改善但有明显波动，反映探索与利用的平衡。RL engine 每次预测额外开销低于 0.1 秒；32 次 LLM 查询平均每次 13.7 秒，论文日志中两者合计低于 wall-clock 时间的 1%，且可与 profiling/testing 并行。

### 7.4 消融实验

去掉硬件性能计数器后，模型仅在 32.3% 函数上更好、52.3% 函数上变差，归一化性能几何平均下降约 2%。LLM 集成在评测阶段使 35/65 函数改善、19/65 变差，几何平均略降；在训练阶段，LLM 版本改善 53/91（58.2%）函数、变差 38/91（41.8%），几何平均变化为正。因此论文的证据更支持 LLM 用于冷启动加速，而不是保证已训练模型的最终性能提升。

### 7.5 模拟器反馈的作用

训练阶段每个优化步骤更新模拟性能信息；评测时为降低开销只在第一个优化选项后更新一次。完全取消中间模拟会使不同 benchmark 在更多 epoch 下出现行为分化，体现模拟开销与更细反馈之间的取舍。

## 8. 主要创新点

### 8.1 LLM 引导 RL 冷启动

LLM 被用作外部先验，为 RL 早期探索提供候选优化集合，不进行参数微调。论文的消融结果显示这一机制在训练阶段更有帮助，但在已训练模型评测阶段可能轻微伤害几何平均性能。

### 8.2 静态—动态增强观测

DeCOS 将 IR2vec embedding、硬件性能计数器、已执行选项和最耗时指令组合为优化状态，目标是让模型看到程序结构、当前执行状态和已走过的搜索路径。去掉硬件计数器的实验支持该设计具有实际影响。

### 8.3 合成调参与模拟去噪

用 MiBench 交互统计构造合成数据以选择 RL 配置，用 Cachegrind 提供稳定中间反馈，再用真实 perf 结果约束最终目标。这是围绕编译优化 RL 数据成本设计的工程—算法组合。

## 9. 局限性

### 9.1 论文明确承认的局限

LLM 查询存在外部 API 延迟，模拟结果不能完全等价真实运行；热点函数级优化与整程序性能可能不一致。论文还展示了 LLM 集成在部分函数上造成退化，以及模拟次数与性能收益之间的权衡。

### 9.2 阅读后发现的潜在局限

实验固定使用 Clang-12、特定 AMD CPU、最多 16 个 pass 和 60 个候选选项，不能直接推断对其他 LLVM 版本、RISC-V 后端或更长序列有效。Cachegrind 只用于中间观测，不能代替真实硬件周期；以超过总时间 2% 作为热点门槛也可能遗漏多个中等热点共同作用的情况。论文未明确给出 RL 算法名称、完整损失函数和所有奖励权重，复现实验时需要补充实现细节。

## 10. 阅读后的研究方向反思

最值得借鉴的是把 LLM 限制为冷启动先验，把最终性能决策交给编译反馈和 RL，从而避免把 LLM 的自然语言判断直接当作性能证据。核心贡献已包含 LLVM/硬件计数器/Cachegrind/LLM 的组合，后续不能只把 CPU 换成 RISC-V 就形成充分创新。对 RISC-V 研究而言，真正的新问题应是如何建模 VLEN、LMUL、向量寄存器压力、访存和真实 RVV 周期，并验证跨硬件迁移。

## 11. 可进一步尝试的研究方向

### 11.1 面向 RVV 的 LLM 冷启动与可验证反馈

#### 研究问题

LLM 建议的 RVV/LLVM 优化序列如何经过后端合法性检查、汇编检查和真机周期反馈筛选。

#### 与原论文的区别

增加 RVV-specific lowering、向量长度和寄存器压力，不把 LLM 建议直接视为正确或高性能。

#### 可能的创新点

设计包含 RVV 状态、反汇编特征和硬件计数器的观测，并研究 LLM 先验与真实硬件反馈的冲突处理。

#### 实验框架

```text
LLVM IR → LLM 候选 pass/向量化建议 → LLVM/RVV 合法性检查
    → RVV 真机周期与 PMU → RL 更新 → 跨 VLEN 平台测试
```

#### 可行性

需要 LLVM RISC-V 后端、RVV 真机、PMU 工具、反汇编检查和可重复 benchmark。

#### 主要风险

硬件型号、RVV 版本和编译器版本差异可能污染迁移结论；LLM 建议可能造成搜索偏置。

### 11.2 模拟器—真机不确定性建模

研究 Cachegrind、QEMU 或微架构模拟器与真机 PMU 的偏差，并让 RL 使用置信度而不是无条件使用模拟奖励；区别在于显式建模反馈可靠性。

### 11.3 函数级与整程序联合优化

将热点函数收益、调用频率和代码大小共同纳入奖励，处理 DeCOS 在 641.leela_s 中出现的函数级与程序级目标不一致问题。

## 12. 与其他已读文献的关系

本批次 C24 Pearl 和 C25 DeCOS 都使用 RL 搜索编译优化动作。Pearl 处理 Tiramisu 多面体循环变换，强调结构化 AST 动作和未见循环程序泛化；DeCOS 处理 LLVM pass 序列，强调运行时计数器、LLM 冷启动和跨硬件迁移。C25 更适合作为 LLVM/RISC-V 动态反馈 baseline，C24 更适合作为结构化循环动作参考；二者可以组合，但实验指标和编译对象不同，不能直接比较 speedup 数字。
