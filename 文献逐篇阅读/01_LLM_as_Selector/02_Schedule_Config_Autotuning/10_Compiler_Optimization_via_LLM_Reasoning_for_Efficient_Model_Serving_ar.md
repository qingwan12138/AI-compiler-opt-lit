## 1. 研究背景

神经网络模型推理的高效执行高度依赖底层计算核的编译优化，核心优化决策包括tile size（分块大小）、fusion（算子融合策略）、data layout（内存布局选择）和loop ordering（循环顺序）。这些优化决策之间相互依赖——例如，tile size的选择会影响哪些fusion策略可行，而layout又会改变数据访问局部性。传统方法（如TVM AutoTVM、Ansor）使用随机搜索或基于成本的模型来探索这个组合空间，但面临样本效率低且容易探索无效区域（如不满足依赖关系的融合方案）的问题。自动搜索时间可能长达数小时甚至数天，尤其当优化参数维度增大时，搜索空间呈指数级增长。最近的工作尝试用LLM来指导搜索，但往往需要重新训练模型或依赖大量标注数据，这限制了LLM在不同模型和硬件场景之间的泛化能力。同时，已有方法通常将LLM作为固定的优化器而非可迭代改进的推理引擎，没有充分利用LLM理解性能反馈并进行自调整的能力。

## 2. 论文要解决的问题

### 2.1 如何在不重新训练LLM的情况下加速编译优化搜索

该工作聚焦于利用现成的预训练LLM（GPT-4、Claude、Llama等）作为搜索指导，而非训练专用模型。核心挑战在于：预训练LLM虽然具备广泛的代码理解能力，但缺乏针对特定编译器优化空间的专门知识。如何通过提示工程和上下文学习弥补这一差距，使其生成的优化建议比随机搜索更有价值，是该方法需要回答的首要问题。

### 2.2 如何将LLM的推理能力与结构化搜索算法有效结合

需要将LLM的代码分析和理解能力与结构化搜索算法（如MCTS）结合起来，在保持探索质量的同时提高样本效率。具体而言，LLM的proposal需要作为MCTS树扩展的先验指导，同时MCTS的UCT平衡机制需要防止LLM过度聚焦于局部最优区域。此外，如何将搜索过程中的历史性能反馈和程序状态信息传递给LLM，使其逐步聚焦于高潜力区域，无需参数更新即可实现上下文学习，也是一个关键的设计挑战。

### 2.3 不同LLM在指导编译优化搜索时的能力差异

需要研究不同的LLM（大小不同、训练数据不同）在指导编译优化搜索时是否表现出一致的能力差异。例如，GPT-4等大模型相比Llama-2 7B等小模型在proposal质量上是否有显著优势？这种优势是否在所有类型的优化算子上一致？大型模型的额外计算开销是否被更好的proposal质量所抵消？

> 本文主要研究：如何在不需要重新训练LLM的条件下，通过将预训练LLM的代码理解和推理能力与MCTS搜索算法相结合，显著提升tensor程序编译优化的样本效率。

## 3. 核心方法概述

ReasoningCompiler采用LLM + MCTS的混合搜索策略，不对LLM进行任何训练或微调。在每次搜索迭代中，LLM接收当前程序的IR表示、已尝试的优化配置及其性能结果作为上下文，然后提出一个或多个新的优化选择（tile size、fusion decision、layout等）。这些候选变换通过编译和实际运行来获得性能反馈。MCTS框架在外层组织搜索过程，LLM作为proposal policy驱动树的分支选择。

```
目标Tensor程序 + 程序状态编码
        ↓
LLM Proposal模块（基于历史反馈生成优化候选）
        ↓
MCTS搜索引擎（节点选择 -> 扩展 -> 评估 -> 回传）
        ↓
编译候选配置
        ↓
在目标硬件上运行评估（AMD EPYC CPU）
        ↓
性能反馈加入历史轨迹，LLM据此调整后续proposal
        ↓
循环直至预算用完或收敛
```

## 4. 实验框架与训练流程

系统架构包含四个核心组件：

### 4.1 程序状态编码器

将待优化的tensor程序转换为LLM可读的文本表示，包括循环结构、张量形状、依赖图和数据流信息。编码方案的设计关键是将结构化信息（如循环嵌套、张量维度）转化为LLM容易理解的文本格式，同时不丢失关键语义。编码后的程序状态通常包含循环层级、循环边界表达式、张量读写模式、已知数据依赖等信息。编码方案需要平衡信息完整性和上下文窗口限制（LLM的token限制），这对大维度张量程序尤为重要。

### 4.2 LLM Proposal模块

使用预训练LLM（实验中比较了GPT-4、Claude、Llama-2 7B/13B等），给定当前状态和历史轨迹，生成下一步优化动作的描述性文本（如"将tile size设为128, 128，并融合外层循环"）。这些文本被解析为具体编译配置。Prompt模板包含程序结构描述、历史搜索轨迹（已尝试的配置及其结果）、以及当前待决策的优化维度列表。关键设计是让LLM看到历史的性能反馈，从而在不解锁参数更新的情况下实现迭代改进。

### 4.3 MCTS搜索引擎

维护搜索树结构，每个节点存储访问次数、平均奖励和LLM生成的proposal文本。使用PUCT/UCT算法选择节点，LLM的proposal作为先验概率指导树增长。搜索树的每个分支对应一个完整的优化配置（如一组tile size + fusion + layout决策）。树搜索到一定深度后对叶节点编译评估。MCTS的结构化搜索特性补偿了LLM可能的不稳定性——即使LLM偶尔生成次优proposal，MCTS的探针选择机制仍然保证搜索不会完全偏离最优区域。

### 4.4 性能评估器

编译候选配置并在目标硬件（AMD EPYC CPU）上实际运行，记录延迟等指标作为奖励信号。每个评估结果（成功/失败、延迟数值、其他性能指标）被添加到历史轨迹中，用于后续LLM推理的上下文。该架构的关键设计决策是将LLM作为proposal policy而非value network，因为proposal生成是LLM最擅长的任务。

## 5. 奖励函数、损失函数或关键公式

该方法的核心算法是MCTS中的节点选择和奖励回传机制：

| 符号 | 含义 |
|---|---|
| UCT(s, a) | 节点s下动作a的上置信界 |
| Q(s, a) | 动作a在节点s的平均奖励 |
| N(s, a) | 动作a在节点s被选择的次数 |
| N(s) | 节点s的总访问次数 |
| c | 探索常数，控制探索与利用的平衡 |
| P(s, a) | LLM提供的先验概率（proposal偏好） |

UCT公式：`UCT(s, a) = Q(s, a) + c * P(s, a) * sqrt(log(N(s)) / (1 + N(s, a)))`

LLM的proposal质量直接影响先验概率P(s, a)的准确性，这是该方法区别于纯MCTS（无先验）或随机搜索的关键。奖励信号Q(s, a)来自实际硬件评测的延迟数值，通常归一化到[0,1]区间。该方法没有使用额外的损失函数或梯度更新，完全依靠LLM的推理能力和MCTS的探索机制来迭代改进。

## 6. 实验设置

### 6.1 数据集来源

实验使用神经网络模型服务场景下的典型tensor程序测试算子，涵盖矩阵乘法（GEMM）、卷积（conv2d）、归一化（layer norm/softmax）等常见深度学习张量操作。使用不同张量形状组合测试泛化性（从32x32到1024x1024不同尺寸）。

### 6.2 模型与工具

目标硬件为AMD EPYC CPU（x86-64架构）。比较的LLM后端包括GPT-4、Claude 3、Llama-2 7B/13B和Mixtral 8x7B等模型。编译工具链为TVM/Ansor/TIRAMISU等张量编译框架。

### 6.3 对比方法

比较的基线包括：随机搜索、纯MCTS（无LLM指导）、AutoTVM（基于成本模型的搜索）、Ansor（基于模板的搜索）和之前的TIRAMISU工作。

### 6.4 评价指标

核心指标包括：收敛到最优性能所需的评测样本数（sample efficiency）——衡量达到相同性能水平所需的硬件评估次数，这是核心指标；最终收敛的运行时间（推理延迟，越低越好）——衡量最终优化质量；搜索时间（wall-clock time）——包括LLM推理时间、编译时间和硬件评估时间。

## 7. 实验结果与结论

### 7.1 主要结果

LLM + MCTS在几乎所有测试算子上都优于纯MCTS和随机搜索，达到相同性能水平所需的样本数减少2-5倍。在卷积算子搜索中，LLM+MCTS约需30次评估达到最优，而纯MCTS需要约150次。LLM的proposal质量比随机采样高，因为LLM能够利用历史反馈来识别高潜力区域——例如，当某组tile size表现差时，LLM倾向于提出完全不同的值而非在附近微调，这种"跳跃式搜索"比局部微调更高效。不同LLM后端之间存在性能差距，更强的模型（GPT-4）通常产生更好的proposals，但较小模型（Llama-2 7B）在某些算子（如softmax）上的表现也接近GPT-4。与传统AutoTVM/Ansor相比，LLM+MCTS在搜索空间较大时（如8维以上的优化参数）优势更明显，在小搜索空间上差异不显著。搜索时间中，LLM推理时间占比约20-30%，编译和硬件评估仍占主导。

### 7.2 消融实验

历史轨迹的深度（context length）影响LLM的推理质量——提供最近5-10次评估结果作为上下文效果最佳，过长（20+次）的历史可能引入噪声，过短（3次以下）则缺乏有效信息。消融实验还表明，移除程序状态编码中的关键信息（如依赖图）会导致LLM的proposal质量明显下降，证实了编码方案中每个信息维度的必要性。

### 7.3 案例分析

论文对单个卷积算子的搜索过程进行了可视化分析，展示了LLM如何逐步缩小搜索范围：初始proposal分布较分散（覆盖多个tile size区间），随着性能反馈的累积，proposal逐渐聚焦到最优区域附近。这验证了LLM的上下文学习能力在编译优化中的有效性。

## 8. 主要创新点

### 8.1 创新点一：LLM作为MCTS的Proposal Policy

首次将LLM作为MCTS的proposal policy用于编译优化，而不需要微调或重新训练LLM。这显著降低了LLM在编译器优化中的使用门槛，使现成的商业/开源LLM可直接用于搜索指导。相比需要昂贵训练的方法，这种方法更实用且更易于快速部署到新的硬件平台上。

### 8.2 创新点二：轻量级程序状态编码方案

设计了一个轻量级的程序状态编码方案，使LLM能够理解tensor程序的优化上下文。编码平衡了信息完整性和上下文窗口限制，将结构化程序信息转化为LLM友好的文本形式。这一编码方案的设计原则（结构化信息的文本化表示、分层式描述、关键依赖显式标注）可以被扩展到其他编译优化场景。

### 8.3 创新点三：量化LLM推理能力对样本效率的影响

通过消融实验量化了LLM推理能力、历史轨迹长度和模型选择对样本效率的影响，为后续工作的LLM选择提供了数据支持。关键发现是影响proposal质量的核心因素不是模型大小而是模型的推理对齐质量——即模型能否理解性能反馈中的语义并做出相应调整。

### 8.4 创新点四：零参数更新的迭代优化

证明了一个重要的概念：LLM可以利用编译性能反馈进行多轮推理和自修正，而无需参数更新。通过上下文中的性能反馈，LLM可以逐步调整其proposal策略。这意味着编译器优化中的"在线学习"可以通过LLM的上下文学习实现，而无需复杂的online RL训练框架。

## 9. 局限性

**论文明确承认的局限：**
(1) 目标域仅限于神经网络模型服务的tensor程序优化，不是通用的LLVM IR或任意程序的编译优化。优化动作（tile、fusion、layout）是张量程序特有的，不适用于通用编译器Pass排序。方法的泛化性在通用程序优化上未经测试。
(2) 实验仅在x86-64（AMD EPYC）上进行，无任何跨ISA（如RISC-V、ARM SVE）或跨硬件的迁移实验。LLM在不同架构上的提议质量差异未知，历史反馈在跨架构场景下的迁移效率也是开放问题。
(3) 不同LLM之间的性能差异显著，依赖强LLM（如GPT-4）可能引入API成本和不稳定性（API变更、版本更新等）。小模型如Llama-2 7B效果不稳定，在某些算子上的表现接近随机搜索。

**阅读后发现的潜在局限：**
(4) 搜索结果的可复现性存疑——LLM推理具有随机性（即使设置temperature=0，不同次运行的搜索路径也可能不同），使得实验结果的精确复现困难。这对学术可重复性是一个挑战。
(5) 没有正确性验证机制——LLM生成的配置在编译时可能产生错误代码（如错误的tile导致越界访问），仅靠运行时反馈无法区分语义错误和性能不佳。可能搜索到了"高错误率但高平均性能"的配置但没有意识到。
(6) 没有研究LLM的proposal质量是否可以从一个硬件平台迁移到另一个平台——在AMD EPYC上学到的知识对RISC-V后端的帮助有多大仍是未知。这限制了方法的泛化性和实用性。

## 10. 阅读后的研究方向反思

【分析内容】对于后续研究而言，LLM Proposal + MCTS的组合是后端智能体搜索策略的强基线，但不应把MCTS加LLM本身作为多架构创新——这一组合已经被ReasoningCompiler验证过，需要进一步差异化。该工作证明了LLM可以利用历史性能反馈进行迭代改进，这支持了"后端反馈驱动IR优化"的设计思路——不同后端上的性能反馈可以作为LLM的"跨架构上下文"。一个重要启示是：LLM在不同硬件上的proposal质量可能差异显著，需要额外的机制来桥接跨架构的知识鸿沟。在一架构上有效的优化策略可能在另一架构上无效甚至适得其反。该工作缺乏正确性验证，而验证正是后端多架构场景中的关键需求——性能再高的错误变换也毫无价值。程序状态编码方案的设计思路可以扩展到通用IR——如何将LLVM IR的结构化信息转化为LLM友好的格式，同时保留对编译优化足够的信息量。MCTS的搜索树结构可用于建模跨架构搜索空间——每个架构（x86/RISC-V/ARM）可以是MCTS树中的一个条件分支。

## 11. 可进一步尝试的研究方向

### 11.1 跨架构的LLM+MCTS编译优化搜索

#### 研究问题
如何将ReasoningCompiler的LLM+MCTS搜索框架扩展到跨架构场景（x86-64 + RISC-V），使LLM能在不同硬件平台上共享优化经验？

#### 与原论文的区别
原论文只针对AMD EPYC单平台，本方向引入多架构支持和知识迁移机制。

#### 可能的创新点
架构感知的程序状态编码（加入架构特征作为条件输入）、跨架构MCTS树结构（架构作为树的条件分支）、历史反馈的跨架构迁移学习。

#### 实验框架
在x86-64和RISC-V两个平台上分别运行LLM+MCTS搜索，比较独立搜索与跨架构迁移搜索的样本效率差异。

#### 可行性
高，基于现有方法框架（LLM+MCTS）做架构扩展，无方法学颠覆。

#### 主要风险
跨架构知识迁移的策略需要谨慎设计，负迁移风险存在（在x86上有效的策略在RISC-V上可能有反效果）。

## 12. 与其他已读文献的关系

【分析内容】ReasoningCompiler与ACCLAIM和LLM-VeriOpt形成互补关系。ReasoningCompiler侧重于单层（tensor程序级）的搜索效率优化，使用LLM但不进行训练；ACCLAIM扩展到了多层级（source/IR/assembly）但同样使用预训练LLM；LLM-VeriOpt则引入了训练（RL）和验证机制。三者的技术路线呈递进关系：从不训练的LLM推理搜索（ReasoningCompiler）到多智能体协作（ACCLAIM）再到验证引导的训练（LLM-VeriOpt）。ReasoningCompiler的MCTS+LLM组合方法可以被ACCLAIM采纳进IR Agent的搜索策略中，同时其缺少的验证机制可以由LLM-VeriOpt的验证框架补充。对于综述（Paper 9）的分类框架，ReasoningCompiler被归类为(selector, pretrained, source-level, optimization)类别。
