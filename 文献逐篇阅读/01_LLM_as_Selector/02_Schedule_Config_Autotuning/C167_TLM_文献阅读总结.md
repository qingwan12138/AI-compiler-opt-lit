## 1. 研究背景

本文研究深度学习张量程序编译。卷积、矩阵乘法、注意力等算子的执行效率高度依赖循环分块、展开、并行绑定、向量化、内存布局等调度选择。传统深度学习框架依赖 cuDNN、oneDNN 等手写库，覆盖面和维护成本受限；TVM、Ansor、MetaSchedule、Halide 等自动编译器则在巨大调度空间中搜索。

论文第 1–3 页指出两类主要瓶颈：启发式方法编译快但可能错过高性能方案；搜索方法保留更大空间，却需要随机采样、代价模型和大量编译—执行测量，BERT 等大模型的调优可能耗时数小时或数天。论文的动机是把已有高质量调度中的结构规律交给语言模型学习，以减少运行时搜索。

## 2. 论文要解决的问题

### 2.1 编译时间与运行性能的冲突

搜索式张量编译器可以发现高性能配置，但需要大量在线探索；规则式编译器速度较快，却可能牺牲执行效率。论文要解决的是在不进行大规模运行时探索的情况下，仍生成接近搜索方法性能的调度。

### 2.2 如何让语言模型表达合法调度

原始 IR 或源代码较长且层次复杂，不适合直接作为短序列预测输入。论文构造 Tensor Language，把算子图、张量形状、硬件元数据和调度决策压缩为有序 token 序列，并由 Space Builder 给出满足语义和硬件约束的决策空间。

> 本文主要研究：如何用离线训练的自回归语言模型，从结构化张量程序和硬件上下文中一次生成完整、合法且高性能的编译调度。

## 3. 核心方法概述

TLM 框架由 Space Builder 和 Generator 两部分组成。Space Builder 接收计算图并拆分子图，构造包括 tiling、unrolling、线程/块绑定、向量化和内存布局的调度空间；Generator 使用 GPT-2 small 架构的 Tensor Language Model，按 token 自回归生成完整 tensor sentence。之后 TVM 后端把该调度编译成实际低层程序。

```text
计算图/张量子图 + 形状 + 硬件元数据
        ↓
Space Builder 构造有约束的调度决策空间
        ↓
Tensor Language 序列化
        ↓
GPT-2 small/TLM 自回归生成调度 token
        ↓
完整 tensor sentence（调度配置）
        ↓
TVM 后端编译与真实硬件执行
        ↓
运行延迟与编译时间评估
```

按 taxonomy v2，语言模型的最终输出是 schedule/configuration，现有编译器负责实际变换，因此归入 SELECTOR，而不是 TRANSLATOR。论文强调生成阶段不执行在线搜索、代价模型迭代或强化学习反馈。

## 4. 实验框架与训练流程

### 4.1 数据构造与预训练

论文第 11–12 页称，数据来自 ResNet-50、MobileNetV2、EfficientNet、BERT-base、GPT-2 和 LLAMA-7B 的子图；总计约 3,300 个子图、320 万条 tensor sentences。预训练覆盖好坏不同的程序，以因果语言模型目标预测下一个 token，学习算子、硬件上下文和调度结构的统计规律。

### 4.2 监督微调

作者为 tensor programs 在真实硬件上测量延迟，保留高性能调度作为正例，构成 SFT 数据。模型在这些带性能信息的高质量序列上进行监督微调，使生成倾向于低延迟调度。论文未给出 SFT 子集的精确条数。

### 4.3 推理与编译评估

输入新的算子/子图、形状和硬件信息后，Space Builder 产生决策结构，TLM 单向自回归生成完整调度。生成结果交给 TVM 0.10 编译并在真实机器上执行。论文将其与 Ansor、MetaSchedule、Roller、TensorRT 和 PyTorch eager 比较。

### 4.4 训练/反馈边界

本文包含 CLM 预训练和 SFT；没有 PPO、GRPO、RLHF 或运行时强化学习。生成阶段也没有在线代价模型训练、模拟器反馈或迭代修正。论文明确说避免 RL 是为了减少环境交互、延迟测量和奖励工程成本。

## 5. 奖励函数、损失函数或关键公式

本文没有使用强化学习，因此不存在强化学习奖励函数。

论文第 7 页用集合表示调度空间：`S = (s1, s2, ..., sn)`，其中每个 `si` 是一组调度选择，包括 tiling、循环展开、并行化和内存布局变换。该式表达的是合法候选空间，不是训练奖励。

预训练和 SFT 使用因果语言模型的 next-token prediction 与交叉熵损失；论文说明了交叉熵目标，但未给出完整的数学展开式。SFT 的性能导向来自真实硬件延迟筛选出的高性能样本，而非显式奖励函数。

## 6. 实验设置

### 6.1 数据集来源

数据由六类模型的子图和历史搜索/专家标注调度组成：CV 为 ResNet-50、MobileNetV2、EfficientNet，共约 1,500 个子图/120 万条序列；NLP 为 BERT-base、GPT-2、LLAMA-7B，共约 1,800 个子图/200 万条序列；总计约 3,300 个子图/320 万条序列。论文未明确给出独立训练、验证、测试集的具体划分，也未做数据泄漏量化分析。

### 6.2 模型与工具

| 项目 | 论文信息 |
|---|---|
| 模型 | GPT-2 small；12 层、768 hidden units、12 attention heads |
| 训练 | 一张 NVIDIA V100 32 GB；预训练约 10 小时，SFT 约 10 分钟 |
| 编译器 | TVM 0.10 |
| GPU 栈 | NVIDIA V100 32 GB、CUDA 11.7、cuDNN 8.4 |
| CPU 栈 | Intel Xeon Platinum 8255C，24 cores、2.50 GHz、AVX-512 |
| 训练/加载 | PyTorch 2.1、Hugging Face Transformers，条件允许时使用 FP16 |
| 测量 | 裸机真实执行，不是模拟器；固定随机种子并对多次运行取平均 |

### 6.3 对比方法

Ansor 和 MetaSchedule 代表基于搜索与代价模型的自动调优；Roller 代表快速但偏启发式的调度生成；TensorRT 代表工业 GPU 部署管线；PyTorch eager 代表易用但通常未充分编译优化的基线。

### 6.4 评价指标

主要指标为编译时间和执行/推理延迟。编译时间越小越好；执行延迟越小越好；speedup 表示相对基线的运行速度比。论文还比较编译时间—推理延迟的 Pareto 关系，并讨论相同输入下生成结果的确定性和可复现性。

## 7. 实验结果与结论

### 7.1 主要结果

摘要和第 15–17 页报告：在子图层面，TLM 编译速度最高约为 Ansor/MetaSchedule 的 60–61 倍；相对 Roller，论文摘要给出最高约 2.25 倍的编译速度优势，同时第 15–17 页报告 TLM 在测试子图上通常取得约 1.3–1.5 倍的运行 speedup。不同图表的精确逐点数值应以原图读取，当前 PDF 文本不足以可靠恢复全部柱状图数值。

### 7.2 与搜索和启发式方法比较

第 16–17 页称，ResNet 卷积子图中 TLM 的执行时间与 MetaSchedule 最佳结果相差约 23% 以内；部分 BERT 矩阵乘法子图中 TLM 比 Ansor 快约 5%。Ansor/MetaSchedule 每个子图通常需要约 300–500 秒的编译—测量过程，而 TLM 平均约 5–7 秒生成全部子图的结果；Roller 编译较快但某些情况下运行慢约 15–20%。

### 7.3 端到端模型

在 ResNet-50、BERT-base 和 GPT-2 的整模型测试中，TLM 的推理延迟接近或略优于搜索基线，并比 Roller 最多约 1.5 倍快。论文举例称 ResNet-50 使用 TLM 约 20 秒编译，而 Ansor 约 600 秒、MetaSchedule 约 550 秒；整模型编译时间相对搜索方法约快 20–30 倍。所有运行时间均为真实硬件测量，不应解释为模拟器估计。

### 7.4 消融实验

论文主体没有提供一个清晰、独立列出的“去掉 Tensor Language/Space Builder/SFT”的完整消融表。文中通过子图、整模型、不同工作负载和工业管线比较来验证系统设计，但当前 PDF 内容不足以确认各模块的独立因果贡献。

### 7.5 稳定性与案例

论文称相同输入下 TLM 生成一致调度，避免搜索方法的随机种子和测量噪声导致结果波动；还声称模型可学习跨算子内存复用、算子融合和线程块映射等全局规律。不过，论文未给出这些现象的单独定量统计。

## 8. 主要创新点

### 8.1 创新点一：把张量调度重表述为序列生成

论文不是让通用 LLM 直接生成源代码，而是把算子图、硬件上下文和调度决策编码成 Tensor Language，让自回归模型直接预测 schedule token。该设计使模型输出属于 SELECTOR 的配置结果，并由 TVM 执行实际编译。

### 8.2 创新点二：Space Builder 与 Generator 解耦

Space Builder 保留大而有约束的候选空间，Generator 学习在其中选择高质量配置。论文认为这种解耦避免了启发式提前裁剪，同时把昂贵的探索成本转移到离线数据阶段。

### 8.3 创新点三：离线 CLM + SFT 替代运行时搜索/RL

预训练学习结构，SFT 使用真实延迟筛选的高性能序列。实验结果支持其在固定硬件与相似工作负载上降低编译时间；但“创新有效”应限定在论文测试栈和数据分布内，不能外推为普遍最优。

## 9. 局限性

### 9.1 论文明确承认的局限

第 20 页明确指出分布偏移是主要问题：新算子、新硬件 primitive 或显著不同的架构可能导致次优调度。预训练需要大规模 tensor programs、轨迹和硬件配置，成本较高。实验只在一套固定硬件上进行，跨硬件泛化没有被充分验证。框架没有最优性形式化保证，并且更适合卷积、矩阵乘法和注意力等具有重复结构的工作负载。

### 9.2 阅读后发现的潜在局限

论文把高质量搜索轨迹和专家标注作为数据来源，因此 TLM 的上限受离线数据覆盖度影响；同时没有给出明确的训练/验证/测试划分，存在需要进一步审计的泄漏风险。PDF 中部分表格/图的精确数字无法从文本层完整复原，不能把摘要中的最高 speedup 当作所有模型的平均值。Tensor Language 的语义合法性主要依赖其语法和 Space Builder 约束，论文没有提供形式化验证器或跨架构正确性证明。

## 10. 阅读后的研究方向反思

值得借鉴的是“结构化调度语言 + 编译器约束 + 离线性能数据”三者结合，以及把 LM 输出限制为可执行配置。它比直接生成低层代码更容易让既有编译器承担正确性与代码生成责任。对 RISC-V 的关系是中等：论文没有 RISC-V 实验，但其硬件元数据条件化方式可迁移到 RISC-V CPU/RVV 或自定义加速器；仅替换 CUDA 为 RISC-V 并不足以形成新贡献。

本文核心贡献是 Tensor Language、TLM 训练和 Space Builder/Generator 体系，后续工作不应简单复刻。更合适的定位是 SELECTOR baseline 和调度表示方法参考；若引入 RISC-V，应研究 RVV 向量长度、LMUL、尾部策略、缓存层次与实际微架构反馈的联合泛化，而不只是换平台。

## 11. 可进一步尝试的研究方向

### 11.1 面向 RISC-V/RVV 的硬件条件化调度

#### 研究问题

TLM 能否根据 RVV 的 vlen、LMUL、缓存容量和核数生成跨芯片可迁移的张量 schedule？

#### 与原论文的区别

不只是把 GPU token 改成 RISC-V token，而是研究可变向量长度和微架构差异造成的调度分布偏移。

#### 可能的创新点

加入 RVV 体系结构描述、跨芯片元学习和硬件计数器校准。

#### 实验框架

```text
张量子图 + RVV/缓存元数据 → TLM 生成 schedule → LLVM/TVM-RVV 编译
→ 裸机运行与计数器反馈 → 跨芯片泛化评估
```

#### 可行性

需要 RVV 工具链、至少两类 RISC-V 平台或仿真/实机、TVM/LLVM 后端和可重复的张量基准。

#### 主要风险

硬件样本不足时容易把设备记忆误当成泛化；仿真时间也不能替代真实性能结论。

### 11.2 搜索与生成的风险感知混合调度

#### 研究问题

在 TLM 置信度低或检测到分布外输入时，何时回退到 Ansor/MetaSchedule 搜索？

#### 与原论文的区别

保留 TLM 的快速路径，同时建立可解释的 OOD 检测和有限预算搜索回退，而非声称单次生成总能可靠。

#### 可能的创新点

基于 token 不确定性、硬件距离和少量测量的动态路由。

#### 实验框架

```text
TLM 生成 + 置信度/OOD 判断 → 高置信度直接采用；低置信度进入有限搜索
→ 性能/编译时间联合比较
```

#### 可行性

可复用本文 Tensor Language、TVM 和已有搜索基线。

#### 主要风险

回退规则可能抵消编译时间收益，且置信度未必与真实性能相关。

### 11.3 可验证的调度配置生成

#### 研究问题

如何把 Tensor Language 的语法合法性扩展为可检查的语义保持和资源约束保证？

#### 与原论文的区别

原论文主要依赖 Space Builder 的约束与真实执行；新方向增加静态检查、资源上界检查和失败修复。

#### 可能的创新点

设计调度 DSL 的类型系统，检查向量化、共享内存和布局变换的约束，并报告不可行原因。

#### 实验框架

```text
TLM 生成 → DSL 类型/资源验证 → 合法配置送入编译器
→ 不合法配置受约束修复 → 性能与拒绝率评估
```

#### 可行性

需要 MLIR/TVM 约束接口、调度 DSL 和跨算子测试集。

#### 主要风险

静态合法不等于实际高性能；验证规则过严会缩小探索空间。

## 12. 与其他已读文献的关系

本次 S2 staging 只完成这一篇论文的独立全文阅读，没有同批已确认的其它论文可用于逐篇横向比较。正式语料中已有的 `AutoComp`、`LLM-Guided Autoscheduling`、`PerfDojo`、`MailoHLS` 和 `LLM4HLS` 等条目仅作为去重与范围核验输入，本笔记不把未重新阅读的既有笔记当作本次正文证据。就角色而言，TLM 与这些 S2 条目的共同点是 LM 输出调度/配置；它与直接生成代码的 TRANSLATOR 论文边界在于 TLM 不直接输出最终源代码或 kernel。
