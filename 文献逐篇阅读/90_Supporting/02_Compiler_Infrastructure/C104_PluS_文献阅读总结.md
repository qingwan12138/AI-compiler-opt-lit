## 1. 研究背景

本文属于机器学习编译器与异构 GPU 代码生成领域。ML 编译器通常把深度神经网络（DNN）降低为计算图，再通过算子融合和代码生成把图映射到硬件。论文指出，模型结构一方面呈现部分收敛趋势（例如注意力机制广泛使用），另一方面又快速出现 RMSNorm、SwiGLU、FlashAttention 等新算子组合和优化技术（第 1 节）。

论文将现有编译器分成两类：

1. **嵌入式图变换编译器**：例如 XLA、TorchInductor、TensorRT 等，把融合规则写在编译器内部。优势是自动化，但新增专家优化往往需要修改复杂的编译器实现。
2. **模板式/可插拔编译器**：允许用户提供模板或模式，较容易接入新优化，但通常按精确算子组合匹配，面对结构相近但算子略有变化的模型时需要重复编写前端、后端和注册代码。

因此，论文要解决的是：既保留编译器对模型变化的适应性，又能快速接入专家提供的高性能子图实现和调度。引入的不是大语言模型，而是面向 DNN 图编译的可插拔模式仓库、循环中心子图抽象与代码模板机制。

## 2. 论文要解决的问题

### 2.1 新图优化接入成本高

嵌入式编译器依赖预定义图变换规则。新出现的融合、注意力或归一化优化需要修改图变换模块和相关代码，导致编译器追赶手工优化库的速度较慢（第 1、2 节）。

### 2.2 精确算子模式匹配不够灵活

模板式编译器可以由专家添加模板，但若模型只改变了偏置、简单逐元素算子或层归一化组合，原有模板可能无法复用。论文以 AITemplate 对 T5/T5LayerNorm 的支持为例，说明需要重新添加前端和后端实现（第 2.1、6.3 节）。

### 2.3 子图调度和编译器基础设施耦合

高性能代码的循环结构和调度通常由专家确定，但传统方案把图识别、融合、代码生成和编译器规则紧密绑定。论文研究如何把“子图模式—代码生成调度”从编译器实现中解耦，同时保持正确的数据依赖和动态形状支持。

> 本文主要研究：如何利用循环中心的子图抽象和可插拔代码模板，在不频繁修改编译器核心的情况下，把专家优化的子图调度复用到结构相近的 DNN 子图，并生成 GPU 可执行代码。

## 3. 核心方法概述

PluS 是一个端到端 ML 编译器。其核心设计包括：

* **+Loop**：用循环大小、并行性和关键操作等属性描述算子的循环结构。
* **+Graph**：由若干 +Loop 组成，用循环中心特征表示子图，而不是只比较精确的算子列表。
* **模式仓库（pattern warehouse）**：保存 +Graph 到专家代码模板的映射。
* **子图识别**：从骨架算子开始，通过贪心扩展、前序/后序融合和匹配条件识别可融合子图。
* **+Code 接口**：以数据占位符、计算和写回三类语句描述专家代码模板；编译器补齐具体数据地址、操作和剩余代码。

整体数据流：

```text
PyTorch 模型
    ↓
TorchDynamo 得到 torch.fx.GraphModule
    ↓
Hidet API 解析为低层算子图和 +Graph 表示
    ↓
模式仓库中的 +Graph 与输入子图匹配
    ↓
复用 CUTLASS、ByteTransformer、FlashAttention 等代码模板
    ↓
编译器根据 +Loop 数据依赖补齐代码并生成 CUDA kernel
    ↓
生成可执行 GPU 子图并运行 DNN
```

LLM 不在系统中扮演角色；论文也没有把语言模型作为生成器或优化策略。编译器调用的是 PyTorch/TorchDynamo、Hidet、CUDA/NVCC 和现有高性能 kernel 库。与传统精确算子匹配相比，PluS 试图复用“相同循环结构”的调度，使算子有小变化的子图仍可以使用已有模板。

## 4. 实验框架与训练流程

### 4.1 编译运行流程

本文不涉及模型训练、SFT、强化学习或多阶段训练，主要采用静态编译与运行时性能评估。PluS 的编译流程是：

1. 接收 PyTorch 模型的 `torch.fx.GraphModule`。
2. 使用 Hidet API 解析为由低层算子组成的计算图。
3. 将算子表达成 +Loop，并构成 +Graph。
4. 从模式仓库选择骨架算子并贪心扩展，匹配可融合的前序、后序和生产者算子。
5. 将匹配的 +Graph 映射到代码模板；遍历 +Loop 叶节点，填入数据、计算和写回代码。
6. 通过 NVCC 等工具编译，得到 GPU kernel 并执行。

### 4.2 专家模式添加流程

专家可以直接提供一个 `torch.nn.Module` 及其代码，由 PluS 自动生成并存储模式；也可以显式编写 +Graph 与 +Code 模板。论文实现的模式仓库集成了 CUTLASS、ByteTransformer、FlashAttention 等来源的 kernel。模式仓库支持动态插入和删除（第 5 节）。

### 4.3 动态形状与多调度

PluS 使用符号维度在识别阶段表示动态形状，并把这些维度传递到代码模板。专家可以在模板中根据运行时输入大小选择不同调度；同一子图模式也可以存放多个实现。

## 5. 奖励函数、损失函数或关键公式

本文不涉及强化学习奖励函数，也没有训练损失函数。论文的主要目标是编译图模式匹配、代码生成和端到端推理延迟。

论文使用了如下实验性指标定义：

```text
fusion rate = 原始基础算子数量 / 图变换后的层数量
```

它用于描述算子融合程度，数值越大表示单位融合层包含的原始算子越多。论文没有把这个比率作为可学习目标，而是用于比较不同编译器的图变换结果（第 6.2 节）。

## 6. 实验设置

### 6.1 数据集来源

论文使用五个典型 DNN 模型作为工作负载：BERT-base、ALBERT、GPT-2、T5 和 ViT。它们覆盖 NLP Transformer 与视觉 Transformer。语言模型默认序列长度为 128，ViT 输入图像为 224×224；批大小为 1 和 16（第 6.1 节）。论文中未提供传统意义上的训练集、验证集或测试集规模，因为实验对象是编译和推理工作负载，不是训练数据集。

### 6.2 模型与工具

| 项目 | 论文设置 |
| --- | --- |
| 编译器/框架 | PluS、TorchInductor 2.4.0、TensorRT 10.5.0、AITemplate 0.3.dev0 |
| 前端/运行时 | PyTorch、TorchDynamo、ONNX Runtime 1.18.0（TensorRT 对比路径） |
| 代码生成与库 | CUDA 11.8、NVCC、CUTLASS、ByteTransformer、FlashAttention |
| GPU | NVIDIA A100 PCIe 80GB、NVIDIA GeForce RTX 4090 |
| CPU | AMD EPYC 7V13、Intel Xeon Gold 5318Y |
| 操作系统 | Ubuntu 22.04 |
| 性能分析 | Nsight Systems（T5 的 TensorRT 特殊情况） |

### 6.3 对比方法

* **TorchInductor**：TorchDynamo 提供的嵌入式图编译器路径。
* **TensorRT**：通过 ONNX Runtime 的 TensorRT provider 运行，开启动态形状并设置 batch/序列长度范围。
* **AITemplate**：模板式/可插拔图变换编译器；论文指出它不支持动态形状，且无法直接报告 T5 的结果，因为没有定义 T5LayerNorm 模块。
* **PyTorch eager mode**：用于子图消融比较的未优化基线。

### 6.4 评价指标

| 指标 | 含义 | 趋势 |
| --- | --- | --- |
| 端到端推理延迟 | 模型一次端到端推理的平均延迟；10 次执行、重复 3 次，先热身 10 次 | 越小越好 |
| Speedup | 相对比较方法的加速比 | 越大越好 |
| Fusion rate | 原始算子数与融合后层数之比 | 越大表示融合更充分 |
| 子图延迟 | 关键子图的 GPU 执行延迟 | 越小越好 |
| 编译时间/内存开销 | 编译阶段耗时与额外 CPU 内存 | 越小越好 |
| 输出绝对误差 | 优化路径与 PyTorch eager 输出的绝对差异 | 越小越好 |

## 7. 实验结果与结论

### 7.1 主要结果

在五个模型、batch size 1 和 16 的端到端推理实验中：

* 在 A100 上，PluS 相对 TorchInductor 平均加速 4.04×，相对 TensorRT 平均加速 1.77×。
* 在 RTX 4090 上，PluS 相对 TorchInductor 平均加速 4.59×，相对 TensorRT 平均加速 2.01×。
* 相对 AITemplate，PluS 在 A100 上平均性能高约 7.8%，在 RTX 4090 上高约 7.2%；AITemplate 无法支持 T5，因此该对比不是五个模型完全对称的比较。

这些数值来自论文第 6.2 节的端到端延迟实验。TensorRT 的 T5 出现异常长的 GPU-CPU 传输时间，论文使用 Nsight Systems 中的纯 kernel 执行时间作为该模型的端到端运行时间，因此该个案的口径与其他模型不同。

### 7.2 与传统方法的比较

表 1 给出五个模型的原始基础算子数和融合后的层数。PluS 的融合后层数分别为 BERT 87、ALBERT 88、GPT-2 87、T5 220、ViT 87；论文据此报告，相对 TorchInductor 的平均 fusion rate 提升为 2.08×，相对 TensorRT 为 1.25×。更大的可融合子图范围来自模式仓库和循环中心匹配，而不是仅依赖编译器内置规则。

### 7.3 与模板式方法的比较

PluS 与 AITemplate 在已有模型上表现接近，但 PluS 可以利用循环结构相同的模板处理 T5 的变体。论文给出的代码规模案例是：AITemplate 为支持含偏置变化的子图需要超过 250 行前后端代码；为 T5LayerNorm 需要 1701 行相关代码（453 行前端注册、1248 行后端实现）；PluS 对 T5LayerNorm 的模式需要 18 行 +Graph 定义和 129 行代码模板。

### 7.4 消融实验

关闭 CUTLASS、ByteTransformer 和 FlashAttention 等优化 kernel、改用通用实现时，在 10 个子图上，PluS 相对 PyTorch eager mode 平均加速：batch size 16 为 4.79×，batch size 1 为 13.27×。论文还展示了 S1/S6 注意力子图：PluS 将其实现为单个大 kernel，两个案例的执行时间分别为 0.015 ms 和 0.0077 ms。

### 7.5 编译开销与正确性案例

缓存模型时，PluS 编译开销为 18–25 秒，主要由 NVCC 编译占据；首次编译模型需要 1–2 分钟。额外 CPU 内存开销为 130–190 MB。随机标准正态输入下，优化输出与 PyTorch eager 输出的最大绝对差为 1.9e-3，平均绝对差为 3.57e-5。该实验是数值一致性检查，不是形式化证明。

## 8. 主要创新点

### 8.1 创新点一：可插拔图调度

论文提出把专家提供的子图优化和代码生成调度放入模式仓库，使新增优化不必修改编译器核心图变换模块。价值在于缩短高性能 kernel/子图接入路径；端到端性能和代码规模实验支持了这一设计的有效性。

### 8.2 创新点二：循环中心的 +Graph 抽象

与精确算子组合匹配不同，+Graph 保留循环大小、并行性、归约和关键操作等结构属性。这样，Add/Sub 等不会改变核心循环结构的变化可以复用已有调度。论文将该抽象与四类循环变换原语结合，用于逐步构造可匹配的子图。

### 8.3 创新点三：模式匹配与模板补全协同

PluS 不要求专家为每个完整算子图重新定义所有代码。专家提供关键循环骨架与 +Code 占位符，编译器根据数据依赖自动补齐数据访问、计算和写回。该机制使动态形状、多种算子变体和多来源 kernel 可以共存。

### 8.4 不应被误称为创新的内容

使用 GPU、CUDA、PyTorch、CUTLASS 或 FlashAttention 本身不是本文创新；这些是实现和实验依赖。论文的贡献在于编译器如何组织、匹配并复用这些高性能实现。

## 9. 局限性

### 9.1 论文明确承认或正文可直接确认的限制

* 当前实现基于 PyTorch/TorchDynamo，论文虽然讨论了对其他主流 DNN 框架的可支持性，但没有给出其他框架的完整实验。
* 实验平台是 NVIDIA A100 与 RTX 4090，未验证 AMD GPU、CPU、RISC-V 加速器或其他异构后端。
* PluS 依赖专家编写模式和代码模板；它降低了接入成本，但没有自动发现或自动生成所有高性能 kernel。
* TensorRT 的 T5 结果使用纯 kernel 时间替代异常的端到端传输时间，导致该项横向比较需要谨慎解读。
* AITemplate 不支持动态形状，且缺少 T5LayerNorm 实现，因此与 AITemplate 的模型覆盖范围不完全一致。

### 9.2 阅读后的潜在局限

* 循环中心特征能否充分表达复杂控制流、稀疏计算、跨算子别名和同步语义，论文没有系统评估。
* 数值正确性只通过随机输入的输出误差检查，未使用形式化等价验证；对浮点重排、边界形状和异常输入的覆盖有限。
* 模式仓库越大，匹配歧义、版本兼容和选择最优模板的维护成本可能越高；论文的贪心扩展策略不等于全局最优融合搜索。
* 论文主要报告延迟和编译开销，没有给出能耗、峰值显存、长期运行稳定性或跨 GPU 迁移成本的系统分析。

## 10. 阅读后的研究方向反思

1. 最值得借鉴的是“稳定的结构抽象 + 可替换后端模板”这一分层方式：它把模型图变化与底层调度复用分开，适合作为 MLIR/LLVM 多级 lowering 的设计参考。
2. 不能简单照搬的是 CUDA kernel 与 NVIDIA 库组合。将其直接替换为 RISC-V 或另一种 GPU 后端，只能证明移植性，不能自动形成新研究问题。
3. PluS 更适合作为编译器基础设施或代码生成模块，而不是 LLM 训练方法。若与 LLM 结合，LLM 可以提出 +Graph/+Code 候选，但候选仍需由编译器、测试或验证工具检查。
4. 对 RISC-V 的相关性是“方法层面中等、实验层面有限”：循环中心的模式可映射到 RVV 或自定义加速器，但论文没有提供 RISC-V 后端、RVV 指令选择或真实硬件测量。

## 11. 可进一步尝试的研究方向

### 11.1 面向 RVV 的循环中心子图代码生成

#### 研究问题

如何将 +Loop/+Graph 映射到 RISC-V Vector Extension（RVV）的向量长度无关代码，并处理尾部、mask、归约和动态 shape。

#### 与原论文的区别

不是把 CUDA 模板替换成 RVV 汇编，而是重新定义向量化、VL/VLMAX、mask 和内存布局约束下的模式匹配与调度复用。

#### 可能的创新点

RVV 特有的向量长度无关抽象、形状感知的模式选择、LLVM 后端合法性检查。

#### 实验框架

```text
DNN/张量图 → +Graph → RVV 约束匹配 → LLVM IR/向量 intrinsic → RVV 后端 → 仿真器或真实板卡
```

#### 可行性

需要 LLVM/RVV、MLIR 或现有张量编译器后端，以及 Spike/QEMU 或真实 RVV 硬件。

#### 主要风险

向量归约和内存布局可能使循环结构相似但硬件代价不同；模拟器时间不能替代真实硬件性能。

### 11.2 验证引导的可插拔图调度

#### 研究问题

如何在每次模式融合或模板替换后自动检查数值语义、边界形状和内存安全，而不是只依赖随机输出比较。

#### 与原论文的区别

增加编译期/运行期验证层，研究验证成本与调度搜索空间之间的平衡。

#### 可能的创新点

对 +Graph 的数据依赖生成验证条件；将局部等价验证、差分测试和数值误差界结合。

#### 实验框架

```text
+Graph 候选 → 代码生成 → 等价/数值/边界检查 → 通过后进入模式仓库 → 性能测量
```

#### 可行性

可从小型算子和 LLVM/MLIR 局部变换开始，逐步加入 GPU 或 RVV 后端。

#### 主要风险

浮点计算通常难以获得严格等价；验证可能抵消编译时间收益。

### 11.3 LLM 提议、编译器筛选的模式仓库维护

#### 研究问题

LLM 能否从新模型结构中提出 +Graph/+Code 草案，并通过编译器反馈自动过滤不可编译、低性能或不正确候选。

#### 与原论文的区别

原论文依赖专家定义模式；该方向研究 LLM 作为候选生成器，编译器和测试工具作为约束与评估器。

#### 可能的创新点

结构化输出协议、基于编译错误和性能反馈的迭代生成、模式去重与版本管理。

#### 实验框架

```text
新模型子图 → LLM 生成结构化模式 → 编译器/验证器 → 性能测试 → 接受、修复或拒绝
```

#### 可行性

需要模式 DSL、编译器 API、测试集和可复现实验硬件；不要求把 LLM 当作最终正确性来源。

#### 主要风险

LLM 可能产生语义不完整或性能投机的模板；候选验证和实际测量成本可能很高。

## 12. 与其他已读文献的关系

当前 batch-7/slot-2 只交付本篇论文，没有另一篇已通读论文可进行事实性横向比较。就研究位置而言，PluS 更接近 ML 编译器基础设施、图级优化与 GPU 代码生成；它可以作为后续 LLM 代码生成、验证引导优化或 RISC-V 后端研究的编译器承载层，但不能直接视为 LLM 优化、形式化验证或 RISC-V 论文。

| 项目 | 内容 |
| --- | --- |
| 论文研究任务 | 构建可扩展的 ML 编译器，支持可插拔子图调度 |
| 核心问题 | 嵌入式规则难扩展，精确模板匹配难复用 |
| 输入 | PyTorch 模型/torch.fx.GraphModule |
| 输出 | 融合后的 GPU 子图与 CUDA kernel |
| 核心方法 | +Loop/+Graph、模式仓库、贪心子图匹配、+Code 模板 |
| 使用的模型 | BERT-base、ALBERT、GPT-2、T5、ViT |
| 使用的编译器工具 | PyTorch、TorchDynamo、Hidet、NVCC、CUTLASS 等 |
| 是否使用强化学习 | 否 |
| 是否使用形式化验证 | 否；使用随机输入的数值差异检查 |
| 数据集规模 | 不适用；五个 DNN 工作负载 |
| 主要指标 | 端到端延迟、speedup、fusion rate、编译时间、内存、输出误差 |
| 最重要实验结果 | A100 上相对 TorchInductor 4.04×、TensorRT 1.77×平均加速；相对 AITemplate 平均约 7.8%提升 |
| 核心创新 | 用循环中心结构抽象实现可复用的可插拔图调度 |
| 主要局限 | 依赖专家模式和 NVIDIA GPU；无形式化验证和 RISC-V 实验 |
| 与 RISC-V 研究的相关性 | 中；抽象可迁移，但论文未实现 RVV/其他 RISC-V 后端 |
| 最适合作为 | ML 编译器基础设施、代码生成模块和后续验证/LLM 研究的 baseline |

这篇论文最值得学习的是把子图识别的稳定结构与后端调度模板解耦，从而降低模型变体和新 kernel 接入的重复工作；最主要的局限是实验集中于 PyTorch 与 NVIDIA GPU，正确性只做了随机数值检查。如果用于后续研究，合理方式是把 PluS 的循环中心抽象作为编译器模块，再研究 RVV 后端、验证机制或 LLM 候选生成，而不是简单把 CUDA 模板替换成另一种硬件代码。
