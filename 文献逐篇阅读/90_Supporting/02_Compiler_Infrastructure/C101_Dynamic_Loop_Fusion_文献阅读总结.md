## 1. 研究背景

高层次综合（High-Level Synthesis，HLS）把较高层次的程序描述转换为 FPGA 上的硬件实现。对规则代码，静态编译器可以发现指令级和内存级并行性；但图分析、稀疏线性代数等不规则代码存在数据相关地址和不可预测控制流，静态调度难以安全地跨循环并行化（第 1 节）。

动态 HLS 使用额外硬件在运行时做内存消歧，可以处理单个循环中的不规则依赖；然而现有方案遇到跨兄弟循环的共享依赖时，通常要先让一个循环完成，因而丢失细粒度并行性。静态循环融合又要求地址表达式满足较强的仿射/依赖距离条件。论文的动机是：在不要求完整地址历史、也不牺牲顺序一致性的前提下，让具有可分析地址单调性的多个循环并行执行。

## 2. 论文要解决的问题

### 2.1 跨循环依赖导致的串行化

当两个循环存在 RAW（读后写）、WAR（写后读）或 WAW（写后写）依赖时，现有动态 HLS 的 load-store queue（LSQ，加载/存储队列）往往串行化循环。论文要判断某个新的内存请求是否安全，而不是等待另一个循环的全部地址历史产生。

### 2.2 非仿射和数据依赖地址

静态循环融合对非仿射地址通常无法证明合法。论文希望利用比仿射更宽松的“内层循环地址单调不减”条件，支持包括数据依赖地址在内的一部分不规则代码；对于无法由编译器推导的稀疏格式，允许程序员声明单调性。

### 2.3 硬件代价与调度表达

若直接保存完整多维迭代点或搜索地址历史，硬件代价较高。论文需要一个可在硬件中比较的程序序表示、可裁剪的依赖检查逻辑，以及对 DRAM 突发合并和 store-to-load forwarding（存储到加载转发）的支持。

最后概括：本文主要研究如何在内层地址单调的约束下，通过编译器分析、程序序调度和参数化数据单元，让 FPGA HLS 中存在跨循环内存依赖的多个循环动态并行执行。

## 3. 核心方法概述

论文提出 dynamic loop fusion：编译器把循环森林分解为多个独立的 processing element（PE，处理单元），每个 PE 再解耦为 address generation unit（AGU，地址生成单元）和 compute unit（CU，计算单元）；专用 data unit（DU，数据单元）在运行时完成跨循环内存消歧。

```text
输入 HLS 程序/LLVM IR
        ↓
循环森林分析：单调性、拓扑序、依赖对
        ↓
编译器 pass：循环解耦为 PE，并拆成 AGU/CU
        ↓
按依赖图参数化 DU 与 hazard checks
        ↓
Intel HLS 生成硬件并部署到 FPGA
        ↓
DU 运行时进行程序序比较、地址安全检查、突发合并和转发
        ↓
输出保持顺序一致性的并行 HLS 实现
```

地址分析基于 Chain of Recurrences（递归链，表达循环中值/地址如何随迭代变化）和 LLVM/GCC 的 Scalar Evolution（SCEV）思想。论文要求依赖源的内层循环地址单调不减；外层循环可以非单调，系统用 `lastIter` 信息处理地址重置。DU 使用请求/确认中的地址和程序序信息进行 RAW/WAR/WAW 检查，并可在待提交存储缓冲区中查找并直接转发值。

按照 taxonomy v2 的角色规则，建议候选分类为 `GENERATOR / G1_Compiler_Pass_Generation`：论文产出可复用的 HLS 编译器 pass、分析与参数化 DU 组件，而不是模型选择配置或直接生成某个应用程序。该分类仅为 staging 建议，不分配 Paper_ID。

## 4. 实验框架与训练流程

### 4.1 编译器执行流程

本文不涉及模型训练、SFT、强化学习或提示词推理，主要采用静态编译分析与硬件生成流程：

1. 输入 LLVM IR；
2. 分析循环单调性、拓扑顺序和内存依赖对；
3. 运行 transformation pass，将循环森林转换为 DAE 风格的 PE/AGU/CU；
4. 根据 load/store 数量及依赖对参数化 DU；
5. 用 Intel HLS 工具生成硬件并在 FPGA 上运行。

### 4.2 运行时流程

AGU 提前产生地址和 schedule；DU 保存请求/确认地址、schedule 和待提交值。请求满足程序序安全条件且不存在可能的地址重置时才继续；动态 LSU 合并不规则访问形成的突发请求。对 RAW 依赖，待存储缓冲区命中时可以直接转发；条件分支中的内存请求采用推测发送，CU 用 valid bit 取消错误推测的存储。

### 4.3 训练、工具反馈和验证边界

本文没有训练模型，也没有奖励函数或损失函数。论文通过编译器静态条件和硬件运行时 hazard check 保持依赖顺序，但没有把该机制表述为形式化验证证明；其“正确性”依赖提出的检查逻辑和实验实现。

## 5. 奖励函数、损失函数或关键公式

本文没有使用强化学习，因此不存在强化学习奖励函数。关键目标是运行时内存安全检查，而不是可训练目标。

### 5.1 地址单调性

论文把循环表达式表示为：

```text
CR = {base, operator, step}
```

其中 `base` 和 `step` 可以继续是递归链，`operator` 可为 `+`、`×` 或 `÷`。在地址分析中，递归链的步长非负时视为单调不减。论文指出，单调递归链比仿射递归链更一般；例如 FFT 访问可以是单调但非仿射。

### 5.2 Hazard Safety Check

论文将安全条件写成概念上的组合：

```text
HazardSafety = ProgramOrderSafety
               OR (req.address_a < ack.address_b AND NoAddressReset)
```

`ProgramOrderSafety` 比较共享循环深度上的请求/确认 schedule；`NoAddressReset` 保证依赖源地址在相关 schedule 区间内没有因非单调外层循环而重置。若两个操作不共享循环，检查可简化为地址比较；共享循环时最多增加程序序比较和地址重置检查。论文还利用依赖传递性裁剪 hazard pairs；FFT 示例从 44 对裁到 10 对。

### 5.3 Store-to-load forwarding

RAW 检查使用下一个 store 请求和待存储缓冲区的关联查找；若地址命中，加载可直接消费最新的待提交值而无需等待 DRAM。该机制是硬件优化，不是奖励或损失。

## 6. 实验设置

### 6.1 数据集来源

论文使用 10 个来自动态 HLS 研究的规则/不规则代码基准，挑选存在跨兄弟循环并行机会的程序；有些基准通过外层循环展开或组合多个 kernel 来暴露融合机会。数据集不是训练集/验证集/测试集划分，论文中未提供机器学习意义上的数据泄漏分析。

主要基准与参数包括：

| 基准 | 内容与规模 |
| --- | --- |
| RAWloop/WARloop/WAWloop | 两个循环分别形成 RAW/WAR/WAW 跨循环依赖，`n=10,000,000` |
| bnn | 稀疏二值神经网络一层，`n=10,000`，数据依赖访问由程序员声明单调 |
| pagerank | CSR 图，web-NotreDame 图，10 次迭代、325,729 节点、1,497,134 边 |
| fft | 中间循环展开 2 倍，`n=1,048,576` |
| matpower | CSR 稀疏矩阵幂，外层循环展开 2 倍，`nz=4,096` |
| hist+add | 两个直方图相加，`n=10,000,000` |
| tanh+spmv | tanh 后接 COO 稀疏矩阵向量乘，`n=10,000`、`nz≈10,000` |

论文正文将表格列为 9 行基准组合，其中 RAW/WAR/WAW 是三个独立微基准；正文称总数为 10 个不规则代码。这里不把微基准行数误写成数据集规模。

### 6.2 模型与工具

没有基础模型、参数规模或训练框架。实现集成在 Intel HLS compiler 中，编译器中间表示为 LLVM IR；使用 Altera Arria 10 GX1150 FPGA 板卡，两块 DDR4，内存控制器使用两个 512-bit 通道；面积和频率来自 Quartus 19.2 place-and-route 报告。每个代码执行三次，报告最小时间；面积指标为 Adaptive Logic Modules（ALMs）。论文说明实现和评估公开可得，但本 staging 只保存核验后的论文 PDF。

### 6.3 对比方法

| 方法 | 含义 |
| --- | --- |
| STA | Intel HLS 的自动静态循环融合基线，使用相同的动态突发合并 LSU |
| LSQ | 在 Intel HLS 中实现的动态调度，使用 LSQ 处理内存访问，但不支持动态合并 |
| FUS1 | 本文 dynamic loop fusion，不启用 store-to-load forwarding |
| FUS2 | FUS1 加上 store-to-load forwarding |

### 6.4 评价指标

| 指标 | 含义 | 方向 |
| --- | --- | --- |
| Time | FPGA 实测执行时间，秒；每个代码三次取最小值 | 越小越好 |
| Speedup | 相对于指定 baseline 的执行时间加速比 | 越大越好 |
| ALMs | place-and-route 后的自适应逻辑模块数 | 通常越小越好 |
| Frequency | 实现电路频率，MHz | 越大越好 |
| DSP/BRAM | 资源是否增加 | 越少增加越好 |

## 7. 实验结果与结论

### 7.1 主要结果

在十个不规则代码的总体汇总中，FUS2 平均比 STA 快约 14×，比使用 LSQ 的动态 HLS 快约 4×。表 1 的调和平均时间归一化为 STA=1、LSQ=0.12、FUS1=0.10、FUS2=0.07；这是相对时间汇总，不是单个程序的绝对秒数。

代表性结果（均为表 1 中 Altera Arria 10 GX1150 实测时间）：FUS2 在 `fft` 上为 1.7 s，相比 STA 的 7.8 s 和 LSQ 的 7.8 s；在 `matpower` 上为 1.6 s，相比 STA 的 18 s 和 LSQ 的 3.7 s；在 `hist+add` 上为 0.2 s，相比 STA 的 3.9 s 和 LSQ 的 1.0 s；在 `tanh+spmv` 上为 0.5 s，相比 STA 的 4.4 s 和 LSQ 的 0.9 s。

### 7.2 与传统方法的比较

RAW/WAR/WAW 微基准的理论上限为 2×，FUS2 实际约 1.7×，差距主要来自 FUS2 较低的电路频率。LSQ 在 RAW/WAR 上可能慢于 STA，因为其非突发 LSU 为避免 hazard 违反而使加载循环停顿。论文的优势来自跨循环并行执行，而不是所有代码都适合融合。

### 7.3 与其他 LLM 方法的比较

本文不比较 LLM，也没有 LLM 组件。将其与 LLM 代码生成或 HLS agent 直接横向比较会改变论文问题定义。

### 7.4 消融实验

FUS1 与 FUS2 的对比考察 store-to-load forwarding。跨循环 forwarding 在该实验设置下通常没有可观察收益；同一循环中的 RAW 依赖中，forwarding 很关键。论文还比较依赖对裁剪：FFT 中未裁剪的 FUS2 比裁剪版本面积多 32%、频率低 28%。

### 7.5 案例分析

动态融合对计算复杂度相近的循环更有效。pagerank 中存在一个主导运行时间的 O(n²) 边循环，因此相对 LSQ 只有约 1.1×；论文使用 web-Google 图时给出 875,713 个节点和 5,105,039 条边，理论上限约为 1.3×。FFT、matpower 受益于不必担心不规则依赖破坏而进行外层展开；hist+add、tanh+spmv 体现了细粒度任务融合。

## 8. 主要创新点

### 8.1 创新点一：跨循环动态内存消歧

现有动态 HLS 主要在单循环内处理依赖，跨循环则串行化。本文在内层地址单调条件下，用最新地址和程序序信息替代完整地址历史，使共享依赖的兄弟循环可以并行运行。十个不规则代码上的速度结果支持其有效性。

### 8.2 创新点二：面向硬件的程序序表示

论文不是直接复用完整多维 polyhedral schedule，而是每个循环深度使用一个元素、按循环体调用递增，并只比较最内层共享循环深度。编译器依据内存操作拓扑序配置比较符，从而在较短 schedule 中恢复所需程序序。

### 8.3 创新点三：编译器参数化的 DU

DU 根据 load/store 数量、依赖图、单调性和拓扑序专门化；同时支持动态突发合并、store-to-load forwarding 和 hazard pair 裁剪。它把中端分析结果直接转化为可部署的硬件逻辑，而不只是选择一个既有 HLS pragma。

## 9. 局限性

### 9.1 论文明确承认的局限

* 当前实现不能处理 vendor 后端闭源部分实现的自动 loop-unroll pragma，需要手工展开；论文因此没有系统研究自动展开。
* 研究聚焦 DRAM streaming 应用，pending buffer 为保证关联搜索可行而必须较小，片上数据复用受限。
* 当前实现对条件中的内存操作采用整循环推测，未来可研究不必执行全部迭代的推测方案。
* 论文提出 BRAM cache、MSHR 和多端口仲裁作为未来扩展，当前不是完整的 BRAM/cache 方案。
* 单调性检查使用符号的最大值进行保守判断，可能产生 false positive；论文实验中未观察到，但运行时精确检查留作未来工作。

### 9.2 阅读后发现的潜在局限

* 实验依赖 Intel HLS/Quartus 和 Arria 10，迁移到 AMD/Xilinx HLS 或其他 FPGA 的编译器接口与内存 IP 需要额外验证。
* 运行时 hazard 逻辑保证的是特定假设下的顺序安全，论文没有给出独立形式化证明；不能把它写成形式化验证通过。
* 24% 平均面积增加、9% 频率下降（相对 STA）说明吞吐收益存在硬件代价；排除 OpenCL kernel runtime 和 DRAM interconnect 后，RAWloop 的局部 area overhead 可达 2.1×。
* 结果是特定基准和大内存输入上的硬件测量，不能直接外推到所有不规则程序或所有 FPGA 架构。

## 10. 阅读后的研究方向反思

本文最值得借鉴的是“静态分析负责缩小安全条件，运行时硬件只检查必要信息”的软硬件协同边界。对于 LLVM/MLIR 研究，它提供了一个清晰的中端分析—后端参数化接口案例；对于 RISC-V，相关性是中等偏低，因为论文目标是 FPGA HLS 数据流与 DRAM 消歧，而不是 RISC-V 指令集。但其依赖对裁剪、程序序编码和硬件反馈思想可以作为异构编译器的参考。

不能简单照搬的部分包括：把 FPGA 换成 RISC-V 并不会自动形成新贡献；Arria 10 的 DDR/LSU 代价模型、LLVM IR pass 接口和 HLS 后端均需重新建立。该工作更适合作为 GENERATOR 角色的编译器 pass/硬件组件 baseline，而不是 LLM 训练方法或 RISC-V 代码生成框架。

## 11. 可进一步尝试的研究方向

### 11.1 MLIR 可验证的动态循环融合方言

#### 研究问题

如何把循环单调性、依赖对、schedule 和 DU 参数建模为 MLIR dialect，并在 lowering 过程中检查约束。

#### 与原论文的区别

不只是重写 LLVM pass；重点是跨方言合法性、可组合 lowering 和可诊断的约束失败。

#### 可能的创新点

把单调性证明条件与硬件资源估计绑定，生成可审计的 lowering artifact。

#### 实验框架

```text
HLS/MLIR 输入 → 单调性与依赖分析 → 融合候选/约束 IR
             → DU 参数生成 → 多 FPGA 后端 lowering → 实测性能与资源
```

#### 可行性

需要 MLIR、LLVM Scalar Evolution 或等价分析、至少一个开放/可用 HLS 后端和 FPGA 仿真或实测平台。

#### 主要风险

不同 vendor 后端的闭源优化会削弱可移植性；形式化证明与真实硬件结果可能不一致。

### 11.2 面向 RISC-V 向量/加速器的依赖安全调度

#### 研究问题

能否把跨循环地址单调性用于 RVV 或可编程加速器的数据流调度，而不是生成 FPGA DU。

#### 与原论文的区别

目标从 FPGA DRAM LSU 变为 RISC-V 向量内存操作、scratchpad 或协处理器接口，并研究 ISA 可见的调度代价。

#### 可能的创新点

设计能感知向量长度、内存一致性和 scratchpad bank 冲突的依赖检查/调度模型。

#### 实验框架

```text
LLVM/RVV IR → 地址与依赖分析 → RVV/协处理器调度候选
            → Spike/QEMU/RTL → 周期、带宽、代码尺寸与正确性评估
```

#### 可行性

需要 LLVM RVV、模拟器或 FPGA 上的 RISC-V 原型；不应把 FPGA 论文结果直接当作 RVV 结果。

#### 主要风险

内存一致性和向量访存语义比本文假设更复杂；周期模型可能不能代表真实系统。

### 11.3 成本感知的 forwarding/缓存选择

#### 研究问题

何时跨循环转发值得付出关联搜索和面积，何时应切换 BRAM cache 或不启用 forwarding。

#### 与原论文的区别

原论文主要展示机制和固定配置；新方向把组件选择变成硬件感知的多目标决策问题。

#### 可能的创新点

构建结合带宽、pending buffer、面积、频率和循环复杂度的选择器，并校准实测硬件反馈。

#### 实验框架

```text
依赖图/循环特征 → 成本模型 → forwarding/cache/无转发配置
                → HLS 实现 → 性能-面积-频率 Pareto 分析
```

#### 可行性

可以从本文的 FUS1/FUS2 和 benchmark 开始，逐步加入 BRAM cache 与多 FPGA 目标。

#### 主要风险

成本模型容易对单一板卡过拟合；需要明确区分估计指标和真实硬件时间。

## 13. 一页式总结

| 项目 | 内容 |
| --- | --- |
| 论文研究任务 | 不规则 FPGA HLS 的跨循环动态融合与内存消歧 |
| 核心问题 | 现有动态 HLS 因跨循环依赖而串行化，静态融合又难处理非仿射地址 |
| 输入 | HLS 程序/LLVM IR、循环森林和内存依赖 |
| 输出 | PE/AGU/CU、参数化 DU 与可部署 FPGA HLS 实现 |
| 核心方法 | 地址单调性分析、硬件程序序 schedule、动态 hazard check、转发 |
| 使用的模型 | 无机器学习模型；传统编译器分析与硬件生成 |
| 使用的编译器工具 | Intel HLS compiler、LLVM IR、Quartus 19.2 |
| 是否使用强化学习 | 否 |
| 是否使用形式化验证 | 否；有静态条件和运行时安全检查，但非形式化证明 |
| 数据集规模 | 10 个不规则代码/基准组合；参数见第 6 节 |
| 主要指标 | FPGA 实测时间、speedup、ALMs、频率、DSP/BRAM |
| 最重要实验结果 | 平均比 STA 快 14×、比 LSQ 动态 HLS 快 4×；平均面积增加 24%、频率下降 9% |
| 核心创新 | 用单调地址和紧凑程序序表示支持跨循环动态内存消歧 |

| 最适合作为 | HLS 编译器 pass/硬件协同设计 baseline 与方法参考 |

这篇论文最值得学习的是把 LLVM 中端的循环/依赖分析转化为专用硬件的最小运行时检查；最主要的局限是单调性、DRAM streaming 和特定 vendor 工具链假设。如果用于后续研究，合理方式是复用其分析—硬件参数化边界并重新验证成本模型，而不是简单把 FPGA 名称替换成 RISC-V 或把有限测试结果写成普适保证。
