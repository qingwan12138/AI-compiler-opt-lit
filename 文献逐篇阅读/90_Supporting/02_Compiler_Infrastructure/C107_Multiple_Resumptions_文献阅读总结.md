## 1. 研究背景

本文研究函数式语言中的效果处理器（effect handler）实现。效果处理器把程序对外部上下文的影响，例如异常、生成器、回溯或异步操作，与这些影响的具体实现分离。程序执行效果操作时，会把处理器以内的剩余计算捕获为 continuation（续体），处理器可以不恢复、恢复一次，或多次恢复该续体。

多次恢复适合回溯搜索、概率编程和解析等场景，但它与高效的栈切换及栈分配的可变引用存在冲突：续体本质上包含运行时栈；若同一个续体被恢复多次，第一次恢复期间对栈上可变状态的写入不应错误地泄漏到后续恢复。已有实现通常通过防御性复制或保存/恢复状态解决，带来额外成本；而只支持一次恢复的实现牺牲了表达能力。

作者特别关注 lexical effect handler（词法效果处理器）：效果操作使用的处理器由词法作用域决定。Lexical handler 可以通过直接访问对应栈段来避免逐个搜索处理器，但栈复制会使普通栈指针失效。因此论文要在多次恢复、局部可变状态和常数时间的常见路径之间取得平衡。

## 2. 论文要解决的问题

### 2.1 多次恢复与栈上可变状态的兼容

论文要实现同时支持 multi-shot continuation（可多次恢复的续体）和 stack-allocated mutable reference（栈分配的局部可变引用），并保证两者的语义交互正确。这里的“正确”来自论文给出的 MCode 抽象机器和编译到 ASM 的运行时语义，而不是只做语法层面的转换。

### 2.2 常见 one-shot 路径的效率

很多效果处理器实际上只会恢复续体一次，例如异步等待或尾部恢复。论文希望在能够判断续体唯一拥有时避免复制，使捕获和恢复保持常数时间；只有共享续体确实需要再次使用时才复制。

### 2.3 深层嵌套处理器的可扩展性

作者还要解决既有 Effekt JavaScript 后端中随嵌套处理器数量增加而出现的非线性处理器查找开销。目标是直接定位词法处理器对应的栈段，而不是在线性链表上逐个查找。

> 本文主要研究：如何通过稳定 prompt、引用计数和栈段运行时系统，把支持 multi-shot continuation 与局部可变状态的词法效果处理器编译为高效的 LLVM 后端。

## 3. 核心方法概述

核心设计包含三点。第一，prompt（提示对象）地址保持稳定，prompt 内部指向当前有效栈段；栈复制时只更新 prompt 指针，外部持有的 prompt 地址不变。第二，使用无垃圾引用计数判断续体是否仍由多个引用共享；若当前恢复是最后一次或唯一一次，则直接恢复，否则复制续体。第三，把引用表示为“prompt + 栈内偏移”，从 prompt 找到当前栈，再按偏移访问状态，因此可支持栈重分配和续体复制。

```text
Effekt 源程序
        ↓
共享中间表示及高层优化
        ↓
接近 MCode 的中间语言
        ↓
编译为 LLVM IR
        ↓
LLVM IR 运行时系统管理 meta stack、prompt、续体和引用计数
        ↓
LLVM 优化并生成可执行代码
        ↓
效果处理器 benchmark 与对比实现测试
```

输入是带词法效果处理器、代数数据类型、可变数据结构等特性的 Effekt 程序。输出是 LLVM IR 及其运行时支持。编译器在共享中间表示阶段已有若干高层优化，例如消除尾部恢复处理器中的续体捕获；本文新增后端按照 MCode 到 ASM 的思路生成 LLVM IR。论文还形式化了一个无类型的 MCode 和理想化 ASM，以解释 `reset`、`shift`、`resume`、`ref`、`get`、`set` 的语义。

续体恢复的关键路径是：检查续体是否唯一且有效；若是，直接把 meta stack 指针切换到续体；若不是，深复制续体各栈段，再使复制品重新有效。局部引用通过 prompt 与 offset 间接定位，读写各需常数数量的内存访问。

## 4. 实验框架与训练流程

### 4.1 编译器和运行时实现阶段

本文不涉及模型训练、SFT、强化学习或提示词推理，主要采用静态编译器和运行时系统实现流程：

1. 在已有 Effekt 编译器中加入新的 LLVM 后端。
2. 将共享中间表示降低到接近 MCode 的形式。
3. 将 MCode 风格的控制操作编译到 LLVM IR。
4. 直接用 LLVM IR 编写管理 meta stack 的运行时系统。
5. 让 LLVM 同时编译生成代码和运行时，以便继续做 LLVM 优化。

### 4.2 运行时执行阶段

`reset` 创建 prompt 与新栈段；`shift` 在 prompt 处切下当前栈段形成续体；`resume` 把续体重新接入 meta stack。若续体不是唯一引用，则执行深复制和 revalidate（重新验证 prompt 指针）；若恢复完成后栈段被释放，则通过引用计数和 eraser 函数回收相关值。

### 4.3 实验阶段

作者用新 Effekt 实现（版本 0.22.0）对比 Effekt MLton、Lexa、OCaml、Koka 和 Eff。测试使用效果处理器社区 benchmark suite，并增加需要多次恢复和局部可变状态的 Checkpointing 案例。每项实验至少运行 10 次，报告中位数；硬件为 16 核 AMD Ryzen 7 PRO 7840U、64 GB 内存。

## 5. 奖励函数、损失函数或关键公式

本文没有使用强化学习，因此不存在强化学习奖励函数，也没有神经网络损失函数。关键目标是运行时复杂度与语义不变性。

### 5.1 续体表示与唯一性检查

论文将续体表示为由栈段构成的循环链表，续体句柄指向最后一个栈段。每个栈段关联一个稳定 prompt；当 prompt 指回自身时，栈段有效。恢复前用 `unique` 检查续体是否唯一拥有：

```text
若续体唯一且有效：直接 resume，避免复制
否则：copy(continuation) → revalidate(copy) → resume(copy)
```

形式化 ASM 中的 `unique r` 根据某个指针是否仍被其他寄存器或堆对象引用返回布尔值。它不是奖励，而是运行时分支条件。

### 5.2 局部引用访问

局部引用由 prompt `rp` 和栈偏移 `ro` 表示：

```text
get r：k = load rp[0]; x = load k[ro]
set r y：k = load rp[0]; store y k[ro]
```

论文称这两种访问在抽象目标机上都是常数时间，但 prompt 间接层会带来额外运行时开销。本文没有把常数时间声明解释为所有真实硬件上固定的指令数或固定延迟。

### 5.3 复制和回收成本

唯一恢复是常数时间路径；共享续体需要遍历并复制其栈段，因而与续体大小相关。引用计数保持最新状态，但丢弃续体（例如异常）需要遍历续体释放引用，因此是线性成本。栈增长通过倍增重分配摊销为常数时间，但单次扩容仍需复制。

## 7. 实验结果与结论

### 7.1 主要结果

新 Effekt LLVM 后端在社区 benchmark 上总体表现良好。排除 Countdown 后，作者报告其几何平均性能相对于 OCaml 快约 2.2 倍、相对于 Eff 快约 3.2 倍、相对于 Koka 快约 10.2 倍。与 Effekt MLton 和 Lexa 相比，新后端仍具有竞争力，但 MLton 约快 1.25 倍、Lexa 约快 1.29 倍。上述数字是论文给出的 benchmark 几何平均相对结果，不是单个程序的硬件加速比。

### 7.2 与传统实现的比较

新实现对于动态效果处理器实现表现尤其好。Lexa 和 OCaml 不能运行需要多次恢复的 Checkpointing，Eff 在该测试上遇到编译器内部错误；这体现了论文实现的表达能力优势，但不能把“未运行”当成性能落后或领先。

Countdown 主要在编译期被求值，因此是几何平均中的明显异常值；Iterator、Parsing 和 Handler Sieve 受益于尾部恢复优化及局部可变引用的快速访问。Product Early 表现较差，作者认为原因是异常路径需要线性擦除续体。

### 7.3 与其他 LLVM/编译器后端方法的比较

论文没有比较不同神经模型，也没有和 GCC 或其他通用 LLVM pass 选择器比较。Fibonacci 上新后端不如部分实现，作者推测自定义调用约定和栈管理未被 LLVM 充分优化；这是论文对结果的解释，不是单独证明的因果结论。

### 7.4 消融和开销实验

作者把 prompt 间接引用改成直接指针，得到一个不支持多次恢复的对照实现。完整 benchmark 中两者性能差异低于 2%，因为 LLVM 优化会移除很多内存操作；关闭优化后两者也近似，其他计算成本掩盖了内存访问差异。

在手工转换到 LLVM IR 的紧循环中，作者用 volatile 防止状态访问被消除。图 16 报告：相对直接引用，间接引用在未优化代码中约为 1.2 倍开销，在优化代码中约为 1.9 倍；作者将约 2 倍视为这一设计的最坏情况量级，而不是所有应用的普遍慢化。

### 7.5 嵌套处理器扩展性

图 17 使用不断增加嵌套处理器、且 Tick 处理器位于最底层的测试。作者报告新的 LLVM 后端消除了既有 Effekt JavaScript 后端由于线性处理器搜索导致的非线性扩展问题。图中没有在正文中给出一张可直接抄录的统一数值表，因此具体曲线数值当前 PDF 内容不足以确认；结论依据图示和文字说明。

## 8. 主要创新点

### 8.1 稳定 prompt 解决栈复制后的指针失效

普通直接栈指针在复制栈段后会失效。本文让 prompt 地址稳定，prompt 只保存当前栈段指针；复制栈段时更新 prompt，而使用 prompt 的外部引用保持不变。该机制是同时支持栈分配引用和 multi-shot continuation 的核心。

### 8.2 引用计数选择性复制续体

本文不是每次捕获或恢复都防御性复制，而是根据无垃圾引用计数判断续体是否共享。唯一恢复沿常数时间路径执行，共享恢复才进行复制。这把多次恢复的表达能力与 one-shot 常见路径的效率结合起来。

### 8.3 形式化 MCode 到 ASM 的编译与运行时

作者给出了包含多 prompt 控制和局部可变状态的 MCode，并形式化了到抽象 ASM 指令集的编译。形式化明确说明了 meta stack、prompt、栈段、引用偏移、复制、失效和重新验证之间的关系，超出只描述一个工程后端的实现报告。

### 8.4 完整 LLVM Effekt 后端

论文实现了一个功能完整的新 Effekt LLVM 后端，成功编译约 10k 行标准库和约 10k 行测试代码，并支持一系列实际语言特性。真正的贡献是把上述运行时设计落到可执行编译器系统并与其他效果处理器实现比较，而不是单纯“使用 LLVM”。

## 9. 局限性

### 9.1 论文明确承认的局限

最重要的限制是 continuation 不可 reentrant（不可重入）：同一个续体不能在其另一个副本仍运行时再次恢复。实现会在运行时检测到这种情形并终止程序。论文给出的触发来源包括一等函数、双向效果以及潜在的并行执行。

局部引用的 prompt 间接层会增加常数开销；紧循环微基准中最坏约为两倍量级。引用计数还使异常等丢弃续体的路径需要线性遍历。论文的性能测试集中在效果处理器 benchmark 和给定 CPU，不能直接推出其他语言、架构或真实生产负载上的结果。

### 9.2 阅读后发现的潜在局限

1. 论文把 reentrancy 的安全性主要留给运行时错误；若用户通过库间接使用效果处理器，错误可能难以定位。
2. 论文讨论了可能通过类型系统静态排除重入，但没有实现这一方案，因此当前系统仍依赖动态检测。
3. LLVM 能否优化自定义调用约定和栈管理会显著影响结果；Fibonacci 的结果已暴露该后端相关性。
4. 实验没有覆盖 RISC-V、GPU 或异构硬件，不能把 LLVM 后端结果直接当作这些平台上的代码生成证据。
5. 论文比较的是效果处理器语言实现，不能直接说明该运行时设计适用于通用 C/C++ 编译器或任意 LLVM IR 程序。

## 10. 阅读后的研究方向反思

本文对“大语言模型与编译器优化、LLVM IR、RISC-V、多架构优化”的直接相关性为中等偏低：它是扎实的 LLVM 代码生成和运行时设计参考，但不是 LLM 优化论文，也没有 RISC-V 实验。

值得借鉴的是“语义不变性约束 + 编译器/运行时反馈”的设计思想。对 LLM 编译器工作而言，模型如果生成续体、栈操作或 LLVM IR 变换候选，必须由形式化语义、类型/效果系统或可执行验证器检查；仅通过测试通过不能替代语义正确性。

不应直接照搬的部分包括：把 LLVM 后端替换为 RISC-V 后端本身不构成充分创新；把 prompt 设计简单改名为 RISC-V 地址设计也不能证明新贡献。更合理的研究定位是：把本文作为运行时/代码生成 baseline，或把其 MCode/ASM 形式化作为验证接口，再研究多架构下的 continuation lowering、栈布局和验证成本。

## 11. 可进一步尝试的研究方向

### 11.1 面向 RISC-V 的可验证 continuation lowering

#### 研究问题

如何把 stable prompt、meta stack 和 selective continuation copying 编译到 RISC-V，并证明关键操作保持源语言语义。

#### 与原论文的区别

不是只把 LLVM 目标换成 RISC-V，而是研究 RISC-V 调用约定、寄存器保存规则、栈增长和异常路径如何影响验证与性能。

#### 可能的创新点

设计 RISC-V 特定的栈段布局和 ABI 适配；为 `shift/resume` 与 prompt 指针建立 ISA 层翻译验证条件。

#### 实验框架

```text
Effekt/MCode → RISC-V lowering → Spike/QEMU/真实板卡
                         ↓
             语义验证 + benchmark + 栈/复制开销测量
```

#### 可行性

需要 LLVM RISC-V 后端、RISC-V 模拟器或开发板、效果处理器 benchmark，以及 Alive2 之外适合控制流/运行时的验证工具。

#### 主要风险

动态栈和非重入约束可能超出已有验证器能力；模拟器时间不能直接代表真实硬件性能。

### 11.2 LLM 辅助的 MCode/LLVM IR 优化并带语义守门

#### 研究问题

LLM 能否提出尾部恢复、栈访问或引用定位优化候选，同时由形式化规则拒绝破坏 multi-shot 语义的候选。

#### 与原论文的区别

原论文的优化是编译器工程与手工设计；新方向引入 LLM 作为候选生成器，但不让 LLM 单独决定正确性。

#### 可能的创新点

建立以 MCode 操作语义、引用生命周期和 reentrancy 条件为约束的候选生成/验证循环。

#### 实验框架

```text
MCode/LLVM IR + 约束 → LLM 生成候选
                    ↓
          语义等价/类型效果检查
                    ↓
          LLVM 编译与 benchmark 测量
                    ↓
          保留正确且更快的候选
```

#### 可行性

可先使用本文已明确的尾部恢复、直接/间接引用和异常清理路径作为候选族；需要可执行测试与形式化/符号检查。

#### 主要风险

测试不足会把有限测试误写成语义等价；LLM 可能提出违反 prompt 生命周期或非重入不变量的代码。

### 11.3 多架构 continuation runtime 的成本模型

#### 研究问题

如何预测 stable prompt 间接、栈复制、引用计数和异常擦除在 x86-64、RISC-V 与 WebAssembly 上的成本。

#### 与原论文的区别

原论文主要在单一 AMD CPU 上评估；新方向研究跨 ISA 代价及代码生成决策。

#### 可能的创新点

构建同时考虑栈段大小、分支、内存层级和 ABI 的运行时成本模型，并用真实测量校准。

#### 实验框架

```text
相同 MCode → 各目标后端 → 模拟器与真实硬件
                         ↓
                 成本模型拟合/误差分析
```

#### 可行性

使用本文 benchmark、LLVM 多目标后端和少量真实 RISC-V 硬件即可开始。

#### 主要风险

不同后端优化器对调用约定和栈管理的处理差异很大；需要严格区分静态估计、模拟器结果和真实硬件时间。
