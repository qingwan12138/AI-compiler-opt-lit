## 1. 研究背景

AI 编译器把 PyTorch、TensorFlow、JAX 等高层张量程序降低为 GPU 上执行的低层代码。问题在于 GPU 指令和厂商手工优化内核更新很快；同一个数学操作可能有多种图形写法，并且高性能内核通常只支持特定张量形状、数据类型、布局和属性组合。

论文以 cuBLAS 等高性能库为例说明：编译器必须识别满足复杂前置条件的子图，然后才能把普通矩阵乘法或融合操作替换为专用内核。传统做法往往把匹配逻辑直接增量写入大型 C++ 编译器实现，难以理解、复用和判断正确性。

作者在 DLCB（一个独立的 GPU AI 编译器后端）中设计 PyPM（嵌入 Python 的模式匹配 DSL），使专家可以以 Python 风格描述张量计算图模式、属性约束和替换规则，并进一步为其核心匹配语言建立可机械化证明的数学基础。

## 2. 论文要解决的问题

### 2.1 如何表达复杂的 AI 计算图模式

模式需要支持固定结构、模式备选、递归子图、非线性变量复用、任意算子函数变量、张量形状/元素类型约束以及局部变量。论文认为仅靠简单树模式不足以覆盖真实模型中的 GELU、MHA、矩阵乘加 epilog 等结构。

### 2.2 如何让匹配实现具有明确的正确性含义

PyPM 的生产实现包含数千行 C++ 匹配代码，原实现没有清晰的独立规格。论文把其核心抽象为 CorePyPM，分别定义声明式语义和带回溯的算法式语义，并证明两者一致，从而给匹配器提供数学依据。

### 2.3 如何验证该语言足以支撑实际优化

作者用手工编写的 FMHA（融合多头注意力）和 GEMM epilog 规则，在 HuggingFace Transformers 与 TorchVision 模型上评估优化效果和匹配编译开销；另外提出“定向图分区”，让匹配器先划出可优化子图，再交给其他 AI 编译器即时生成替换内核。

> 本文主要研究：如何用一个表达力较强、可形式化的子图模式语言，把 AI 编译器中的模式识别和重写规则从难以审计的实现中抽象出来，并验证其核心匹配语义。

## 3. 核心方法概述

PyPM 是嵌入 Python 的 DSL。用户声明算子、定义 `@pattern` 模式和 `@rule` 替换规则；Python 前端通过类似符号执行的方式把定义序列化为可移植模式二进制，DLCB 的 C++ 后端加载这些二进制，在计算图上匹配并进行破坏式重写。

```text
Python 模式/规则定义
        ↓
PyPM 前端拦截方法、断言、赋值和控制流
        ↓
生成 CorePyPM 风格的模式并序列化
        ↓
DLCB 加载模式二进制
        ↓
遍历张量计算图，按顺序尝试模式并在失败时回溯
        ↓
匹配成功后执行规则，替换子图为融合/专用内核
        ↓
输出新的 PyTorch IR 并执行模型基准测试
```

PyPM 的关键构造包括：模式备选 `p || p'`、守卫约束、存在变量、匹配约束、函数变量和递归固定点。匹配算法通过保存替代点、当前变量替换和继续动作来实现确定性的左优先回溯。

本文没有 LLM、SFT、强化学习或模型训练流程；“AI 编译器”指面向机器学习计算图的编译器，不是语言模型驱动的编译器。

## 4. 实验框架与训练流程

本文不涉及模型训练，主要采用静态 DSL、编译器重写和运行时基准测试。

### 4.1 PyPM 前端执行

`@pattern` 和 `@rule` 方法保持 Python 外观。序列化时，前端改写断言、赋值和控制流，把普通 Python 参数替换为符号对象，遍历可能路径并构造模式/规则的核心表示，随后输出可移植二进制。

### 4.2 DLCB 匹配与重写

DLCB 启动时动态加载模式二进制。匹配 pass 反复遍历算子图；对每个节点按原 Python 文件中的顺序尝试模式。备选失败会恢复变量绑定并回溯；成功后执行第一个适用规则，以规则右侧子图替换匹配到的根节点，直到达到固定点。

### 4.3 基准测试流程

模型先由 PyTorch 编译为内部 IR，再转换为 DLCB 内部 IR，运行 PyPM 重写，再转回 PyTorch IR，最后交给 HuggingFace 和 TorchVision 基准脚本运行推理。实验分别关闭 FMHA 和 epilog、单独开启其中一个、同时开启两者，比较模型推理时间分布和匹配编译开销。

### 4.4 形式化流程

CorePyPM 用项、模式、变量替换和函数替换建模匹配；声明式语义描述“什么模式匹配什么项”，算法式语义描述实际状态机如何推进、保存回溯点并报告成功/失败。正文说明该开发在 Coq 中完成并证明语义等价。

## 5. 奖励函数、损失函数或关键公式

本文没有使用强化学习奖励函数或神经网络损失函数。

论文给出的关键数学对象不是训练目标，而是匹配判断。例如，声明式判断可概括为：

```text
p @ <theta, phi> ≈ t
```

其中 `p` 是模式，`t` 是待匹配项，`theta` 是普通模式变量到项的替换，`phi` 是函数变量到算子符号的替换。算法式语义的运行状态包含当前替换、函数替换、回溯栈和待执行动作；匹配失败时从栈中恢复保存状态。

论文的核心定理是声明式匹配与算法式执行的一致性/完备性方向的语义联系。正文与附录给出了匹配弱化、守卫、存在变量、匹配约束、函数变量和递归模式的规则；没有把这些定理表述为性能奖励。

## 6. 实验设置

### 6.1 数据集来源

实验使用 HuggingFace Transformers 基准和 TorchVision 基准中的预训练模型集合。模型以 PyTorch 代码表示，经过 PyTorch 内部 IR、DLCB 内部 IR 和反向转换后进行推理。正文未给出两个基准所包含的模型总数、训练/验证/测试划分或数据集样本规模；这些信息写作“论文中未明确说明”。

### 6.2 模型与工具

| 项目 | 论文明确内容 |
| --- | --- |
| 编译器 | DLCB；PyPM Python 前端与 C++ 匹配后端 |
| 前端/IR | PyTorch；PyTorch 内部 IR；DLCB 内部 IR |
| 优化 | FMHA、GEMM epilog 的手工 PyPM 规则 |
| 形式化工具 | Coq proof assistant；CorePyPM |

### 6.3 对比方法

主要对比是 DLCB 在四种配置下的自身基线：无 FMHA/epilog、仅 FMHA、仅 epilog、两者同时开启。论文不是在比较多个学习模型或多个自动调优器。

### 6.4 评价指标

| 指标 | 含义 | 趋势 |
| --- | --- | --- |
| 相对推理加速比 | 相对未启用两种优化的 DLCB 配置的每模型推理性能 | 越大越好 |

## 7. 实验结果与结论

### 7.1 主要结果

HuggingFace 和 TorchVision 的图表以相对加速比直方图展示 FMHA、epilog 及两者组合相对于未优化基线的分布。正文没有在文字中给出每个模型、均值或中位数的精确数值，因此当前 PDF 内容不足以确认可抄录的统一百分比。论文强调这些实验首先用于证明 PyPM 能表达专家手工编写的有效优化，而不是把“使用融合内核更快”本身作为新发现。

### 7.2 与传统方法的比较

没有独立的传统编译器 pass、自动调优器或人工基线对照实验。比较对象是 DLCB 的不同 PyPM 重写配置。

### 7.3 与其他 LLM 方法的比较

本文没有 LLM baseline，也没有 SFT、提示推理或工具调用模型对比。

### 7.4 消融实验

四种 FMHA/epilog 开关组合提供了模块级对照：可观察单独开启和同时开启的影响。但正文没有把它命名为统计意义上的消融，也没有报告统一的显著性检验。

### 7.5 编译时间和案例

在作者报告的 HuggingFace 与 TorchVision 模型上，FMHA/epilog 匹配 pass 运行至固定点的单模型时间均未超过 3 秒。Epilog 匹配即使最终没有匹配，也比 MHA 匹配花费约两个数量级更长，原因是模型中存在更多矩阵乘法和更多部分匹配检查。作者还给出 `MatMulEpilog` 的定向图分区示例：先识别矩阵乘法后接任意点算子链的子图，再把该子图递归交给 AI 编译器生成融合内核；该方向在正文中作为概念提出，不能写成已完成的端到端实验结果。

## 8. 主要创新点

### 8.1 创新点一：面向 AI 计算图的高表达力嵌入式模式语言

PyPM 把模式备选、递归、非线性变量、函数变量、张量属性守卫和匹配约束组合在一个 Python 嵌入式 DSL 中，专门服务于把复杂张量子图替换为专用内核。创新不在“使用重写”本身，而在于把这些约束统一成可由 AI 编译器专家编写的语言接口。

### 8.2 创新点二：从实现抽象出 CorePyPM 及双重语义

论文不是只描述 C++ matcher 的工程实现，而是抽象出声明式语义与算法式回溯语义，并在 Coq 中机械化。这样可以区分“哪些图应该匹配”和“实际状态机如何寻找匹配”，为复杂匹配器提供独立规格。

### 8.3 创新点三：将模式匹配用于定向图分区

论文提出利用 PyPM 识别可优化子图，再把子图交给另一个 AI 编译器即时生成替换内核。该设计解决手工规则必须预先提供右侧替换的问题，但正文主要将其作为扩展用例和研究方向说明。

## 9. 局限性

### 9.1 论文明确承认的局限

- PyPM 的优化需要可用的手工替换内核；如果右侧融合内核过于复杂或组合数量过多，手写规则并不现实。
- DLCB 只能理解一大部分 PyTorch 算子；不支持的算子会成为 opaque node，无法被 PyPM pass 匹配。
- 模式匹配具有破坏式重写语义，不是 equality saturation 式的非破坏等价类维护。
- 递归模式若没有合适的基例可能不终止；论文的形式化语义保留了这种可能性。

### 9.2 阅读后发现的潜在局限

- 评测固定在单张 RTX A6000 和两个模型基准，跨 GPU、CPU、RISC-V 或其他 AI 加速器的迁移效果未被验证。
- 论文展示的是手工 FMHA/epilog 规则，不能推出 PyPM 自动发现优化、自动生成内核或普遍优于现有 AI 编译器。
- 文字部分未给出所有模型数、加速分布的精确统计量和置信区间，当前 PDF 内容不足以确认更细的总体结论。
- CorePyPM 语义证明不等于完整 C++ 实现、Python 前端转换器和所有具体属性解释都已被端到端形式化验证。
- 匹配成本与图大小、部分匹配数量和模式顺序有关；复杂递归/回溯规则可能在更大图上产生更高编译时开销。

## 10. 阅读后的研究方向反思

值得借鉴的是“声明式候选变换 + 编译器可执行匹配 + 形式化语义”这一组合：它比让模型直接输出任意 IR 更容易审计，也能把张量形状、数据类型和硬件内核前置条件显式化。

不能简单照搬的是 PyPM 的 GPU/CUDA 内核假设、DLCB 的内部 IR 和破坏式重写策略。仅把目标平台换成 RISC-V 并不足以形成新贡献；需要研究 RISC-V/RVV 自定义扩展、向量长度、对齐和 ABI 约束如何进入模式语义及替换合法性检查。

对现有方向而言，本文更适合作为 GENERATOR 角色的“优化规则/变换语言与验证基础”参考，也可作为 Translator/Selector 系统的规则执行器。它不是 LLM 训练方法，也不是通用的自动调优框架。

## 11. 可进一步尝试的研究方向

### 11.1 面向 RISC-V/RVV 的可验证张量子图重写

#### 研究问题

如何把 RVV 向量长度、LMUL、元素类型、对齐和自定义指令能力编码为可检查的模式守卫，并安全地把张量子图替换为 RISC-V 微内核。

#### 与原论文的区别

不只是把 CUDA 替换为 RISC-V，而是将 ISA/ABI/向量配置约束纳入匹配语义，并在真实 RVV 硬件上测量。

#### 可能的创新点

硬件能力谓词、可证明的规则前置条件、跨 RVV 配置的规则复用和失败边界记录。

#### 实验框架

```text
张量图 → RVV 能力分析 → PyPM 类模式匹配 → 规则重写
       → LLVM/MLIR lowering → QEMU/真实 RISC-V → 语义与性能检查
```

#### 可行性

需要 MLIR/LLVM、RVV 交叉编译器、RVV 模拟器或开发板、形状化测试集和等价性检查工具。

#### 主要风险

向量长度变化、浮点舍入和布局转换可能使图级等价与真实内核行为难以统一；模拟器性能也不能代替真机性能。

### 11.2 从规则匹配到编译器反馈驱动的右侧内核生成

#### 研究问题

当模式识别出可融合子图但没有手工右侧规则时，如何调用 MLIR/TVM/LLVM 后端生成候选内核，并以编译成功、验证和硬件测量作为筛选依据。

#### 与原论文的区别

把论文中的定向图分区概念实现为闭环，而不是只识别子图或预先登记替换内核。

#### 可能的创新点

结构化候选接口、失败可回滚的替换协议、语义验证与真实测量联合选择。

#### 实验框架

```text
PyPM 模式 → 子图分区 → 后端生成多个内核 → 编译/验证/测量
         → 选择可行候选 → 缓存为后续规则
```

#### 可行性

可从少量 GEMM/attention/epilog 模式开始，使用现有 MLIR、TVM、LLVM 和 GPU/RVV 后端。

#### 主要风险

候选生成成本可能超过一次运行收益；有限测试不能替代完整语义证明，且硬件测量噪声会影响选择。

### 11.3 模式匹配器的差分测试与形式化边界审计

#### 研究问题

如何系统地生成同时覆盖声明式语义、算法式回溯和真实 C++ matcher 的模式/项对，定位实现与规格的不一致。

#### 与原论文的区别

重点从“证明 CorePyPM 的语义关系”转向“测试完整工程实现与形式化核心之间的边界”。

#### 可能的创新点

基于模式语法的 fuzzing、回溯路径覆盖、属性解释器差分和可复现反例缩减。

#### 实验框架

```text
生成模式/项/属性 → CorePyPM 求解 → C++ matcher 执行
                 → 比较成功/失败/替换绑定 → 缩减并归档反例
```

#### 可行性

可复用论文附录中的语法和规则，以 Coq 核心或可执行解释器作 oracle。

#### 主要风险

随机模式可能大量不终止或触发指数回溯；oracle 与生产实现的属性域必须严格对齐。
