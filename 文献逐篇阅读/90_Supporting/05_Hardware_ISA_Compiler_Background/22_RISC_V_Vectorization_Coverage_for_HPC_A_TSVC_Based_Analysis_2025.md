## 1. 研究背景

编译器自动向量化是高性能计算领域的一个经典研究课题。自向量化编译器诞生以来，研究人员和编译器开发者一直在努力提升编译器识别和转换向量化机会的能力。为了系统性地评估编译器的向量化能力，研究人员开发了 TSVC（Test Suite for Vectorizing Compilers）基准测试套件。TSVC 最初由 Callahan 等人开发，包含约 150 个测试用例，覆盖了多种循环向量化模式，包括线性循环、归约操作、条件语句、间接寻址、前缀和等，是衡量编译器向量化覆盖率的行业标准工具。

随着 RISC-V Vector Extension（RVV）进入高性能计算领域，一个关键问题浮现出来：当前的编译器对 RVV 后端的向量化支持究竟在多大程度上能够覆盖 HPC 应用中的常见计算模式？x86（SSE/AVX）和 ARM（NEON/SVE）平台上已有大量基于 TSVC 的向量化覆盖率研究，但 RVV 作为新兴的向量架构，其向量长度无关（VLA）的设计给编译器向量化带来了独特的挑战——编译器需要生成与具体 VLEN 无关的代码，同时确保在 diverse VLEN 配置下的向量化覆盖率。

该研究正是在这一需求驱动下展开的，旨在利用 TSVC 基准测试套件系统性地评估 RISC-V 编译器在 HPC 场景下的向量化覆盖率。该工作的意义在于，向量化覆盖率作为编译器成熟度的重要衡量指标，直接影响 RISC-V 在 HPC 领域的竞争力——如果编译器连 TSVC 中的标准模式都无法有效向量化，那么复杂的 HPC 应用的向量化效果更无从谈起。

## 2. 论文要解决的问题

### 2.1 问题一：RISC-V 编译器对 HPC 常见计算模式的向量化覆盖率未知

当前缺乏针对 RVV 后端的编译器向量化覆盖率系统评估。在 x86 AVX-512 和 ARM SVE 等平台上，编译器经过多年优化已经能够覆盖大部分 TSVC 测试用例，但 RVV 后端由于发展时间较短，其向量化覆盖率尚不清楚。这直接影响了 RISC-V 进入 HPC 市场的可信度。

### 2.2 问题二：编译器向量化报告与实际向量化能力之间可能存在差距

编译器可能报告成功向量化但实际上生成的向量代码效率极低，或者编译器可能具备向量化能力但受限于保守的分析策略而没有启用。TSVC 的系统性评估有助于发现编译器在哪些模式上存在漏向量化（missed vectorization）和错误向量化（mis-vectorization）的问题。

### 2.3 问题三：GCC 和 LLVM 在 RVV 向量化支持上的成熟度差异需要量化比较

GCC 和 LLVM 两个主流编译器对 RVV 的支持处于不同的开发阶段，各自的向量化策略和实现质量存在差异。系统性地量化这种差异对于指导编译器开发和用户选择编译器都具有实际意义。

> 本文主要研究：利用 TSVC 基准测试套件系统评估 RISC-V 编译器在高性能计算场景下的向量化覆盖率及其与 x86/ARM 平台的对比。

## 3. 核心方法概述

由于源材料受限，以下方法描述基于 TSVC 基准测试套件的典型使用方式推断。

【推断内容】该研究可能采用以下方法框架：

```
TSVC 基准测试套件（~150 个向量化测试用例）
  ↓
按循环模式分类（归约、前缀和、间接寻址、条件运算等）
  ↓
在 GCC RVV 后端和 LLVM RVV 后端分别编译
  ↓
检查编译器向量化报告（-fopt-info-vec-missed / -Rpass=loop-vectorize）
  ↓
逐一确认每个测试用例是否被成功向量化
  ↓
统计各个类别的向量化成功率
  ↓
与 x86 AVX 和 ARM SVE 上的已有结果进行跨平台对比
```

该方法的优势在于利用 TSVC 已经建立好的一套分类体系，使得研究结果可以直接与 x86 和 ARM 平台上的历史数据进行对比。TSVC 的测试用例从简单到复杂，覆盖了从"容易向量化"到"难以向量化"的各种场景，有助于发现编译器在不同难度层级上的向量化能力边界。

## 4. 实验框架与训练流程

该研究为编译器向量化覆盖率评测类工作，不涉及模型训练。本部分描述实验的执行流程。

### 4.1 测试用例分类与编译

TSVC 基准测试套件的 150 余个测试用例按循环模式分为若干类别：线性循环、归约、条件归约、前缀和、间接寻址、if 转换、符号循环等。每个测试用例在编译时通过编译器的向量化报告（GCC 的 -fopt-info-vec-missed 选项或 LLVM 的 -Rpass=loop-vectorize 选项）获取向量化状态。同时可能需要人工或半自动方式确认编译器报告与实际情况的一致性。

### 4.2 跨平台对比分析

在获取 RISC-V 平台上的向量化覆盖率数据后，与 x86 AVX 和 ARM SVE 平台上的已知数据进行对比。这种跨平台对比可以帮助识别：
- 哪些向量化模式是所有平台通用的（编译器基础设施的能力）
- 哪些模式在 RVV 上表现差于 x86/ARM（RVV 后端特有的缺陷）
- 哪些模式在 RVV 上意外优于 x86/ARM（VLA 架构的潜在优势）

## 5. 奖励函数、损失函数或关键公式

该论文为覆盖率评测类工作，不涉及奖励函数或损失函数。核心评估指标为向量化覆盖率，其计算方法可能如下：

| 公式 | 含义 |
|---|---|
| Vectorization Coverage = (Vec_success / Total_cases) x 100% | 编译器成功向量化的测试用例占比 |
| Category Coverage = (Vec_in_category / Total_in_category) x 100% | 每个类别内的向量化成功率 |
| False Positive Rate | 编译器报告向量化但实际未向量化的比例 |
| False Negative Rate | 编译器未报告向量化但实际可向量化的比例 |

其中 Vec_success 为编译器成功向量化的测试用例数量，Total_cases 为 TSVC 中所有可测试用例的总数。对于每个向量化模式类别，单独计算其覆盖率。

## 6. 实验设置

### 6.1 数据集来源

TSVC（Test Suite for Vectorizing Compilers）基准测试套件，包含约 150 个 C/Fortran 编写的向量化测试用例。TSVC 最初由 Callahan 等人于 1990 年代提出，后续由 Maleki 等人扩展和改进，是向量化编译器评估领域最广泛使用的基准测试集之一。

### 6.2 模型与工具

- GCC RVV 后端（version 14 / 15，取决于论文写作时间）
- LLVM/Clang RVV 后端（version 18 / 19）
- RISC-V 模拟器（Spike / QEMU）或真实硬件（Banana Pi F3 / SiFive 开发板）
- 编译器向量化报告解析工具

### 6.3 对比方法

- GCC 编译时的向量化覆盖率
- LLVM/Clang 编译时的向量化覆盖率
- （可选）与 x86 AVX-512 和 ARM SVE 上已有 TSVC 结果的历史对比

### 6.4 评价指标

- 总体向量化覆盖率（%）
- 各类别的向量化覆盖率（%）
- GCC vs LLVM 的覆盖率差异
- 编译器报告与实际情况的一致性

## 7. 实验结果与结论

### 7.1 主要结果

当前无可用源材料，无法核验具体结果。以下为基于同类平台 TSVC 研究趋势的推测。

【推测内容】根据 x86 和 ARM 平台上 TSVC 研究的常见结果模式推断：
- 简单线性循环和归约操作的向量化覆盖率可能最高（接近 90-100%）
- 带有复杂控制流和间接寻址的循环覆盖率可能较低（50-70%）
- RVV 后端的整体覆盖率可能低于 x86 AVX 和 ARM SVE 的成熟后端
- GCC 和 LLVM 在不同模式上可能各有所长

### 7.2 消融实验

可能的消融分析包括：
- 不同优化级别（-O2 vs -O3 vs -Ofast）对覆盖率的影响
- 不同向量化选项（如 -ftree-vectorize 加与不加）的差异
- -ffast-math 等放宽浮点语义的选项对覆盖率的影响

### 7.3 案例分析

原文很可能包含针对特定失败模式的案例分析，展示某个 TSVC 测试用例在 RVV 后端无法被向量化的具体原因。这些案例是理解编译器局限性的关键窗口，需要获取原文后详细阅读。

## 8. 主要创新点

### 8.1 创新点一：将 TSVC 系统性应用于 RVV 平台

这是较早将 TSVC 基准测试套件系统应用于 RISC-V 向量扩展平台的研究。此前 TSVC 相关的向量化覆盖率研究主要针对 x86 SSE/AVX 和 ARM NEON/SVE，在 RVV 上的应用几乎空白。该工作填补了这一评估空白。

### 8.2 创新点二：跨平台向量化覆盖率对比

通过将 RVV 的向量化覆盖率与 x86 和 ARM 平台上的已有数据进行对比，该研究能够量化 RVV 编译器后端相对于成熟平台的差距。这种跨平台对比对于指导 RVV 编译器开发的优先级具有直接参考价值。

### 8.3 创新点三：编译器之间的系统对比

对 GCC 和 LLVM 两个主流编译器在 RVV 向量化能力上的系统对比，能够揭示不同编译器在向量化策略上的设计差异。

## 9. 局限性

### 论文明确承认的局限（推断）

由于无法获取原文，以下为推测的作者可能承认的局限性：
- TSVC 主要面向 Fortran 和 C 语言的规整循环模式，无法覆盖现代 HPC 中所有重要的向量化场景
- 向量化覆盖率不等同于实际性能提升——被向量化的代码可能效率低下
- 不同平台上的测试环境（硬件平台、编译器版本）可能不完全一致，影响对比的公平性

### 阅读后发现的潜在局限

- TSVC 测试用例规模相对有限（约 150 个），且部分用例较为简单，可能高估编译器在实际 HPC 应用中的向量化能力
- ACM 页面返回 403 错误，该论文的可获取性本身就是一个问题
- 如果实验仅在模拟器上进行而未使用真实硬件，则无法检测到硬件相关的向量化失败
- 该研究是诊断性工作，虽然发现了问题但未提出编译器优化的具体方案

## 10. 阅读后的研究方向反思

【分析内容】向量化覆盖率作为一个度量指标具有两面性：它能快速反映编译器对不同模式的支持程度，但容易误导人认为"覆盖率高即性能好"。对于 CrossTune-RL 研究而言，向量化覆盖率数据的价值在于发现编译器遗漏的模式，这些模式正是 LLM 向量化可以发挥作用的空间。

具体来说，如果 TSVC 分析显示编译器在间接寻址和复杂控制流模式上覆盖率低，那么我们就可以优先设计和测试 LLM 在这些模式上的向量化能力。反之，如果编译器在大多数模式上覆盖率已经很高，那么 LLM 的差异化价值就需要从"更好的代码质量"（而非覆盖率）来体现。

此外，该研究使用的 TSVC 分类体系本身值得借鉴——它提供了一个很好的向量化模式分类框架，可以作为 LLM 向量化能力评估的结构化基础。建议在 CrossTune-RL 的评测体系中引入类似分类，按向量化模式分别评估 LLM 的表现。

## 11. 可进一步尝试的研究方向

### 11.1 方向名称：基于 TSVC 分类的 LLM 向量化能力系统评估

#### 研究问题
LLM 按照 TSVC 的分类体系，在各类向量化模式上的代码生成能力如何？哪些模式是 LLM 的优势领域，哪些是弱点？

#### 与原论文的区别
原论文评估的是编译器的自动向量化能力；本方向评估的是 LLM 的向量化代码生成能力，使用相同的分类体系。

#### 可能的创新点
构建 LLM 向量化能力的基准测试集，与编译器自动向量化进行系统对比，发现 LLM 在哪些模式上具有补充价值。

#### 实验框架
将 TSVC 测试用例的标量版本作为输入，要求 LLM 生成 RVV intrinsic 向量化版本，然后使用与原论文相同的分类体系评估 LLM 的成功率和代码质量。

#### 可行性
TSVC 是公开可用的基准测试套件，可以独立获取和使用。

#### 主要风险
LLM 生成的 intrinsic 代码可能需要人工检查和调试才能正确编译运行，评估成本较高。

## 12. 与其他已读文献的关系

- **与 Paper 21 的关系：** Paper 22（TSVC 覆盖率分析）和 Paper 21（自动向量化性能分析）是同一研究方向的两个互补维度。Paper 22 回答"编译器能识别多少向量化机会"，Paper 21 回答"识别之后实际性能如何"。两者结合才能全面评估 RVV 自动向量化的现状。Paper 22 的覆盖率数据可以作为 Paper 21 性能数据的解释性补充。
- **与 Paper 23 的关系：** Paper 23 揭示了 predication 和 stride load 是当前编译器 cost model 的关键盲区，而 Paper 22 的 TSVC 分析可能从覆盖率角度验证这一发现——例如，涉及条件执行的循环在 TSVC 分类中可能属于"if 转换"类别，而该类别的覆盖率可能低于线性循环类别。
- **与 Paper 24 的关系：** Paper 24（TVM MetaSchedule for RVV）通过调度搜索超越编译器自动向量化。如果 Paper 22 发现编译器在某些 TSVC 模式上覆盖率低，那么这些模式正是需要类似 Paper 24 的搜索方法来弥补的领域。
- **与 CrossTune-RL 的关系：** 该文的向量化覆盖率数据可以作为 CrossTune-RL 研究中评估"需要 AI 辅助向量化的领域"的决策依据——覆盖率低的模式是 LLM 向量化最有可能产生价值的突破口。
