## 1. 研究背景

提高参数规模、微调或 RAG 都不能直接保证生成代码可编译。很多 Agent 系统加入编译器，但很少单独控制变量研究“仅增加编译器反馈”对不同规模模型究竟有多大作用。

## 2. 论文要解决的问题

对 1.35 亿至 700 亿参数的 16 个模型，比较一次性生成与最多五轮 GCC 编译反馈，分析成功率、语义相似度、受益任务和被修复错误类型。

## 3. 核心方法概述

每个 RosettaCode C 任务先由模型生成一次代码作为 baseline；Agent 版本将代码交给 GCC，失败时把原任务、错误代码和完整诊断重新输入同一模型，直至编译成功或五轮耗尽。

## 4. 实验框架与训练流程

```text
任务描述 → 模型生成 C → GCC
        ├─ 成功：结束
        └─ 失败：错误日志+代码回传 → 最多 5 轮
```

不训练模型，不使用单元测试或性能反馈。

## 5. 奖励函数、损失函数或关键公式

无训练损失/奖励。主要结果是 Successful Compile Result；用 BLEU、ROUGE-1 和 CodeBERTScore 比较与参考实现的文本/语义相似度。

## 6. 实验设置

### 6.1 数据集来源

RosettaCode 原有 1,333 个任务，筛出带可直接编译 C 参考答案的 699 个任务，映射到 63 类。

### 6.2 模型与工具

16 个模型，规模 135M–70B；包括 SmolLM、Qwen、Llama 等。工具是 GCC，最多 5 轮反馈，每个任务/模型一次采样。

### 6.3 对比方法

同模型一次性生成与编译反馈 Agent 配对比较，并按模型规模、任务类别和错误标签分析。

### 6.4 评价指标

编译成功率、BLEU、ROUGE、CodeBERTScore，以及语法/未定义引用等错误变化。

## 7. 实验结果与结论

编译器使成功率提高 5.3–79.4 个百分点。Qwen3-4B 提升 79.4 点至 97.4%；Llama3.3-70B 从 92.0% 升到 99.9%。在 Agent 优于基线的任务中，语法错误减少 75%，未定义引用减少 87%，文本/语义相似度总体没有明显恶化。模型规模与“反馈增益”不呈简单正相关，部分小模型 Agent 可超过更大模型。

## 8. 主要创新点

### 8.1 隔离编译器工具效应

不提出复杂新 Agent，而是对编译反馈本身做控制实验。

### 8.2 覆盖宽模型规模

说明工具可部分替代参数规模，而非只服务 7B 以上模型。

### 8.3 错误类型与任务类型分析

定位编译器最擅长修复的语法和符号问题。

## 9. 局限性

“可编译”不等于功能正确，CodeBERTScore 也不能替代测试；只评 C/GCC/RosettaCode、每题单次生成。编译器对算法、性能和语义错误帮助有限，最多五轮的选择也可能影响结论。

## 10. 阅读后的研究方向反思

这篇论文适合作为基础证据：加入编译器能显著减少低级失败，但不能自动形成有创新性的编译优化系统。后续必须引入功能 oracle、性能目标或结构证据。

## 11. 可进一步尝试的研究方向

### 11.1 小模型的分层工具路由

#### 研究问题

错误发生后应调用编译器、测试器、静态分析器还是性能分析器，能否由小模型按诊断类型路由。

#### 与原论文的区别

从单 GCC 循环扩展到多工具且控制调用成本。

#### 可能的创新点

基于不确定性的工具选择与提前停止。

#### 实验框架

```text
候选 → 诊断分类 → 选择 GCC/测试/ASan/perf → 修复 → 预算控制
```

#### 可行性与风险

无需大模型训练；风险是错误可能跨多个类别。

## 12. 与其他已读文献的关系

是 N03 StepCoder、N09 DecLLM、N10 GraphGlue 等复杂反馈系统的基础消融参照；它只证明编译器反馈有效，不证明多 Agent 或性能优化有效。
