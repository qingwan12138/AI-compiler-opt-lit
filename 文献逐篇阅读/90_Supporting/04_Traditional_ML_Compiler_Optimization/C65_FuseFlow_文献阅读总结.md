# FuseFlow 文献阅读总结

论文题目：**FuseFlow: A Fusion-Centric Compilation Framework for Sparse Deep Learning on Streaming Dataflow**

作者：Rubens Lacouture, Nathan Zhang, Ritvik Sharma, Marco Siracusa, Fredrik Kjolstad, Kunle Olukotun, Olivia Hsu

发表时间：2026

发表平台：ASPLOS 2026 Volume 2，23 页，DOI: 10.1145/3779212.3790165
元数据核验来源：[ACM DOI](https://doi.org/10.1145/3779212.3790165)；[作者公开 PDF](https://fredrikbk.com/publications/fuseflow.pdf)
代码/数据/工件：作者代码/artifact 仓库：[FuseFlow](https://github.com/lrubens/fuseflow-artifact)；[Figshare artifact](https://doi.org/10.6084/m9.figshare.30890834)

论文链接或编号：[DOI](https://doi.org/10.1145/3779212.3790165)；[作者 PDF](https://fredrikbk.com/publications/fuseflow.pdf)

关键词：稀疏深度学习、张量编译器、跨表达式融合、数据流架构、设计空间探索

## 1. 研究背景

稀疏权重、激活或输入可减少计算和内存需求，但也带来不规则访存与较低硬件利用率。流式数据流架构通过显式协调功能单元之间的数据移动，适合稀疏计算；编译器需要同时决定融合粒度、并行度、数据流顺序和稀疏 blocking。论文指出，已有 Custard 等方法主要处理单个稀疏张量表达式，不能充分支持机器学习模型中的跨表达式融合与部分融合。

## 2. 论文要解决的问题

### 2.1 跨表达式稀疏融合

如何把 PyTorch 稀疏模型中的多个表达式编译成可融合的数据流图，而不是只在单个表达式内完全融合。

### 2.2 融合与复用的权衡

全模型完全融合可能增加中间状态、同步或资源压力；论文研究不同模型上的融合粒度、数据流顺序和并行参数如何共同影响性能。

> 本文主要研究：如何为稀疏机器学习模型生成并探索跨表达式融合的数据流程序。

## 3. 核心方法概述

FuseFlow 将 PyTorch 模型转换为稀疏抽象机（SAM）表达式，再以 Fusion Table IR 表示跨表达式的融合关系、索引和操作，最后降低到面向 RDA 的稀疏数据流图。它是传统编译器/搜索系统，不涉及 LLM。

```text
PyTorch 稀疏模型
        ↓
稀疏表达式与 SAM 表示
        ↓
Fusion Table IR 建模跨表达式融合
        ↓
枚举融合、并行、数据流顺序和 blocking 配置
        ↓
生成 RDA 数据流图并交给周期精确模拟器
        ↓
性能测量、启发式剪枝与设计空间分析
```

## 4. 实验框架与训练流程

本文不涉及模型训练，主要采用静态编译、配置搜索和硬件模拟。

### 4.1 编译流程

系统先把模型表达式规范化为带索引的稀疏计算，再构造 Fusion Table；Fusion Table 描述每个表达式的迭代空间、操作和跨表达式数据依赖。随后生成不同融合粒度、并行因子、数据流顺序和稀疏 block 配置。

### 4.2 配置评估

候选配置降低为数据流图，交给周期精确模拟器分析微架构行为。FuseFlow 还用快速启发式估计 FLOPs、片上存储与数据复用，以提前剪枝明显次优配置。

### 4.3 硬件验证

论文用 FireSim/Timeloop 相关模拟基础设施进行周期与 DRAM 行为分析，并报告不同融合策略在四类真实稀疏 ML 应用上的结果；论文没有把模拟时间表述为真实芯片实测。

## 5. 奖励函数、损失函数或关键公式

本文没有使用强化学习奖励函数，也没有神经网络损失函数。核心目标是搜索配置的模拟执行代价；论文以周期、带宽/存储行为和模型吞吐等结果比较融合策略。具体统一目标公式在论文中未明确给出。

## 6. 实验设置

### 6.1 数据集来源

实验覆盖四个真实稀疏机器学习应用，包括 BigBird block-sparse attention、GCN、图分析类工作负载以及医学图像/稀疏网络工作负载。论文还考察不同 sparsity pattern（包括 block-diagonal、uniform、power-law 等）。完整训练/测试集划分不适用；模型与稀疏输入作为编译 workload。

### 6.2 模型与工具

输入为 PyTorch 稀疏模型；编译表示包括 SAM 与 FuseFlow Fusion Table IR；目标为可重构数据流架构（RDA）及其周期精确模拟环境。论文正文明确使用 TVM/TACO 等相关系统作比较背景，但没有把 FuseFlow 归为 LLM 系统。

### 6.3 对比方法

主要对比包括未融合 baseline、全融合、部分融合以及不同数据流顺序、并行因子和 block 大小。相关工作还与 Custard、Stardust 等稀疏张量编译方法比较设计差异。

### 6.4 评价指标

| 指标 | 含义 | 方向 |
|---|---|---|
| 模拟周期/执行时间 | 数据流图完成 workload 的代价 | 越小越好 |
| Speedup | 相对未融合 baseline 的加速 | 越大越好 |
| 资源/存储行为 | 融合带来的复用、存储和带宽影响 | 需结合场景 |

## 7. 实验结果与结论

### 7.1 主要结果

全融合并不总是最优，最优融合粒度取决于模型结构和稀疏模式。FuseFlow 能在跨表达式融合、并行化、数据流顺序和 blocking 的组合空间中进行探索。

### 7.2 代表性结果

在 GPT-3 的 BigBird block-sparse attention workload 上，相对未融合 baseline，论文报告最高约 2.7× speedup；该数字来自数据流模拟配置，不是通用硬件实测结论。

### 7.3 消融与案例

图卷积等 workload 显示部分融合可能优于全融合；不同稀疏分布和数据流顺序会改变最优配置。启发式可以快速排除次优配置，但论文没有声称它保证找到全局最优。

## 8. 主要创新点

### 8.1 创新点一：跨表达式稀疏融合

FuseFlow 将融合范围从单表达式扩展到端到端稀疏 ML 模型，并用统一 IR 表示融合关系。实验表明，这一设计能够暴露全融合与部分融合之间的模型依赖性。

### 8.2 创新点二：面向数据流硬件的联合搜索

融合粒度、并行、数据流顺序和 sparsity blocking 被放入同一设计空间，而不是分别手工选择。

### 8.3 创新点三：快速剪枝启发式

用低成本估计帮助缩小模拟搜索空间，降低周期精确评估的开销。

## 9. 局限性

### 论文明确或正文可见的边界

系统目标是特定稀疏表达式、SAM/RDA 数据流模型；支持的算子、硬件资源和模拟器决定了可覆盖范围。实验主要依赖周期精确模拟，论文没有提供通用真实硬件部署结论。

### 阅读后发现的潜在局限

跨模型迁移仍需重新搜索；启发式剪枝的误排风险需要额外验证。与 LLVM/RISC-V 标量或向量后端的直接关系有限，不能仅通过替换目标 ISA 推断同样收益。

## 10. 阅读后的研究方向反思

值得借鉴的是把“变换结构”和“硬件反馈”放在同一个可审计搜索空间中。FuseFlow 本身已经贡献了 Fusion Table 和稀疏数据流编译流程，后续不能只把 RDA 换成 RISC-V 就宣称新颖。它更适合作为传统 ML 编译 baseline、稀疏融合工具模块和硬件反馈实验参考。

## 11. 可进一步尝试的研究方向

### 11.1 面向 RVV 的稀疏融合代价模型

#### 研究问题
如何让融合粒度同时适配 RVV 向量长度、访存模式和稀疏索引开销。

#### 与原论文的区别
目标从 RDA 数据流模拟转为真实 RISC-V/RVV 后端与硬件测量。

#### 可能的创新点
建立向量化收益、索引解码和 cache/带宽的联合代价模型。

#### 实验框架
```text
稀疏模型 → Fusion Table → RVV 配置搜索 → LLVM/RVV 编译 → 板卡测量 → 更新代价模型
```

#### 可行性
需要 MLIR/LLVM、RVV 硬件或模拟器、稀疏模型和 profiling 工具。

#### 主要风险
模拟器与真实硬件偏差、稀疏索引开销难以稳定建模。

### 11.2 可验证的稀疏跨表达式融合

#### 研究问题
如何用代数等价与形状/稀疏性约束证明融合前后语义一致。

#### 与原论文的区别
加入可回溯证明证书，而非只依赖性能模拟。

#### 可能的创新点
为每次融合生成可检查的依赖与边界条件。

#### 实验框架
```text
候选融合 → 约束生成 → SMT/等价检查 → 通过候选进入硬件搜索
```

#### 可行性
需要稀疏张量语义、SMT 和小规模等价验证。

#### 主要风险
复杂动态稀疏模式可能难以形式化。

## 12. 与其他已读文献的关系

与 C64 RedFuser 都研究传统 ML 编译器中的算子融合，但 FuseFlow 面向跨表达式稀疏数据流图，RedFuser 面向级联归约的符号融合条件与 GPU kernel。FuseFlow 更适合作为稀疏数据流设计空间 baseline；C60 的符号基本块 profiling 可作为代价模型特征来源；C21 的自动向量化工作可作为后端连接点。它们均不是 LLM 直接生成代码的工作。

## 13. 一页式总结

| 项目 | 内容 |
|---|---|
| 论文研究任务 | 稀疏 ML 到数据流硬件的跨表达式编译 |
| 核心问题 | 融合粒度与硬件数据流配置如何联合选择 |
| 输入 | PyTorch 稀疏模型/表达式 |
| 输出 | 融合稀疏数据流图 |
| 核心方法 | Fusion Table IR + 配置搜索 + 启发式剪枝 |
| 使用的模型 | 传统编译器；无 LLM |
| 使用的编译器工具 | SAM、Fusion Table IR、周期精确模拟器 |
| 是否使用强化学习 | 否 |
| 是否使用形式化验证 | 未使用语义形式化证明 |
| 数据集规模 | 四类真实稀疏 ML 应用；具体划分不适用 |
| 主要指标 | 模拟周期、执行时间、speedup |
| 最重要实验结果 | BigBird workload 相对未融合约 2.7× speedup |
| 核心创新 | 通用跨表达式稀疏融合与联合设计空间 |
| 主要局限 | 依赖 RDA/模拟器，真实多硬件迁移仍需验证 |
| 与 RISC-V 研究的相关性 | 中：可借鉴融合与反馈框架，但目标硬件不同 |
| 最适合作为 | 传统 ML 编译 baseline、稀疏融合工具模块 |

这篇论文最值得学习的是把稀疏融合粒度视为硬件相关的可搜索决策；最主要的局限是结果依赖特定数据流模型和模拟环境；用于后续研究时，合理方式是把它作为融合与代价建模参考，而不是简单替换成 RISC-V。
