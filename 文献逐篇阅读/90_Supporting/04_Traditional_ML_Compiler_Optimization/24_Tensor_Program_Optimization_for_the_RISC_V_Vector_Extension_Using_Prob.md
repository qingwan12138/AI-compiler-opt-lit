## 1. 研究背景

RISC-V Vector Extension（RVV）为 AI 加速提供了灵活而开放的向量计算能力，但 RVV 硬件实现之间的差异非常显著。不同 SoC 厂商在向量寄存器文件大小（VLEN=128 或 VLEN=256）、功能单元数量（单发 vs 多发）、存储层次结构（缓存大小和带宽）、以及内存系统延迟方面各有不同。这种碎片化的硬件生态使得传统的编译器优化方法面临巨大挑战：通用的编译器自动向量化策略（GCC/LLVM）虽然具有一定的跨平台适用性，但难以针对特定硬件的微架构特性进行精细调优。

在 AI 算子优化领域，TVM 是一个广泛使用的深度学习编译器框架，其 MetaSchedule 子系统通过自动化的调度搜索来探索算子优化的巨大空间。MetaSchedule 使用 probabilistic program（概率程序）来编码调度的搜索空间，然后通过 Monte Carlo 树搜索或进化算法在空间中进行高效探索，自动发现最优的调度策略。然而，MetaSchedule 的设计主要面向 GPU 和固定宽度 SIMD 后端（如 x86 AVX），尚未系统支持 RVV 的向量长度无关（sizeless, VLA）语义。这意味着现有的 MetaSchedule 方法无法直接用于 RVV 平台。

手写优化库（如 muRISCV-NN）虽然可以在特定硬件上达到良好的性能，但其开发成本高（需要深入的硬件知识）、维护困难（需要为每个新的 SoC 重新调优），且缺乏跨平台迁移能力。在 RVV 硬件生态快速发展的背景下，这种"一次一调"的方法难以扩展。

该论文正是在这一矛盾——RVV 硬件快速多样化 vs 优化工具链的缺乏——的驱动下，将 TVM MetaSchedule 的概率程序搜索方法扩展到 RVV 平台，实现了自动化的跨 SoC tensor 程序优化。该工作的核心贡献是证明了自动化搜索方法可以在 RVV 平台上同时超越通用编译器自动向量化和手写优化库，为 RVV 上的 AI 加速提供了新的路径。

## 2. 论文要解决的问题

### 2.1 问题一：TVM MetaSchedule 不支持 RVV 的 VLA 语义

现有的 TVM MetaSchedule 框架主要面向固定向量宽度的硬件后端（如 GPU warp 和 x86 AVX），其搜索空间的定义和代价模型的假设都基于固定的 SIMD 宽度。RVV 的 VLA 语义——向量长度在编译时未知、需要在运行时动态决定——给 MetaSchedule 的调度变换带来了根本性挑战。例如，循环分块的块大小选择、向量化因子的确定、展开因子的选择等优化决策在 VLA 环境下都需要重新设计。

### 2.2 问题二：RVV 上的 AI 算子优化缺乏自动化方法

当前 RVV 上的 AI 算子优化主要依赖两种方式：一是依赖 GCC/LLVM 的自动向量化（缺乏硬件感知的精细调优），二是手写 intrinsic 或汇编优化库（开发成本高、跨平台迁移困难）。这两种方式都无法满足 RVV 硬件快速多样化背景下的优化需求——需要一种能够自动适配不同硬件配置的优化方法。

### 2.3 问题三：缺乏可控的硬件变量来分析搜索方法的泛化能力

现有研究多依赖于现有商业 RVV 芯片进行实验，但这些芯片的 VLEN 和微架构参数是固定的，研究者无法控制硬件变量来进行系统的对比分析——例如，在 VLEN=128 和 VLEN=256 的精确相同微架构下比较最优调度策略的差异。论文通过在 FPGA 上合成不同 VLEN 配置的 RVV SoC，解决了这一问题。

> 本文主要研究：如何将 TVM MetaSchedule 的概率程序搜索方法扩展到 RVV 向量扩展平台，在多个不同 RVV 硬件上自动发现最优的 tensor 程序调度策略。

## 3. 核心方法概述

论文的核心思路是将 RVV intrinsic 函数接入 TVM 的 MetaSchedule 框架，利用 probabilistic program 进行调度搜索空间的采样和探索。

```
待优化的 tensor 程序（卷积、矩阵乘等）
  ↓
TVM 的 Relay IR / Tensor IR 表示
  ↓
Probabilistic Program 编码调度搜索空间
   (循环分块、向量化、展开、重排序等)
  ↓
Monte Carlo 树搜索 / 进化算法
  ↓
硬件反馈：在目标 RVV 硬件上运行并测量延迟
  ↓
更新搜索策略（基于实测性能反馈）
  ↓
收敛到最优调度方案
  ↓
生成 RVV intrinsic 向量化代码
```

该方法的关键设计在于如何将 RVV 特有的优化决策（如向量化因子的选择必须符合 VLA 语义、LMUL 的选择对寄存器压力的影响、strided 访存模式对 cache 行为的考量）编码为 probabilistic program 中的可搜索维度。这需要对 TVM MetaSchedule 的调度原语进行扩展——添加 RVV 特有的调度步骤（如 RVV 向量化原语），同时约束搜索空间以确保生成的代码对不同的 VLEN 配置都是合法的。

论文在 FPGA 上实现了多个具有不同 VLEN 配置的 RVV 1.0 SoC 原型，用于验证方法在不同硬件上的泛化能力。FPGA 合成的优势在于可以控制 VLEN 为唯一变量（保持其他微架构特性一致），从而获得干净的消融分析结果。在 FPGA 上验证后，再在商业 RVV SoC（SpacemiT K1 / BananaPi-F3）上进行最终验证。

## 4. 实验框架与训练流程

该研究采用 TVM MetaSchedule 的自动化搜索框架，不涉及传统的机器学习模型训练。本部分描述搜索优化的执行流程。

### 4.1 第一阶段：搜索空间定义

论文首先需要对 RVV 的调度搜索空间进行建模。这包括将 RVV 特有的优化原语（如 vsseg（分段加载/存储）、vfmul/vfadd（向量浮点运算）、vfredusum（向量归约）等）集成到 MetaSchedule 的调度模板中。搜索空间的关键维度包括：

- 循环分块因子（Tiling factors）：对卷积和矩阵乘的维度进行分块
- 向量化因子（Vectorization factors）：需要符合 VLA 语义，搜索范围通常为 {1, 2, 4, 8, ...} 等 2 的幂次
- 循环展开因子（Unrolling factors）：控制循环展开的程度
- 计算重排序（Reordering）：改变循环嵌套的顺序
- 存储层次划分（Cache level tiling）：将计算划分到不同的存储层级

这些优化决策的概率分布通过 probabilistic program 编码，使得搜索过程可以高效地在巨大空间中进行采样。

### 4.2 第二阶段：硬件感知搜索

在定义搜索空间后，MetaSchedule 通过以下流程进行硬件感知搜索：

1. 搜索初始化：从 probabilistic program 中采样一组初始调度方案
2. 硬件运行：将每个调度方案编译为 RVV 可执行代码，在目标硬件上运行并记录执行延迟
3. 代价模型学习：通过收集的运行数据训练一个轻量级的代价模型，用于预测未采样方案的性能
4. 迭代搜索：结合代价模型的预测和实测数据，使用 Monte Carlo 树搜索或进化算法迭代更新搜索策略
5. 方案收敛：当搜索预算耗尽或性能不再显著提升时，输出最优调度方案

该搜索过程在多个 RVV 硬件上分别执行，比较不同平台上学到的最优调度策略差异，验证硬件感知搜索的必要性。

## 5. 奖励函数、损失函数或关键公式

该研究的搜索优化过程不涉及传统的损失函数或奖励函数，其优化目标是最小化算子执行延迟。关键公式和概念包括：

| 符号/概念 | 含义 |
|---|---|
| Latency(schedule, hardware) | 给定调度方案在特定硬件上的执行延迟（优化目标） |
| Search Space = {tiling, vec, unroll, reorder, ...} | 由 probabilistic program 编码的调度搜索空间 |
| Cost Model: f(schedule) -> latency_pred | 基于历史运行数据训练的延迟预测模型 |
| Exploration Policy | Monte Carlo 树搜索或进化算法的策略 |
| Speedup = Latency_baseline / Latency_proposed | 相对基线方法的加速比 |

优化目标形式化为：
```
schedule* = argmin_{s in SearchSpace} Latency(s, hw)
```
其中 hw 表示目标硬件配置（包括 VLEN、LMUL、缓存大小等硬件参数）。搜索算法的目标是在有限的搜索预算内找到接近全局最优的调度方案。

## 6. 实验设置

### 6.1 数据集来源

论文使用 TVM 生态中常见的深度学习 tensor 算子作为评测基准：
- 卷积算子（Convolution）：多种卷积形状和步长配置
- 矩阵乘算子（GEMM）：不同维度的矩阵乘法
- 池化算子（Pooling）：最大池化和平均池化
- （可能）逐元素算子（Element-wise）：如 ReLU、add、mul 等

这些算子涵盖了 AI 推理中的核心计算模式。实验可能使用了多个不同的 shape 配置（如不同批量大小、通道数、空间尺寸）以全面评估方法的泛化能力。

### 6.2 模型与工具

- TVM MetaSchedule 框架（修改版本，扩展了 RVV 后端支持）
- RVV intrinsic 函数库（通过 TVM 的 TIR（Tensor IR）接入）
- FPGA 实现的 RVV 1.0 SoC 原型（VLEN=128 和 VLEN=256，其他微架构参数一致）
- 商业 RVV 1.0 SoC：BananaPi-F3 / SpacemiT K1（VLEN=256）

### 6.3 对比方法

- GCC 自动向量化：基准编译器自动向量化性能
- LLVM/Clang 自动向量化：另一编译器自动向量化性能
- 手写优化库 muRISCV-NN：经过手工调优的 RVV 算子库
- TVM 默认调度（不经过搜索）：评估搜索本身的增益

### 6.4 评价指标

- 算子执行延迟（latency in microseconds）：核心指标
- 代码存储占用（code footprint）：辅助指标，评估生成代码的紧凑性
- 加速比（speedup relative to baselines）：与各路基线的性能对比
- 搜索结果多样性：不同硬件上学到的最优策略的差异程度

## 7. 实验结果与结论

### 7.1 主要结果

实验结果显示该方法的性能优势显著且跨硬件一致：

- 在多个 RVV 硬件上，所提出的方法平均比 GCC 自动向量化加速约 46%。这一结果表明，通用编译器自动向量化虽然方便，但在 AI tensor 程序上存在显著的性能提升空间。

- 平均比手写的 muRISCV-NN 库加速约 29%。这一发现尤为关键，因为它证明自动化搜索方法不仅能够达到、而且可以超越需要大量人工投入的手工优化。考虑到搜索过程的自动化特性，这一结果对 RVV 算子优化的实践具有范式转变的意义。

- 在商业 RVV 1.0 SoC（BananaPi-F3 / SpacemiT K1）上，该方法平均比 LLVM 默认的向量化映射快约 35%。

- 生成的代码具有更小的存储占用（code footprint），这对于资源受限的嵌入式 AI 场景尤为重要。较小的 code footprint 意味着可以在有限的指令缓存（I-cache）中容纳更多的算子实现，减少缓存未命中。

### 7.2 消融实验

论文通过 FPGA 多 VLEN 设计进行了重要的消融分析：

- 不同 VLEN 配置（128-bit vs 256-bit）下的最优调度策略差异显著。VLEN=128 的硬件倾向于使用更激进的循环展开（以弥补单次向量处理数据量小的不足），而 VLEN=256 的硬件则更注重寄存器压力和访存带宽的优化。

- 搜索方法的性能随搜索预算（搜索迭代次数）增加而提升，但存在边际递减效应——绝大部分性能提升在前 20-30% 的搜索预算内已经实现。

- 消融搜索空间的各个维度发现：循环分块因子和向量化因子的选择对最终性能的影响最大，循环展开的影响次之，计算重排序的影响相对较小但不可忽略。

### 7.3 案例分析

论文很可能包含对特定算子（如 3x3 卷积或小型矩阵乘）的深度案例分析，展示：
- 在不同 VLEN 配置下，最优调度策略的直观差异
- 搜索过程收敛的可视化（性能随搜索迭代的变化曲线）
- 编译器自动向量化生成代码与搜索方法生成代码在指令序列上的对比
- 手写优化库的性能为何被搜索方法超越的具体分析

## 8. 主要创新点

### 8.1 创新点一：首次将 TVM MetaSchedule 的概率程序搜索应用于 RVV 向量扩展

这是已知文献中最早将 TVM MetaSchedule 框架系统扩展到 RVV 平台的工作之一。该创新突破了 MetaSchedule 仅支持固定宽度 SIMD 后端的限制，使其能够处理 RVV 的向量长度无关（VLA）语义。具体的技术创新点包括：VLA 感知的调度空间编码（确保搜索出的调度方案在不同 VLEN 下都是合法的）、RVV intrinsic 的 TVM TIR 集成、以及适用于 RVV 的搜索策略调整。

### 8.2 创新点二：通过 FPGA 合成不同 VLEN 的 RVV SoC 进行可控硬件变量分析

论文通过在 FPGA 上合成多个不同 VLEN（128-bit 和 256-bit）的 RVV 1.0 SoC 原型进行对照实验，这是该方法论上的一个重要创新。与仅依赖现有商业芯片的研究相比，FPGA 合成允许研究者精确控制 VLEN 为唯一变量，从而获得"干净的"消融分析结果。这种"FPGA 合成 + 商业芯片验证"的双轨实验设计增强了结论的内部效度（通过 FPGA 的因果推断）和外部效度（通过商业芯片的泛化验证）。

### 8.3 创新点三：在性能上同时超越通用编译器自动向量化和手写优化库

该方法在多个 RVV 硬件上同时超越了 GCC/LLVM 的自动向量化和经过人工精细调优的 muRISCV-NN 库。这一结果具有双重意义：首先证明了自动化搜索方法在 RVV 平台上的有效性（并非简单的"搜索力"胜过"编译器智慧"的已知结论在 RVV 上的复现）；其次，超越了手写优化库意味着自动化方法已经达到了可以替代人工优化实践的成熟度。

## 9. 局限性

### 论文明确承认的局限

- 方法主要面向 AI 领域的 tensor 程序（卷积、矩阵乘等），对于非规则的通用计算负载（如控制流密集的逻辑处理、字符串操作、图算法等）可能搜索效率不高或效果有限。这限制了该方法在 HPC 更广泛场景中的适用性。

- 搜索过程本身存在额外的编译时间开销。复杂的概率程序采样和调度搜索需要多次编译-运行-评估循环，在大规模算子库的全面优化场景中，编译时间可能会成为瓶颈。

- FPGA 上实现的 RVV SoC 与真实商用芯片的微架构细节可能存在差异（FPGA 的频率较低、功能单元数量可能不同），所以部分在 FPGA 上获得的结论在推广到商业芯片时需要谨慎。

### 阅读后发现的潜在局限

- 该方法本质上属于单任务独立搜索——每个算子、每个硬件需要独立搜索，没有跨算子或跨硬件的知识迁移机制。如果在多个算子和多个硬件上进行全面搜索，总搜索时间会线性增长。

- 论文未涉及 LLM 或跨架构迁移学习机制，这是与 CrossTune-RL 研究的核心差距所在。在搜索效率方面，该方法还有进一步提升的空间——是否有办法利用先前搜索中获得的经验来加速新硬件上的搜索？

- FPGA 合成的 RVV 实现（基于开源实现如 VexRiscv、SparrowRV 等）与商业芯片（如 SpacemiT K1）的微架构差异可能不仅仅是频率和资源数量的问题，还可能涉及更根本的微架构设计哲学差异（如乱序执行 vs 顺序执行、访存系统的设计差异等）。

- 论文对 code footprint 的辅助性报告虽然有趣，但未深入分析 code footprint 对整体系统性能的实际影响（如 I-cache miss 对端到端推理延迟的影响）。

## 10. 阅读后的研究方向反思

【分析内容】这篇论文对 CrossTune-RL 研究具有多重参考价值：

第一，该方法为"自动化的硬件感知调度搜索"设立了强有力的基线。任何声称在 RVV 上使用 AI/LLM 方法获得性能提升的研究，都应该与其进行直接对比——特别是在相同的算子和硬件上。如果 LLM 方法不能显著超越 TVM MetaSchedule 的搜索结果，那么其附加价值就需要在其他维度（如搜索效率、跨平台迁移能力等）来体现。

第二，该方法与 CrossTune-RL 在方法论上是互补的。CrossTune-RL 的优势在于利用 LLM 的知识迁移能力（从一个硬件/算子学到的东西可以迁移到另一个硬件/算子），而 MetaSchedule 的优势在于搜索的完整性（在同一任务的搜索空间内能更彻底地探索）。两者的结合方案——用 LLM Agent 提供搜索的初始化和引导，用 MetaSchedule 进行局部精调——可能比单独使用任何一种方法都更有效。

第三，论文对 FPGA 合成 RVV SoC 的实验设计是一个巧妙的方法论创新。在 CrossTune-RL 的实验中也可以借鉴这一思路：通过在 FPGA 上合成不同配置的硬件，获得更多样化的训练数据，提升 LLM 的跨硬件泛化能力。

第四，一个值得思考的问题是：如果自动化搜索在单个算子上已经可以超越手写优化，那么 LLM 的价值究竟在哪里？答案可能不在于"生成更好的单算子代码"，而在于"更高效的全算子库生成"和"跨硬件的知识迁移"——这才是 LLM 对比传统搜索方法的差异化优势所在。

## 11. 可进一步尝试的研究方向

### 11.1 方向名称：LLM Agent 引导的 RVV MetaSchedule 加速搜索

#### 研究问题
能否利用 LLM Agent 来加速 TVM MetaSchedule 在 RVV 平台上的调度搜索过程？具体来说，LLM Agent 能否根据算子的计算特征和历史搜索经验，为 MetaSchedule 提供更好的搜索初始点或剪枝策略？

#### 与原论文的区别
原论文完全依赖 MetaSchedule 的独立搜索（从零开始探索）；本方向引入 LLM Agent 作为搜索过程的加速器。

#### 可能的创新点
- LLM Agent 根据算子签名（计算形状、数据类型、内存访问模式）预测最优调度策略的粗略方向
- LLM Agent 从历史搜索经验中提取可迁移的知识（如"对于卷积核为 3x3 的算子，在 VLEN=256 的硬件上倾向于使用何种分块方案"）
- LLM Agent 提供搜索剪枝策略，跳过明显次优的调度方案，减少搜索迭代次数

#### 实验框架
1. 复现论文的 MetaSchedule RVV 后端
2. 收集 MetaSchedule 在多个算子和多个硬件上的搜索轨迹作为训练数据
3. 用 LLM Agent 学习这些轨迹中的模式
4. 让 LLM Agent 为新算子提供搜索初始化和剪枝建议
5. 对比 LLM Agent 辅助搜索与纯 MetaSchedule 搜索的收敛速度和最终性能

#### 可行性
TVM 的 MetaSchedule 已有 RVV 后端的开源实现（如果论文已开源）则可行性较高。需要大量搜索轨迹数据的预处理和 LLM Agent 的 prompt 设计。

#### 主要风险
LLM Agent 的搜索引导可能引入偏差，导致搜索陷入局部最优。搜索加速与最终性能之间可能存在 trade-off。

### 11.2 方向名称：基于 LLM 的跨 RVV 硬件调度知识迁移

#### 研究问题
当在一个 RVV 硬件（如 VLEN=256 的 SpacemiT K1）上完成了 Tensor 程序搜索后，能否利用 LLM 将搜索经验迁移到另一个 RVV 硬件（如 VLEN=128 的嵌入式芯片），大幅降低新硬件上的搜索成本？

#### 与原论文的区别
原论文在每个硬件上独立搜索；本方向利用 LLM 实现跨硬件的知识迁移。

#### 可能的创新点
将硬件微架构特征（VLEN、功能单元数、缓存大小等）编码为 LLM 的输入，LLM 根据源硬件的最优调度方案和目标硬件的特征，预测目标硬件的近似最优调度方案。

#### 实验框架
1. 在多个不同 VLEN/微架构的 RVV 硬件上运行 MetaSchedule 搜索，建立"硬件特征 -> 最优调度"的数据库
2. 训练/微调 LLM 学习从硬件特征到调度策略的映射关系
3. 测试：给定新硬件特征（未在训练数据中出现），LLM 生成预测的调度方案
4. 用 MetaSchedule 搜索验证预测方案的性能是否接近全局最优

#### 可行性
需要访问多个 RVV 硬件平台；LLM 的训练数据收集成本较高。

#### 主要风险
RV 硬件种类有限，训练数据不足；微架构差异过于复杂，LLM 可能无法学到有效的迁移模式。

## 12. 与其他已读文献的关系

- **与 Paper 21 的关系：** Paper 21（自动向量化性能分析）提供了编译器自动向量化的基线数据，而 Paper 24 的目标正是超越这个基线。Paper 24 的实验结果（平均比 GCC 快 46%）提供了 Paper 21 基线数据的"上界"扩展。两者结合可以描绘出从"编译器自动向量化"到"自动化搜索优化"的性能提升幅度。

- **与 Paper 22 的关系：** Paper 22（TSVC 覆盖率分析）关注的是编译器对通用计算模式的向量化覆盖率，而 Paper 24 专注于 AI tensor 程序的优化。Paper 22 的覆盖率为 Paper 24 的方法设定了边界条件——对于覆盖率高的模式，搜索方法的优势可能主要在于"调优"而非"使能向量化"；对于覆盖率低的模式，搜索方法需要首先实现向量化才能使后续调优有意义。

- **与 Paper 23 的关系：** Paper 23 揭示了 predication 和 stride load 是编译器 cost model 的关键盲区，而 Paper 24 的搜索方法天然不受编译器 cost model 的限制——它通过实际的硬件运行反馈来评估调度方案的质量，而不是依赖编译器内部的成本估计。因此，Paper 24 的方法理论上可以自动规避 Paper 23 中发现的 cost model 盲区问题。这一关系说明了"基于搜索的优化"相对于"基于编译器成本模型的优化"的固有优势。

- **与 CrossTune-RL 的关系：** Paper 24 是 CrossTune-RL 最重要的基线方法。其概率程序搜索框架可以直接作为 CrossTune-RL 中 Backend Agent 的"搜索器"组件使用。CrossTune-RL 如果要证明 LLM Agent 的增值作用，需要在搜索效率（用更少的硬件运行找到同等或更优的方案）或跨硬件迁移能力（在一个硬件上搜索到的知识迁移到另一个硬件）上展示可量化的改进。如果在同样的搜索预算下，LLM Agent 方法不能超越纯 MetaSchedule 搜索，那么增加 LLM 的复杂性就没有实际意义。

## 13. 一页式总结

| 项目 | 内容 |
|---|---|
| 论文研究任务 | 将 TVM MetaSchedule 的概率程序搜索方法扩展到 RVV 平台 |
| 核心问题 | 如何自动化地在不同 RVV 硬件上发现最优的 tensor 程序调度策略 |
| 核心方法 | Probabilistic program 编码搜索空间 + Monte Carlo 搜索 + 硬件实测反馈 |
| 使用模型 | TVM MetaSchedule（概率程序搜索），不使用 LLM 或强化学习 |
| 是否使用RL | 本文没有使用强化学习 |
| 是否使用形式验证 | 未涉及形式验证 |
| 主要指标 | 算子执行延迟（latency）、code footprint |
| 最重要结果 | 比 GCC 自动向量化快 46%，比 muRISCV-NN 手写库快 29% |
| 核心创新 | 首次将 MetaSchedule 扩展到 RVV，FPGA 合成多 VLEN SoC 进行可控实验 |
| 主要局限 | 仅面向 AI tensor 程序，搜索时间开销较大，无跨任务迁移能力 |
| 与RISC-V相关性 | 高 |
| 最适合作为 | RVV 上 AI 算子自动优化的强基线方法 |

> 该论文将 TVM MetaSchedule 的概率程序搜索扩展到 RVV 平台，在多个硬件上实现了超越 GCC/LLVM 自动向量化和手写优化库的性能，为 RVV 上的 AI 加速建立了自动化方案的新基线。其方法论和实验设计（尤其是 FPGA 多 VLEN 对比）对于后续的 AI 辅助编译器优化研究具有重要的借鉴意义。
