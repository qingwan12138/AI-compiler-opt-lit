## 1. 研究背景

本文研究编译器和异构硬件上的浮点数值不一致问题。相同的浮点程序在不同编译器、优化级别或 CPU/GPU 目标上，可能因舍入、精度处理、FMA 以及激进优化而产生不同结果。此类差异不一定导致崩溃，通常也很小，因此比显式编译错误更难发现。

传统方法包括随机程序生成、语法/文法驱动生成、变异测试和差分测试。论文重点对比的 `Varity` 使用文法随机生成 C/CUDA 浮点程序并跨编译器比较结果，但没有利用领域知识或之前成功触发不一致的测试样例。论文认为，LLM 已经见过大量代码，可能生成更有结构、更接近 HPC 计算模式的浮点程序；但如果不加约束，也容易产生不可编译或无信息的代码。

## 2. 论文要解决的问题

### 2.1 浮点程序空间大且难以有效覆盖

单纯随机生成难以在有限预算内覆盖有意义的表达式、循环、分支和数组访问组合。

### 2.2 不一致触发条件隐蔽

不一致往往依赖特定浮点运算组合、编译器配对和优化级别，且不一定表现为异常值或程序崩溃。

### 2.3 生成质量与探索多样性的矛盾

从头生成可以探索新程序，但容易重复；利用成功样例可以提高命中率，但可能陷入相似结构。

> 本文主要研究：如何用受文法约束并结合历史成功样例的 LLM，生成能够触发跨编译器/优化级别浮点结果不一致的有效 C 程序。

## 3. 核心方法概述

LLM4FP 是一个程序生成与编译器差分测试框架，包含 Grammar-Based Generation（基于文法生成）和 Feedback-Based Mutation（基于反馈的变异）两种互补策略。LLM 生成的是新的浮点 C 测试程序，不是编译器 pass、优化规则或某次输入的优化配置。

```text
选择生成策略
        ↓
构造结构/文法/成功样例提示词
        ↓
GPT-4.1 生成浮点 C 程序
        ↓
编译 C 版本与 CUDA 版本
        ↓
在 gcc/clang/nvcc 及多个优化级别上执行
        ↓
按浮点结果的十六进制位模式做差分比较
        ↓
发现不一致的程序进入 successful set
        ↓
成功样例反馈给下一轮变异生成
```

生成程序固定为 `main` 和 `compute` 两个函数；`compute` 接收标量浮点参数、执行计算并打印一个标量结果。内部文法允许单/双精度、加减乘除、括号、C 数学库函数、嵌套循环、条件分支、临时变量和数组索引。生成的 C 程序还会被改写为 CUDA kernel，在单 block/单 thread 配置下与 CPU 版本比较。

## 4. 实验框架与训练流程

### 4.1 文法生成阶段

第一条程序总是使用 Grammar-Based Generation，因为初始时没有成功样例。提示词包含精度、程序结构、内部文法、只使用 `stdio.h`/`stdlib.h`/`math.h`、初始化变量、避免未定义行为以及只输出代码等约束。

### 4.2 反馈变异阶段

当已有程序触发至少一个不一致后，系统随机选择一个成功样例，要求 LLM 在保持关键结构、精度和有效计算模式的同时，重排或加深表达式、修改常数、加入控制流、替换数学函数或插入中间计算，生成不同程序。

### 4.3 编译、执行与反馈

系统用多个 host/device 编译器和六种优化设置编译程序；只有成功编译的二进制进入执行阶段。若任意编译器对/优化级别的输出在浮点结果十六进制表示上不相等，程序就进入成功集合。

本文不涉及模型训练、SFT、PPO、GRPO 或强化学习；GPT-4.1 以提示词推理方式调用。也不使用形式化等价证明，差分比较只是在给定输入上的动态观测。

## 5. 奖励函数、损失函数或关键公式

本文不涉及强化学习奖励函数或训练损失。核心是差分测试统计量。

```text
Total # Comparisons = C(C, 2) × O × N
Inconsistency Rate = # Inconsistencies / Total # Comparisons
```

其中 `C` 是编译器数量，`O` 是优化级别数量，`N` 是生成程序数量。论文用输出的浮点十六进制表示判断逐对结果是否不一致；它不把每个不一致都断言为编译器 bug，因为差异可能是允许的浮点行为或程序未定义行为造成的假阳性。

## 6. 实验设置

### 6.1 数据集来源

论文没有使用传统训练/测试数据集。每种方法生成 1,000 个程序，每个程序配一个唯一输入值集合；程序运行结果构成动态差分测试数据。默认使用 FP64，论文说明可扩展到 FP32，但本实验未以 FP32 作为主要设置。

### 6.2 模型与工具

| 项目 | 设置 |
|---|---|
| LLM | GPT-4.1，版本 `gpt-4.1-2025-04-14` |
| 生成参数 | temperature 1.2；frequency penalty 0.5；presence penalty 0.6 |
| 生成策略概率 | Grammar-Based 0.3；Feedback-Based Mutation 0.7 |
| 编译器 | gcc 9.4、clang 12.0、nvcc 12.3 |
| 优化级别 | `O0_nofma`、`O0`、`O1`、`O2`、`O3`、`O3_fastmath` |
| 硬件/系统 | NVIDIA RTX A6000；x86_64；Ubuntu 20.04 |
| 代码与数据 | 论文结论声明已公开，仓库为 `ucd-plse/LLM4FP` |

`O0_nofma` 使用 `-O0` 并关闭 FMA；`O3_fastmath` 使用 gcc/clang 的 `-ffast-math` 或 nvcc 的 `--use_fast_math`。每种方法的总比较规模为 18,000 次，来自 1,000 个程序、3 个编译器对和 6 个优化级别。

### 6.3 对比方法

- `Varity`：文法驱动的随机浮点程序生成和差分测试。
- `Direct-Prompt`：只给 LLM 生成有效浮点 C 程序的提示词，不提供文法或样例。
- `Grammar-Guided`：给 LLM 提供本文采用的程序结构和文法，但不使用成功样例反馈。

### 6.4 评价指标

| 指标 | 含义 | 方向 |
|---|---|---|
| Inconsistency Rate | 不一致输出比较次数占全部比较次数的比例 | 越大越好 |
| # Inconsistencies | 发现的不一致总次数 | 越大越好，但不等于真实 bug 数 |
| Time Cost | 生成、编译和执行完整 1,000 个程序的总耗时 | 越小越好 |
| CodeBLEU | 生成程序两两代码相似度平均值 | 越低表示多样性越高 |
| NiCad clone count | Type-1、Type-2、Type-2c 代码克隆情况 | 越少表示重复越少 |

## 7. 实验结果与结论

### 7.1 主要结果

表 2 在相同的 1,000 程序预算和 18,000 次比较下给出：

| 方法 | 不一致率 | 不一致数 | 总耗时 | CodeBLEU |
|---|---:|---:|---:|---:|
| Varity | 11.93% | 2,147 | 00:30:42 | 0.3581 |
| Direct-Prompt | 14.23% | 2,562 | 04:16:37 | 0.3561 |
| Grammar-Guided | 16.47% | 2,964 | 05:56:13 | 0.3442 |
| LLM4FP | 29.33% | 5,280 | 05:37:42 | 0.2788 |

LLM4FP 相对 Varity 的不一致率约为 2.5 倍；CodeBLEU 更低，表示生成程序更不相似。代价是 LLM API 调用使完整测试耗时从约半小时增加到约 5.6 小时。

### 7.2 不一致类型

LLM4FP 的 98.48% 不一致属于 `{Real, Real}`，即两个结果都是正常或次正规实数但位表示不同。相比之下，Varity 更常产生 NaN、无穷大等极端值。论文把 `{Real, Real}` 视为更难被察觉、但不一定自动等同于真实 bug 的差异。

### 7.3 编译器与优化级别比较

LLM4FP 总体上在 host-device 对之间更容易发现差异：`gcc`–`nvcc` 总不一致率为 13.01%，`clang`–`nvcc` 为 12.57%，而 `gcc`–`clang` 为 3.74%。在 `O3_fastmath` 下，`clang`–`nvcc` 达到 2.82%。同一编译器内部相对于 `O0_nofma` 的比较中，LLM4FP 在 gcc、clang、nvcc 上的总率分别为 2.91%、4.60%、2.56%。

### 7.4 消融与变体比较

论文没有单独命名为 ablation 的实验，但 `Direct-Prompt` 与 `Grammar-Guided` 构成了生成约束的逐步比较，完整 LLM4FP 再加入成功样例反馈。Grammar-Guided 比 Direct-Prompt 的不一致率高 2.24 个百分点，LLM4FP 比 Grammar-Guided 高 12.86 个百分点，说明文法约束和成功样例反馈都对本实验设置有帮助。

### 7.5 多样性与克隆分析

所有方法均未检测到 Type-1、Type-2 或 Type-2c 克隆。LLM4FP CodeBLEU 为 0.2788，比 Varity 的 0.3581 低 22.14%。这说明反馈变异没有只重复表面形式，但 CodeBLEU/克隆分析仍不能证明每个程序触发的是不同根因。

## 8. 主要创新点

### 8.1 面向浮点编译器差分测试的 LLM 程序生成

论文把 LLM 的代码生成能力直接用于生成专门针对浮点不一致的测试程序，而不是普通代码补全或通用 fuzzing。实验表明，在本文的编译器、GPU 和预算配置下，它提高了不一致发现率。

### 8.2 文法生成与成功样例反馈的组合

文法负责约束程序结构和可编译性，成功样例反馈负责把搜索引向已有高价值模式附近的新程序。该组合是方法机制上的主要贡献；仅仅“使用 LLM”不是创新本身。

### 8.3 将浮点差分结果转为下一轮生成上下文

系统把触发不一致的程序加入成功集合，形成生成—编译—差分—再生成的闭环。它不是训练 LLM，而是推理阶段的样例条件化搜索。

## 9. 局限性

### 9.1 论文明确承认的局限

- LLM API 延迟使大规模测试成本明显高于 Varity。
- 提示词不能保证完全没有未定义行为，可能造成假阳性。
- 效果依赖精心设计的结构约束、语义约束、格式约束和变异策略。
- 发现的数值不一致不一定是编译器 bug，可能是允许的浮点行为或程序不稳定性。
- 实验没有使用可获得但缺少 AIX 环境的 xlc 编译器。

### 9.2 阅读后的潜在局限

- 仅比较单一输入下的输出位模式，不能单独证明语义错误或 IEEE 违规。
- C 转 CUDA 使用单 block/单 thread，不能代表复杂 GPU kernel、并行竞态或真实 HPC 工作负载。
- 程序预算为每方法 1,000 个，关于更大预算、更多模型和更多编译器版本的可扩展性，当前 PDF 内容不足以确认。
- CodeBLEU 和有限克隆类型只能近似衡量多样性，不能确认触发了不同编译器根因。
- 论文没有报告基于 sanitizer、精确高精度 oracle 或人工 triage 后的真实 bug 数量。

## 10. 阅读后的研究方向反思

LLM4FP 最适合作为 `GENERATOR/G4` 的 compiler test-generation/fuzzing baseline 与工具模块。它不是 `TRANSLATOR`：最终产物不是对输入程序的语义保持改写，而是新生成的测试程序；也不是 `SELECTOR`：LLM 没有选择现成 pass、优化 flag 或编译配置作为最终产物，编译器配置主要由实验驱动器枚举。

对 LLVM/RISC-V 研究的启发是，可以借鉴“结构约束 + 成功样例反馈 + 编译/运行差分”的闭环，但仅把 nvcc 替换成 RISC-V 编译器不构成充分创新。若用于 RISC-V，应引入 ISA/ABI/向量扩展相关的可编译约束，并定义能区分编译器错误、硬件差异和浮点规范允许差异的 oracle。

## 11. 可进一步尝试的研究方向

### 11.1 面向 RISC-V 向量编译器的浮点差分生成

#### 研究问题

如何生成能覆盖 RVV 向量化、FMA、舍入模式和标量/向量路径差异的测试程序。

#### 与原论文的区别

不只是更换目标编译器，而是把 RVV intrinsic、向量长度和 ABI 约束纳入生成文法，并增加硬件/模拟器一致性分层 oracle。

#### 可能的创新点

结构化 RVV 浮点 grammar、标量—向量配对测试、按失败根因聚类的反馈样例选择。

#### 实验框架

```text
RVV-aware grammar → LLM 生成 C/RVV 程序 → GCC/LLVM/模拟器/硬件
→ 精度与位模式比较 → 根因聚类 → 反馈变异
```

#### 可行性

需要 LLVM/GCC RISC-V 工具链、Spike/QEMU 或真实 RVV 平台、浮点参考实现和测试程序生成预算。

#### 主要风险

硬件、模拟器、库函数和 ABI 差异可能制造大量非编译器因素；必须避免把环境差异误判为编译器缺陷。

### 11.2 根因感知的编译器不一致测试生成

#### 研究问题

如何让反馈不仅表示“发现了不一致”，还表示可能涉及的优化 pass、表达式或代码区域。

#### 与原论文的区别

结合 pLiner/Ciel 类隔离工具、编译器 IR 或优化报告，将成功样例按根因而不是按表面代码选择。

#### 可能的创新点

根因标签化反馈、跨编译器 IR 对齐和面向未覆盖优化区域的样例检索。

#### 实验框架

```text
LLM 测试生成 → 编译/差分 → IR/表达式隔离 → 根因标签
→ 标签条件化反馈变异 → 新测试与 bug triage
```

#### 可行性

可从现有 LLM4FP 仓库、LLVM 优化记录和开源编译器构建开始。

#### 主要风险

IR 级根因标签可能不稳定；需要人工复核或可重复的归因规则。

## 12. 与其他已读文献的关系

- 与本仓库已有的 `RAG-Based Fuzzing of Cross-Architecture Compilers`、`LLM4VV`、`ReFuzzer`、`Germinator` 和 `Mut4All` 同属 GENERATOR/G4 的编译器测试生成方向，但 LLM4FP 专门针对浮点跨编译器/跨优化级别数值不一致。
- 与 `Varity` 的关系最直接：LLM4FP 沿用其高层程序结构、浮点 grammar 和差分思路，但加入 LLM 与成功样例反馈。
- 与通用 LLM compiler fuzzing 方法相比，LLM4FP 的测试 oracle 更窄、更数值化；它不能直接替代面向 ICE、崩溃或优化错误的 fuzzer。
- 作为后续研究组件，LLM4FP 适合提供测试程序生成器；Varity 适合作为效率 baseline；pLiner/Ciel 类工具适合作为不一致定位模块。本文没有验证这些组件组合后的效果，因此组合收益不能写成论文结论。

## 13. 一页式总结

| 项目 | 内容 |
|---|---|
| 论文研究任务 | 生成能触发跨编译器/优化级别浮点不一致的测试程序 |
| 核心问题 | 随机测试命中率低，不一致细微且难触发 |
| 输入 | 浮点程序结构、文法、可选的成功样例与精度设置 |
| 输出 | 可编译的浮点 C 测试程序及其差分测试结果 |
| 核心方法 | Grammar-Based Generation + Feedback-Based Mutation |
| 使用的模型 | GPT-4.1 `gpt-4.1-2025-04-14` |
| 使用的编译器工具 | gcc 9.4、clang 12.0、nvcc 12.3、CUDA、差分驱动 |
| 是否使用强化学习 | 否 |
| 是否使用形式化验证 | 否；使用动态位模式差分比较 |
| 数据集规模 | 每方法 1,000 个程序；共 18,000 次比较 |
| 主要指标 | 不一致率、不一致数、耗时、CodeBLEU、代码克隆 |
| 最重要实验结果 | 29.33% 不一致率、5,280 次不一致、CodeBLEU 0.2788；但耗时 5:37:42 |
| 核心创新 | 面向浮点差分测试的 LLM 生成与成功样例反馈闭环 |
| 主要局限 | 成本高、未定义行为风险、差异不等于真实 bug |
| 与 RISC-V 研究的相关性 | 中；闭环可迁移，但需新增 RVV/ABI/硬件 oracle 机制 |
| 最适合作为 | GENERATOR/G4 baseline 与可复用测试生成工具模块 |

这篇论文最值得学习的是把结构化生成、成功样例反馈和编译器差分执行连成一个轻量闭环；最主要的局限是浮点位差异不能直接等同于编译器 bug，且 LLM 调用成本较高。如果用于后续研究，最合理的使用方式是作为面向特定 ISA/编译器的测试生成 baseline 和模块，而不是简单把目标编译器替换成 RISC-V 后宣称完成新的编译器优化方法。
