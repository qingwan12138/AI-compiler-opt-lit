论文题目：**GapForge: Directed Compiler Fuzzing via Coverage-Gap Analysis**

> 本文档依据 staging 中的 12 页 PDF 正文撰写。论文事实、阅读分析和后续建议分开描述；本笔记不代表已写入正式 taxonomy 或索引。

## 1. 研究背景

论文研究大型 C/C++ 编译器的自动测试。编译器代码库规模大、路径复杂，缺陷可能表现为崩溃、静默错误编译或内存安全问题。现有编译器测试大致分为三类：grammar-aided 方法按语法和语义约束生成程序，mutation-based 方法变异已有程序，LLM-based 方法通过提示生成测试程序。

论文指出，这些方法大多是“程序驱动”的：追求程序多样性或触发已知类型的 bug，却没有明确建模哪些编译器源文件和代码区域尚未覆盖。因此测试会反复进入热点路径，长期覆盖不足的尾部区域持续存在。WhiteFox 已经利用编译器源代码做白盒测试，但论文认为整文件摘要粒度过粗，难以给出触发具体未覆盖分支所需的程序结构和编译选项。

## 2. 论文要解决的问题

### 2.1 编译器范围级覆盖缺口

如何在大型 GCC/LLVM 代码库中选择具有覆盖潜力的文件和未覆盖区域，而不是随机或均匀地生成测试程序。

### 2.2 区域级触发条件推断

如何从未覆盖代码及其邻近已覆盖上下文中推断所需的程序结构、控制流条件和编译选项。

### 2.3 失败反馈的持续利用

如何记录同一文件上曾经编译失败或没有带来新覆盖的 prompt，并在后续生成中避免重复无效策略。

> 本文主要研究：如何利用覆盖反馈、局部代码上下文和 LLM prompt synthesis，定向生成能够触达大型编译器长尾代码区域的 C/C++ 测试程序。

## 3. 核心方法概述

GapForge 的最终输出是面向 GCC/LLVM 的完整、可编译 C/C++ 测试程序集合。系统每轮只选择一个目标文件，针对该文件的未覆盖基本块生成程序，编译并收集覆盖率，再将反馈用于下一轮。

```text
目标编译器源代码 + 初始测试套件覆盖率
        ↓
按文件规模与当前覆盖率计算探索分数
        ↓
选择一个目标文件及其未覆盖连续行段/基本块
        ↓
LLM 阅读未覆盖区域 + 相邻已覆盖上下文
        ↓
推断覆盖目标、程序结构约束、编译选项
        ↓
结合历史失败 prompt 合成生成 prompt
        ↓
LLM 生成完整 C/C++ 测试程序
        ↓
编译、运行、gcov 收集覆盖反馈
        ↓
更新覆盖率和逐文件失败日志，进入下一轮
```

GapForge 包含三个核心组件：

1. **Coverage-driven target selection**：根据文件行数和未覆盖比例选择文件。
2. **Targeted summarization**：将未覆盖行段与上下方最近的已覆盖上下文一起交给 LLM，推断细粒度触发需求。
3. **Requirement-guided prompt synthesis with failure reflection**：把通用约束、目标需求和该文件历史失败 prompt 组合成生成 prompt。

LLM 负责代码理解、需求推断和测试程序生成；编译器、运行器和 `gcov` 负责执行及反馈。论文没有把 LLM 的输出称为语义等价证明，差分测试只用于发现潜在错误编译。

## 4. 实验框架与训练流程

本文不涉及模型训练，主要采用提示推理、编译器执行和覆盖反馈。

### 4.1 目标选择流程

对每个源文件 `f`，论文定义探索分数：

```text
S_f = L_f × (1 - C_f)^2
```

其中 `L_f` 是文件行数，`C_f` 是当前行覆盖率。随后归一化为 `W_f`，再用 `k=10` 计算：

```text
P_f = 1 - (1 - W_f)^k
```

归一化后的 `P_f` 用于每轮抽取一个文件。这个变换避免最高分文件长期垄断选择，同时提升低覆盖文件被访问的机会。

### 4.2 目标区域摘要

系统把未覆盖连续行段划为覆盖目标，并向上、向下扫描到最近的已覆盖行，取得立即包围该区域的上下文。LLM 根据两部分代码推断：总体覆盖目标、每个基本块需要的程序结构，以及达到这些路径所需的编译选项。

### 4.3 Prompt 合成与生成

系统维护逐文件失败日志。生成程序在以下任一情况下记为失败：编译失败；或成功编译运行但没有覆盖新的目标基本块。失败记录包括 prompt、编译错误（若有）和偶然覆盖的区域。文件再次被选择时随机取一个尚未使用的失败案例，要求新 prompt 避免相似结构。

### 4.4 执行反馈

生成完整且可编译的 C/C++ 程序，使用指定编译选项编译并运行，使用 `gcov` 收集目标源文件覆盖率。错误发现阶段还用 `-O0/-O1/-O2/-O3` 编译同一程序，比较不同优化级别的输出。

## 5. 奖励函数、损失函数或关键公式

本文不涉及强化学习奖励函数、SFT、PPO 或 GRPO，也没有训练损失函数。关键优化目标是覆盖驱动的文件选择和经验式 prompt 迭代。

| 公式/机制 | 含义 |
|---|---|
| `S_f = L_f × (1-C_f)^2` | 文件规模与低覆盖率共同决定探索潜力；低覆盖文件被非线性放大。 |
| `W_f = S_f / Σ_j S_j` | 将文件分数归一化为相对权重。 |
| `P_f = 1-(1-W_f)^k` | 用 `k=10` 的非线性变换减少高分文件的重复垄断。 |

论文未定义可微奖励；覆盖率和是否产生新基本块是运行时反馈，不是模型训练奖励。

## 6. 实验设置

### 6.1 数据集来源

论文没有使用传统意义上的固定训练/验证/测试数据集。输入是 GCC/LLVM 源代码、已有测试套件产生的初始覆盖信息以及 GapForge 在线生成的测试程序。

目标范围为：

- GCC 14.3.0：`gcc/*.c` 533,176 LOC、`gcc/cp/*.c` 119,331 LOC、`gcc/c/*.c` 30,310 LOC、`gcc/c-family/*.c` 21,907 LOC、`gcc/common/*.c` 12 LOC。
- LLVM 19.1.0：`IR/*.c` 57,869 LOC、`Analysis/*.c` 67,745 LOC、`Transforms/*.c` 250,007 LOC、`CodeGen/*.c` 108,431 LOC。

论文排除非 x86 的特定后端、构建脚本和主编译流水线之外的辅助工具。GCC 14.3.0 的原有测试套件包含 399,007 个测试；论文报告的 GCC/LLVM core 初始覆盖率分别为 82.93% 和 90.55%。

### 6.2 模型与工具

- 摘要模型：GPT-4o；替代实验使用 DeepSeek-v3.2、Qwen3-max。
- 测试程序生成模型：StarCoder；替代实验使用 Qwen2.5-Coder-14B 和 Qwen2.5-Coder-32B。
- 覆盖工具：Gcov-13。
- 实现：Python。
- 硬件：Intel Xeon Gold 6430，16 vCPUs；NVIDIA RTX 4090 24 GB；120 GB 内存；Ubuntu 22.04.3 LTS。
- 论文没有报告训练这些 LLM 的过程或参数。

### 6.3 对比方法

主要 baseline 包括 Csmith、DST、GrayC、Creal、Fuzz4All、WhiteFox、LegoFuzz 和 Optimuzz。Optimuzz 生成 LLVM IR，因此不参与 GCC 比较。论文还构造了加入 GapForge 文件级目标选择的 `WhiteFox Selection` 变体。

### 6.4 评价指标

| 指标 | 含义 | 方向 |
|---|---|---|
| `#Programs` | 预算内生成的测试程序数 | 不是单独的质量目标 |
| `Cov lines` / `Cov(%)` | 从生成程序本身得到的覆盖行数/覆盖率 | 越大越好 |
| `ΔCov lines` / `ΔCov(%)` | 在原有测试套件基础上新增覆盖的行数/比例 | 越大越好 |
| Tokens | LLM token 消耗 | 通常越小越好，但需结合覆盖 |
| Failures | 崩溃或优化级别间输出不一致 | 发现能力，需人工/开发者确认 |

实验预算主要为 24、48、72 小时；消融和 LLM 替换实验使用 24 小时。

## 7. 实验结果与结论

### 7.1 主要结果

72 小时预算下，GapForge 从生成程序本身得到：

- GCC：480,136 行，68.13% 覆盖；相对原套件新增 3,452 行，+2.89%。
- LLVM：334,528 行，69.11% 覆盖；相对原套件新增 531 行，+1.16%。

与最强 baseline LegoFuzz 相比，GapForge 在 GCC/LLVM 分别多覆盖 22,129/12,341 行；与 Csmith 相比多覆盖 120,157/48,163 行。GapForge 生成的程序数量并非最多，但覆盖效率更高。

### 7.2 长尾区域与 token 成本

论文把跨所有技术平均覆盖率低于 30% 的文件定义为 hard-to-cover 文件，GCC 和 LLVM 分别有 152 和 123 个。72 小时下，GapForge 在这些文件上的覆盖率为 GCC 36.29%、LLVM 39.75%，高于 WhiteFox 的 27.43%/29.65%。

GCC 72 小时 token 消耗中，GapForge 为 976,364，WhiteFox 为 2,304,896；LegoFuzz 为一次性 3,628,548，Fuzz4All 为一次性 186,392。token 数受模型/API 实现影响，不能直接等同于金钱或真实运行时间。

### 7.3 故障发现

24 小时生成程序用于 `-O0/-O1/-O2/-O3` 差分测试。GapForge 在 GCC 发现 5 个、LLVM 发现 7 个失败，共 12 个；其中 8 个是 crash，4 个是 miscompilation。论文给出的分类为 GCC 4 crash/1 miscompilation，LLVM 4 crash/3 miscompilation。

代表案例包括：GCC 中将 `_Thread_local`、`_Noreturn` 和 `register` 等互斥说明符组合导致内部编译器错误；LLVM 中嵌套分支、整数约束、位掩码和条件更新共同触发约束消除逻辑的错误编译。

### 7.4 消融实验

- 随机选目标文件的 `GapForge NFS` 少覆盖 25,580 行、少新增 1,733 行，是下降最大的目标选择变体。
- 去掉 targeted summarization 少覆盖 16,730 行。
- 去掉 covered context 少覆盖 8,540 行。
- 去掉编译选项建议少覆盖 19,480 行。
- 去掉历史失败 prompt 反思少覆盖 2,780 行；论文解释 24 小时内同一文件重复选择较少，72 小时时该机制更有价值。
- `k=10` 在 `k=5` 和 `k=15` 之间取得最佳平衡。

### 7.5 不同 LLM

GCC 24 小时下，使用 DeepSeek-v3.2 做摘要的版本比默认 GapForge 少覆盖 9,385 行、少新增 931 行；使用 Qwen3-max 做摘要少覆盖 7,964 行、少新增 502 行。改用 Qwen2.5-Coder-14B/32B 做生成时，后者达到 478,868 行、67.95% 覆盖和 2,425 行新增覆盖，高于默认配置的 474,780 行、67.37% 和 2,043 行。论文结论是模型选择会影响效果，但所有替代版本仍超过主要 baseline。

## 8. 主要创新点

### 8.1 创新点一：把覆盖缺口作为显式区域级目标

以往方法通常从程序侧生成多样输入；GapForge 从编译器源代码覆盖侧反向选择目标文件和基本块，使测试生成面向具体长尾区域。实验中的 hard-to-cover 文件和消融结果支持这一设计有效。

### 8.2 创新点二：未覆盖区域与相邻已覆盖上下文联合摘要

仅给出未覆盖代码可能缺少控制流和数据流前提。GapForge 提供最近的已覆盖上下文，使 LLM 能推断变量状态、分支条件和函数结构；去除上下文导致覆盖下降 8,540 行。

### 8.3 创新点三：将编译选项纳入触发需求

论文强调一些路径由 `-g`、`-gdwarf-4`、`-fsanitize` 等选项门控。将编译选项和程序结构一起生成，比只改写程序内容更能触发特定代码区域。

### 8.4 创新点四：逐文件失败 prompt 反思

失败记录不是泛化训练数据，而是在线生成中的轻量记忆，用于避免相同文件上的无效结构。其短时收益有限，但在长预算或重点反复测试同一文件时更有潜力。

## 9. 局限性

### 9.1 论文明确承认的局限

- 内部有效性依赖各 baseline 实现和 WhiteFox 的复现质量。
- 外部有效性主要基于 GCC、LLVM 和常见 x86 平台，不能直接推及其他编译器或 ISA。
- 构念有效性主要使用 line coverage、token 消耗和优化级别差分；这些指标不能完全代表测试质量。
- 传统 fuzzer 偏 CPU，LLM 方法依赖 GPU；相同硬件下的测试数量和成本存在硬件偏差。
- LLM/API 的 token 消耗会随实现和服务变化。

### 9.2 阅读后发现的潜在局限

- `-O0/-O1/-O2/-O3` 输出不一致只是潜在错误编译信号，不是形式化证明；论文未把所有 12 个 failure 都等同于已确认 bug。
- 摘要模型和生成模型分工依赖外部 LLM，API 可用性、成本和模型版本会影响复现。
- 目标选择使用源代码行覆盖，可能偏向容易被行执行但不一定语义重要的区域；论文未提供更细粒度的路径语义或优化质量指标。
- 评估主要是 C/C++ 与 x86 主流水线；对 RISC-V、GPU 后端、跨架构编译和多语言前端的迁移性尚未验证。
- 论文报告代码和数据位于 Zenodo，但本次阅读未下载或运行该资源，因此可复现性尚未由本轮实测确认。

## 10. 阅读后的研究方向反思

GapForge 最值得借鉴的是“由编译器内部覆盖缺口反向驱动输入生成”的闭环，而不是简单把 StarCoder 替换为另一模型。它适合作为 GENERATOR/G4 的 compiler-test generation baseline 或定向测试工具模块。

对 RISC-V 的直接替换只能构成平台迁移：例如将 LLVM CodeGen 的 x86 目标换成 RISC-V，并不足以自动形成新颖贡献。更有价值的问题是研究 RISC-V 特有指令选择、向量扩展、ABI、压缩指令或多后端差分条件如何进入“目标区域—触发需求—编译选项”的表示。论文当前没有完成这些内容，不能写成其已验证结论。

## 11. 可进一步尝试的研究方向

### 11.1 RISC-V 后端缺口定向生成

#### 研究问题

如何针对 LLVM RISC-V CodeGen 中未覆盖的指令选择、寄存器分配和 RVV lowering 区域生成可验证测试。

#### 与原论文的区别

增加 ISA/ABI/target-feature 结构化约束，而不是只替换编译器目标参数。

#### 可能的创新点

把 `-march/-mabi`、RVV 向量长度、LMUL、寄存器约束和后端 basic block 共同编码为 target requirement。

#### 实验框架

```text
LLVM RISC-V 源码覆盖
  → 未覆盖后端区域
  → 目标特性/ABI需求摘要
  → 生成 C/LLVM IR
  → llc/clang + Spike/QEMU + 差分检查
```

#### 可行性

需要 LLVM、RISC-V 交叉工具链、QEMU 或 Spike，以及可控的覆盖采集。

#### 主要风险

硬件/模拟器行为、未定义行为和目标特性组合可能造成难以归因的差分信号。

### 11.2 编译器覆盖与语义重要性联合选择

#### 研究问题

如何避免仅优化 line coverage，优先选择对优化正确性或后端风险更重要的区域。

#### 与原论文的区别

在 `S_f` 中加入优化 pass 类型、历史 bug 密度、IR 复杂度或差分失败先验。

#### 可能的创新点

构造覆盖率、风险和触发成本的多目标选择策略，并验证它是否发现更多真实 miscompilation。

#### 实验框架

```text
覆盖/历史bug/IR特征
  → 多目标目标文件评分
  → LLM需求推断与测试生成
  → 覆盖 + 差分 + bug确认
```

#### 可行性

可复用 GapForge 的 prompt/失败日志框架，新增风险特征和确认流程。

#### 主要风险

历史 bug 分布可能造成数据泄漏或过拟合；真实 bug 确认成本高。

### 11.3 多编译器/多 ISA 统一缺口测试

#### 研究问题

同一个生成程序能否同时定位 GCC/LLVM 及 x86/RISC-V 后端的对应覆盖缺口。

#### 与原论文的区别

从单编译器、单平台扩展为带编译器/ISA条件的共享目标表示。

#### 可能的创新点

研究跨编译器覆盖区域映射和平台条件化 prompt，避免把平台特定路径误当作通用缺口。

#### 实验框架

```text
多编译器/多ISA覆盖矩阵
  → 共享与特有缺口分析
  → 条件化测试生成
  → 编译、运行、输出/覆盖交叉验证
```

#### 可行性

需要统一的源程序、交叉编译器和可比的覆盖归一化方法。

#### 主要风险

不同编译器内部代码不可一一对应，跨平台输出差异可能来自合法后端选择而非 bug。

## 12. 与其他已读文献的关系

本笔记只基于当前 PDF 中正文已确认的相关工作，不把未阅读的其他候选写成已验证事实。

- 与 Csmith、DST、GrayC、Creal：同属编译器测试生成，但这些方法分别偏 grammar、配置/覆盖、自适应变异和真实代码种子；GapForge 的区别是 LLM 驱动的源码区域级目标推断。
- 与 Fuzz4All、WhiteFox、LegoFuzz：论文将它们作为 LLM 编译器测试 baseline。GapForge 关注覆盖缺口和失败 prompt 反思；WhiteFox 更聚焦优化代码的白盒摘要；LegoFuzz 通过语义组件/代码块复用生成复杂程序。
- 与 Optimuzz：Optimuzz 生成 LLVM IR 并用 translation validation 定向优化 pass；GapForge 生成 C/C++，使用源代码 line coverage 和优化级别差分。
- 作为语料角色，GapForge 最适合作为 `GENERATOR / G4_Tool_Test_Fuzz_Generation` 的 baseline/tool module，不是 pass selector 或 IR translator。

## 13. 一页式总结

| 项目 | 内容 |
|---|---|
| 论文研究任务 | 覆盖缺口驱动的大型 GCC/LLVM 编译器测试生成 |
| 核心问题 | 现有方法难以触达长期低覆盖的编译器代码区域 |
| 输入 | 编译器源代码、初始覆盖率、未覆盖区域、失败 prompt |
| 输出 | 定向生成的可编译 C/C++ 测试程序集合 |
| 核心方法 | 文件探索分数、区域级摘要、编译选项推断、失败 prompt 反思 |
| 使用的模型 | GPT-4o、StarCoder；替代实验含 DeepSeek-v3.2、Qwen3-max、Qwen2.5-Coder |
| 使用的编译器工具 | GCC 14.3.0、LLVM 19.1.0、Gcov-13、差分优化级别 `-O0` 至 `-O3` |
| 是否使用强化学习 | 否 |
| 是否使用形式化验证 | 否；差分测试不是形式化证明 |
| 数据集规模 | 无固定训练集；目标代码规模见第 6.1 节；GCC 原有测试 399,007 个 |
| 主要指标 | line coverage、增量覆盖、token 消耗、crash/miscompilation failure |
| 最重要实验结果 | 72 小时 GCC 68.13%、LLVM 69.11%；共发现 12 个 failure |
| 核心创新 | 将编译器未覆盖区域作为显式目标，并联合上下文、编译选项和失败反馈生成测试 |
| 主要局限 | 主要验证 GCC/LLVM x86；依赖 LLM/API；覆盖和优化级别差分不能证明语义正确性 |
| 与 RISC-V 研究的相关性 | 中：方法可迁移到 RISC-V 后端，但论文未做 RISC-V 实验 |
| 最适合作为 | GENERATOR/G4 baseline、定向 compiler-fuzzing 工具模块 |

这篇论文最值得学习的是把“编译器哪里没有被测到”转化为 LLM 可以处理的局部代码和触发条件；最主要的局限是验证仍集中在 GCC/LLVM x86 和有限的覆盖/差分指标；如果用于后续研究，最合理的使用方式是作为定向测试生成基线并加入 RISC-V 后端或风险语义约束，而不是简单替换模型或平台。
